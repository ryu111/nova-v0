# 封閉集合成員的殺手盤點

**這份是「已裁定」的結構化紀錄，不是掃描器輸出。**
sol 在 R16 裁定 discovery 與 authority 必須分開：

- **廣召回掃描器只負責找候選，永遠不裁真假。** 它的殺手判定靠散文比對，一定會誤報
  （`POLICY_STOP` 就是現成的例子——08:684 有真殺手，掃描器沒認出來）。
- **候選分批人工確認，每批最多六個，按同一個集合宣告切**，不按檔案數硬湊。
- **hard gate 只讀這份已裁定的資料**，不讀掃描器輸出。
- 清到零後移除 debt baseline，改成絕對不變式；散文掃描器永遠退回 audit-only。

判定值三選一：

| 值 | 意思 |
|---|---|
| `FALSE_POSITIVE` | 掃描器誤報，成員有真殺手（附 locator） |
| `MISSING` | 確認沒有命名殺手，要補 |
| `DECLARATION` | 刻意 record-only／不可准入，機械權力已明文剝奪（附裁定出處） |

**候選總數 42**（22 份計畫，全集來源＝fenced `NAME = "NAME"` 加散文宣告行）。
本檔只收已裁定的；未列出的仍是未裁定候選。

### `OUTPUT_LIMITED`：同一格負控涵蓋兩條 claim，只釘了其中一條的終態

05:301 的固定負控同時服務 `execution.limit.round.externally-enforced` 與
`execution.limit.output-bytes.externally-enforced` 兩條 claim，
控制文字也同時講了「不得把 code point 數誤當 byte 數」與「不得送出第 N+1 個回合 grant」。

**但 Step 1 的 fence 只 parametrize 回合邊界，斷言 `ROUND_LIMITED`；
byte 那半沒有任何斷言指名 `OUTPUT_LIMITED`。**
Step 2 的 `Expected` 寫「FAIL at N+1／UTF-8 case」——**散文提到了，斷言沒有。**

**這是「宣告做一半」的第四個實例**，而且是新變種：
前三個是同一支工具的旗標面做一半（`--write`、`--self-test-failure-propagation`）、
同一個封閉集合的碼做一半（`CATALOG_DIGEST_MISMATCH`）；
這個是**同一格負控涵蓋兩條 claim，只釘了其中一條的終態**。

修法：Step 1 的 parametrize 增 byte 邊界列，斷言 `OUTPUT_LIMITED`
（UTF-8 三 byte 字元讓 code point 數與 byte 數分岔的那一格）。

### 本批的方法論收穫：掃描器不讀 fenced code

`ROUND_LIMITED` 與 `SPEND_LIMITED` 的終態斷言都住在 fenced code 裡，
而掃描器的殺手判定只看固定負控段、`Expected:` 行與含「必須／必紅／不得」的行。

**這是「全集來源太窄」第六次**，這次在掃描器的**殺手判定側**
（前五次分別是：小寫漏檢兩次、ASCII-only 正則、fenced-only 取全集、裁定時 grep 碼字串）。

### 修掃描器時我又踩了一次，而且差點拿壞數字去報告

補 fenced code 時我把「含 `terminal` 的行」也算成殺手行。**但宣告行本身就寫著
`terminals：...`**——於是每個成員都被**自己的宣告行**判為清白，
候選數從 39 掉到 16，09 從 12 個掉到 1 個。

**我差點據此宣布「sol 對 09 的判斷是誤報」。** 實際上是我的殺手判定把宣告行
算進了殺手區——**「驗到一層就以為驗到底」發生在殺手判定上**，第七次同形。

修法：殺手區明確排除宣告行號。修完 **30 個**（09 的成員全部回來，
證實 sol 當初的判斷是對的）。

> **這一條寫在這裡是因為它是這份檔存在的理由**：掃描器的每一次「改進」都可能
> 是把誤報換成漏報。**漏報比誤報糟**——誤報會被逐筆確認擋下，漏報不會有人去看。
> 所以掃描器永不裁真假，只有這份檔裁。

## 附帶稽核：claim 落點是否可解析（14 份 claim 檔全掃）

**動機**：T11 交付時 claim 的兩個 `faulty_subject` 指到不存在的測試函式，

### 結果一：`faulty_subject` 有兩種不相容的表示法

```
① pytest node id      驗收/.../測_指定突變.py::測試_固定負控一_三分之一門檻拒絕為越權

                      pyproject.toml::[tool.mutmut].also_copy[removed]
```

①是「跑這個測試」，②是「把這個符號換成這個變體」。**兩者的解析器不同。**
我第一版稽核假設全是①，於是把 13 個②誤報成「函式不存在」——
**又一次「全集來源太窄」，這次是我對表示法的全集只認了一種。**

列為給 T19 的已知條件，不立案。

### 結果二：一個真的壞落點

`規格/工程/保證/閘必須自動執行.claim.json` 的 `ci-drops-a-gate`：

```json
"faulty_subject": ".github/workflows/驗收.yml::steps[types-removed]"
```

**`.github/workflows/驗收.yml` 不存在**，該目錄下只有 `gates.yml`。

**而它為什麼被改名，正是這條 claim 在講的事**：CLAUDE.md 第 153 行記著實測
——叫 `驗收.yml` 時 GitHub 註冊成功、顯示 active、手動觸發也跑得起來，
但 `push`／`pull_request` 一次都不觸發，UI 上完全看不出異常。

**所以「閘必須自動執行」這條 claim 的負控，指向一個因為「閘靜默不觸發」而被改名的檔案。**
教訓寫進了 CLAUDE.md、也寫進了 workflow 檔名，**唯獨 claim 沒跟著改**。

**提案（待 sol 與 fable 兩票）**：把該 `faulty_subject` 改成
`.github/workflows/gates.yml::steps[types-removed]`。

依 CLAUDE.md「實作者不能改已准入的 ClaimSpec、固定負控」，
**我不自行修改，走提案**——即使這是一個明顯的改名跟進。

```
         不得產生 remaining、0% used 或普通派工 eligibility。
fence：   assert evidence.state is EvidenceState.WINDOW_ROLLED_UNOBSERVED
         assert evidence.remaining is None and evidence.utilization is None
```

其餘四態**全份只出現在 07:18 那一行宣告**——07 的其他八格固定負控（99／154／271／
323／376／434／488／547）逐條讀過，沒有一格對這四態做分類斷言。

### 為什麼這四態不能判 `DECLARATION`

依 sol 在批次三立下的紀律：**`DECLARATION` 只給不參與裁決的欄位。**

QuotaBucket 的五態**直接決定派工資格**（211 那格的控制文字自己寫著
「不得產生……普通派工 eligibility」）。它們參與裁決，所以每一態都要有殺手。

### 修法形狀（供立案，不在本批口徑內）

Task 3 的 Step 1 改成**遍歷五態的參數化**——每態一組 `(observation, now, policy)`
輸入與期望 `EvidenceState`，並各自斷言 `remaining`／`utilization` 該有還是該是 `None`。
`WINDOW_ROLLED_UNOBSERVED` 那格現成，其餘四格照同格式補。

**這與批次二 `OUTPUT_LIMITED` 的修法同形**——都是「現成同格式，把參數化補滿」。

## 附錄：跨計畫 `Task N` 引用的語料表（I13 的回歸基準）

**這張表是逐條列舉語料得來的，不是猜的。** 留檔的理由是 fable 提的：
**下次有人「改進」I13 的 parser 時，這是回歸基準**——少認一種形式不會有人發現。

我第一版只測了以 `01` 開頭的五種樣式，報「跨計畫引用只有 4 處」。
逐條列舉後是 **16 處、四種寫法**。

| 形式 | 實例 |
|---|---|
| `plan NN Task M` | 00:20 `plan 01 Tasks 1`、00:229 `plan 17 Task 1`、00:235 `plan 13 Task 9`、00:242 `plan 01 Task 1`、08:797 `plan 08 Task 1` |
| `計畫 NN Task M` | 05:407 `計畫 08 Task 4`、08:257 `計畫 05 Task 8`、08:666 `計畫 06 Task 8`、10:470 `計畫 03 Task 8` |
| `NN Task M` | 01B:27 `05 Task 7`、09:270 `01 Task 15`、10:112 `09 Task 8`、10:472 `03 Task 8`、20:832 `01 Task 13`、20:835 `01 Task 9` |
| `NN 的 Task M` | 16:313 `15 的 Task 8` |

（09:270 與 20:832 已隨 T12 拆分改號為 `01 Task 16`／`01 Task 14`。）

### 這張表教的兩件事

**一、漏一個形式會在鄰規則長出假陽性。** `NN 的 Task M` 沒被跨計畫規則認出來，
那個 `Task 8` 就掉進「裸 `Task N`」那條，被報成「16 只有 7 個 task」。
**漏報的第二種代價**：不只沒人看見，還會以誤報的樣子出現在**別條規則名下**，
把 debug 引去錯的地方。I13 的「先排除跨計畫 span 再檢裸引用」正是這個耦合的正解
——**規則之間有排他順序時，上游的漏會變下游的誤。**

**二、驗形式覆蓋的測試，樣本要跨值域。** 我測五種樣式時**全部用 `01`**，
於是 `計畫 NN Task M` 我測的是 `計畫 ?01...`、零命中，就結論「不支援也沒差」。
這跟「負控自己不能是假的」同構——**測自己的覆蓋時測資沒跨值域，
零命中會被讀成『不存在』。**

## 補記：我在同一份 PR 裡寫了一個不會發生的「先紅」

改號 PR 的新 Task 12，我寫 Step 2「三格都要紅」。sol 查了 baseline：

- **未知運算已經 fail-closed**——`案例執行.py:60` 的 `比對` 末行就是 `return False`，
  `比對("甲", "SOUNDS_LIKE", "乙")` 現在回 `False`。
- **crash 已經被釘成 `HARNESS_ERROR`**——
  `驗收/保證規格語言/測_敏感度.py::test_negative_自己爆掉不算抓到錯`。

**三格裡有兩格根本不會紅。** 那正是我當天退 T11（那兩格不是真的 faulty subject）
與 T9 補強（負控驗的是複製品）的同一個理由，出現在我自己寫的東西裡。

**而 fable 的審查讓它更糟。** 它的小條件 b 要我照第四問補第三格的 fence 斷言
（「散文提到、斷言沒有」），我照做了——**加的是一個已經為真的性質的斷言**，
使「三格都要紅」這句更站不住。**兩個審查者都沒去查 baseline。**

### 這一筆補上的是第五問

前四問是紅因、紅位、紅的前提、紅有沒有被斷言接住。它們**都假設現在是綠的**。

> **第五問：那個紅現在真的還沒發生嗎？**
> baseline 已經滿足的性質寫成先紅，測試從第一天就是綠的，
> 而它掛著「這一格證明了某件事」的名字。

sol 的修法也值得留：**那兩格不是刪掉，是降級成 named faulty-subject 回歸控制**
——它們防退化，只是不在本 task 內轉紅。**「不是先紅」不等於「沒有價值」。**
