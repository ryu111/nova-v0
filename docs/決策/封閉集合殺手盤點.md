# 封閉集合成員的殺手盤點

**這份是「已裁定」的結構化紀錄，不是掃描器輸出。**
sol 在 R16 裁定 discovery 與 authority 必須分開：

- **廣召回掃描器只負責找候選，永遠不裁真假。** 它的殺手判定靠散文比對，一定會誤報
  （`POLICY_STOP` 就是現成的例子——08:684 有真殺手，掃描器沒認出來）。
- **候選分批人工確認，每批最多六個，按同一個集合宣告切**，不按檔案數硬湊。
- **hard gate 只讀這份已裁定的資料**，不讀掃描器輸出。
- 清到零後移除 debt baseline，改成絕對不變式；散文掃描器永遠退回 audit-only。

判定值三選一：

| 值 | 意思 |
|---|---|
| `FALSE_POSITIVE` | 掃描器誤報，成員有真殺手（附 locator） |
| `MISSING` | 確認沒有命名殺手，要補 |
| `DECLARATION` | 刻意 record-only／不可准入，機械權力已明文剝奪（附裁定出處） |

**候選數不是進度，也不是全集。** 演變鏈（**只有一步是計畫真的改了**）：

```
8 → 42 → 39 → 30 → 33 → 35 → 50
```

| 變化 | 原因 |
|---|---|
| 8 → 42 | 掃描器補上散文宣告來源（原本只認 fenced enum） |
| 42 → **39** | **R15-01／02／03 真的補了三個殺手**——唯一一次計畫變化 |
| 39 → 30 | 殺手判定補讀 fenced code（修掉誤報） |
| 30 → 33 | 殺手判定改帶邊界（`EXHAUSTED` 被 `DEADLINE_EXHAUSTED` 遮等**三個漏報**） |
| 33 → 35 | 認得反引號裡 `A\|B\|C` 的整組宣告 |
| 35 → 50 | 宣告行關鍵詞清單加寬 |

**而 50 不是上限**：關鍵詞清單無法靠加詞修好——09:267 寫的是「cutoff **reasons**」，
那種寫法本來就不在任何詞表裡，fable 是**自己列舉集合**才找到那三個成員的。

> **紀律（sol 的 discovery／authority 分離的最終形）**：
> 掃描器只提候選、**永不裁真假**；而**集合清單的權威來源必須是人逐份列舉**。
> **連 discovery 的數量都不可信，可信的只有逐筆裁定的紀錄。**

本檔只收已裁定的；未列出的仍是未裁定候選。

### `OUTPUT_LIMITED`：同一格負控涵蓋兩條 claim，只釘了其中一條的終態

05:301 的固定負控同時服務 `execution.limit.round.externally-enforced` 與
`execution.limit.output-bytes.externally-enforced` 兩條 claim，
控制文字也同時講了「不得把 code point 數誤當 byte 數」與「不得送出第 N+1 個回合 grant」。

**但 Step 1 的 fence 只 parametrize 回合邊界，斷言 `ROUND_LIMITED`；
byte 那半沒有任何斷言指名 `OUTPUT_LIMITED`。**
Step 2 的 `Expected` 寫「FAIL at N+1／UTF-8 case」——**散文提到了，斷言沒有。**

**這是「宣告做一半」的第四個實例**，而且是新變種：
前三個是同一支工具的旗標面做一半（`--write`、`--self-test-failure-propagation`）、
同一個封閉集合的碼做一半（`CATALOG_DIGEST_MISMATCH`）；
這個是**同一格負控涵蓋兩條 claim，只釘了其中一條的終態**。

修法：Step 1 的 parametrize 增 byte 邊界列，斷言 `OUTPUT_LIMITED`
（UTF-8 三 byte 字元讓 code point 數與 byte 數分岔的那一格）。

### 本批的方法論收穫：掃描器不讀 fenced code

`ROUND_LIMITED` 與 `SPEND_LIMITED` 的終態斷言都住在 fenced code 裡，
而掃描器的殺手判定只看固定負控段、`Expected:` 行與含「必須／必紅／不得」的行。

**這是「全集來源太窄」第六次**，這次在掃描器的**殺手判定側**
（前五次分別是：小寫漏檢兩次、ASCII-only 正則、fenced-only 取全集、裁定時 grep 碼字串）。

### 修掃描器時我又踩了一次，而且差點拿壞數字去報告

補 fenced code 時我把「含 `terminal` 的行」也算成殺手行。**但宣告行本身就寫著
`terminals：...`**——於是每個成員都被**自己的宣告行**判為清白，
候選數從 39 掉到 16，09 從 12 個掉到 1 個。

**我差點據此宣布「sol 對 09 的判斷是誤報」。** 實際上是我的殺手判定把宣告行

> 所以掃描器永不裁真假，只有這份檔裁。

### 結果一：`faulty_subject` 有兩種不相容的表示法

```
① pytest node id      驗收/.../測_指定突變.py::測試_固定負控一_三分之一門檻拒絕為越權

                      驗收/.../測_meta_schema.py::最小_claim+{controls:{positive:[],negative:[]}}
                      pyproject.toml::[tool.mutmut].also_copy[removed]
```

①是「跑這個測試」，②是「把這個符號換成這個變體」。**兩者的解析器不同。**
我第一版稽核假設全是①，於是把 13 個②誤報成「函式不存在」——
**又一次「全集來源太窄」，這次是我對表示法的全集只認了一種。**

**這不是缺陷，但 T19 的落點解析器必須知道有兩種**，否則它會把②全判成查無。

### 結果二：一個真的壞落點

`規格/工程/保證/閘必須自動執行.claim.json` 的 `ci-drops-a-gate`：

```json
"faulty_subject": ".github/workflows/驗收.yml::steps[types-removed]"
```

**`.github/workflows/驗收.yml` 不存在**，該目錄下只有 `gates.yml`。

**而它為什麼被改名，正是這條 claim 在講的事**：CLAUDE.md 第 153 行記著實測
——叫 `驗收.yml` 時 GitHub 註冊成功、顯示 active、手動觸發也跑得起來，
但 `push`／`pull_request` 一次都不觸發，UI 上完全看不出異常。

`execution.terminal.external-authority`。

**批次十二合計：FP 5／MISSING 1。**
加回批次二的五筆，`ExecutionTerminal` 十一成員**全部有紀錄**——
這是第一個**逐成員裁完**的大集合。

### 17 從五收到二、再收到一

fable 初提五成員，sol RETURN（**寫了「五成員」卻沒寫五個名字**）。
fable 重推導自我更正成二成員——`TEMPERATURE`／`TOP_P`／`TOP_K` 零消費端，
是把指紋層參數誤入能力層的湊數。

**我實查時發現它的證據不對稱**：grep 全部計畫檔，`GREEDY` 自己也是零次，
與被排除的三個相同。所以「零消費端」不是 grep 得出來的，是 consumer 分析得出來的。
我把這個不對稱送去請 sol **裁判準而不只裁數字**。

sol 立的判準：

> 成員必須是**可協商的語意能力**；已有明定 consumer 依它改變**准入或選路**，
> 並有獨立負控、防恆真格與 exact-set 保護。

然後用這條判準砍掉 `GREEDY`，理由是**我和 fable 都沒看到的一層**：
`GREEDY ∨ SEED` 的准入條件會**讓沒有 seed 的 probe 鑄出
`SEEDED_OUTPUT_REPEATABILITY_OBSERVED`**，撞上 01B 既有的 `SEEDED_` 語意。

**5 → 2 → 1。每一次都是有人拿判準往回打自己的提案。**

### 19 的撞號是我實查撞到的，草稿沒處理

19:461 已宣告 SimplificationWork 的
`PROPOSED|EVALUATING|AWAITING_APPROVAL|ADMITTING|SUCCEEDED|REJECTED|EXHAUSTED`；
fable 提的需求變更機七成員與它**四個 nonterminal 幾乎同名**，只差

這是 sol 對 03 提的「兩個權威來源互撞」同款危害，**沒有人把它套到 19**。
它直接咬到盤點：批次十一把那四個裁成 `MISSING` ×4，若第二台機器重用同名，

## 語料太窄：整份盤點的「全份別無他處」都只掃了 `docs/計畫/`（2026-08-28）

**發現於 sol 第三十六輪把母項整包 RETURN。** 我與 fable 都判 12 的
`TERMINATE`／`QUARANTINE` 是「真零、全計畫無語意」，sol 指出語意存在於
`docs/決策/sol-新局-第四輪.md`：164 行定 `on_violation: DENY_COMMAND |
TERMINATE_EXECUTION | QUARANTINE_SUBJECT`，201 行定「只有目標權威能執行三種動作」，
316 行定 `QUARANTINED` 的零派工與恢復條件。

### 這不是那五個成員的問題，是整份盤點的語料問題

**每一份計畫的 `**Spec:**` 行都把 `sol-新局-*` 決策檔列為規範來源**（實查：
02、03、04、05、06、07、08、09、10、11、12、13、16、17、18、20 逐份都有）。
決策檔是 Spec，不是討論紀錄。

而本盤點所有「全份只在 X 行」「僅一處」「全計畫無語意」的依據，
**語料都只有 `docs/計畫/*.md`**。

實掃結果：**54 個 `MISSING` 成員裡，37 個出現在決策規範語料中**
（語料＝`sol-新局-*.md`＋`需求-*.md`＋`架構草案.md`；
排除本檔與 `計畫修訂決議.md`——那兩份是在談論這些成員，不是規範它們）。

**「出現」不等於「有規範語意」，也不等於「有殺手」。** 37 是待複驗的上限，
不是已知錯誤數。但每一筆的**依據敘述**都是在錯的語料上算出來的，
所以每一筆都要重新驗依據。

### 為什麼三票沒擋住

三個裁定者用的是同一份語料。**獨立性只能抵銷判斷偏差，抵銷不了共同的輸入缺陷。**
這是「全集來源太窄」第一次發作在**語料層**而不是掃描器層——
前十二次都是「掃描器的樣式漏了某種寫法」，這次是「掃描器掃的目錄少了一半」。
