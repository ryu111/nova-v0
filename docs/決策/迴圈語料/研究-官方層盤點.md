
### prompt 前綴穩定性與 cache 決定性：官方規範、可驗證的「前綴 digest」是否存在，以及 nova 該怎麼落地

**nova_fit**：落點是既有的 `nova/領域/執行/上下文組裝.py`＋`ContextManifest`（計畫 12 T7／T8）與計畫 10 T9 的 cache key，不必新開一層。具體如下。

一、把「前綴的內容與順序」變成 schema，而不是慣例。新增 `規格/執行/PromptPrefixPlan.schema.json`，`additionalProperties: false`：
- `segments: [{index:int, segment_kind, content_digest:str, byte_len:int, is_stable:bool, ttl_class:"1h"|"5m"|null}]`
- `segment_kind` 是封閉枚舉且順序即 index 遞增：`TOOL_DEFS` → `SYSTEM` → `PINNED_DOCS` → `HISTORY` → `CURRENT_QUERY`。這個五段順序官方沒有逐字寫出，是從 Anthropic／Bedrock 的 tools → system → messages 硬性階層加上 append-only 歷史推導的，所以要在 schema 註記為【推論】並在 claim 裡自己背書。
- `prefix_boundary_index:int`：最後一個 `is_stable=true` 的 segment index，即 cache breakpoint 落點；驗證規則直接寫死 Anthropic 那條——breakpoint 不得落在 `is_stable=false` 的 segment 上。
- `stable_block_count:int` 且必須 ≤ 20（Anthropic 與 Bedrock 的 lookback window 上限）。
- 多 TTL 時 `ttl_class=="1h"` 的 segment 必須全部排在 `"5m"` 之前（Bedrock 明文約束）。

二、`ContextManifest` 增四個欄位（`ContextManifest` 已是 immutable 且三處同步揭露，正好承載）：
- `prefix_digest: str`（`sha256:` 前綴）
- `prefix_segments: [...]`（同上結構，不含原文，只含 `content_digest` 與 `byte_len`）
- `canonicalization: "RFC8785+UTF8"`（封閉枚舉，未來換規則就換值，不得靜默改）
- `digest_algorithm: "sha256"`（封閉枚舉；vLLM 的教訓是非加密 hash 在多租戶會出事，不要留 xxhash 這種選項）
digest 的構造照 vLLM 的鏈式做法：`h_0 = sha256(canonical(segment_0))`，`h_i = sha256(h_{i-1} || canonical(segment_i))`，`prefix_digest = h_{prefix_boundary_index}`。鏈式的價值是單一比對即涵蓋整段歷史，且能定位第一個分歧點（等同 Anthropic diagnostics 給的那個分類，但我們自己算得出來，不必等 Beta）。

三、計畫 10 T9 的 cache key 從三元組擴成五元組。現在寫的是 `snapshot digest + backend/model exact fingerprint + serialization-policy digest`；缺的是前綴本身與那批「不在 prompt 裡卻會殺掉 cache」的參數：
`cache_key = (prefix_digest, snapshot_digest, backend_fingerprint, serialization_policy_digest, invocation_params_digest)`
`invocation_params_digest` 覆蓋官方點名的欄位集合，逐 backend 定義並存成 `規格/執行/快取影響參數.policy.json`：Anthropic 側 `model`、`tool_choice`、`thinking`、`output_config.effort`、`output_format`、`context_management`、active `anthropic-beta` header 集合、web search／citations／speed 開關；OpenAI 側 `model`、`prompt_cache_key`、`prompt_cache_options`；Bedrock 側 checkpoint 位置與 `ttl`。少一個欄位就是一個會靜默漂移的洞。

四、後端回報的計數收成二手資料，不得升格為證明。新增 `CacheObservation{read_tokens:int, write_tokens:int, source_field:str, rounding:"NONE"|"FLOOR_128", scope}`，明確標註：OpenAI 的 `cached_tokens` 是 `FLOOR_128` 且不含 hidden system tokens，所以它**永遠不能**用來證明前綴逐字相同，只能反證——`prefix_digest` 相同但 `read_tokens==0` 時發 `CACHE_EVICTED_OR_UNAVAILABLE` 事件（對應 Anthropic 診斷矩陣裡「diagnostics=null 但 cache read 低」那一格：是 TTL 問題不是組裝問題），而 `prefix_digest` 不同時直接是我方 bug，不必問後端。這條正好呼應 CLAUDE.md「監看器事件是二手資料」。

五、序列化政策要真的存在，不能靠 Python dict 插入序。`serialization-policy digest` 的內容至少含：JSON 以 RFC 8785 canonicalize、tool `input_schema` 的 key 排序規則、tools 陣列的固定排序鍵（Anthropic 的 `tools_changed` 逐字點名「reordered」與「serialized non-deterministically」兩種成因）、浮點與 Unicode 正規化規則。

六、固定負控（每格都要能 direct red，且必須先看它紅過）：
1. `SYSTEM` 段內插入時間戳 → `prefix_digest` 必須改變，且組裝器回 typed error 而非照送。
2. tools 陣列重排、內容不變 → digest 必須改變（防「語義相同就當相同」的偷懶實作）。
3. tool `input_schema` 的 dict key 以不同插入序建構 → digest 必須**不變**（證明 canonicalization 真的在跑，這格是反向的）。
4. history 非 append-only（改寫或截斷早期 message、tool_result 重新序列化）→ digest 改變。
5. 只改 `tool_choice`／`thinking`／`effort`，prompt 文字一字未動 → `invocation_params_digest` 必須改變。
6. breakpoint 落在 `is_stable=false` 的 segment → 組裝拒絕。
7. 防恆真格兩個：同輸入重跑 100 次 `prefix_digest` 完全相同（呼應 plan 10 已有的 100 rebuild digest parity）；以及把兩個 segment 對調順序不得產生相同 digest（證明 digest 真的綁順序，不是把內容丟進 set 裡 hash）。

七、拿不到 outbound bytes 的後端（opaque CLI：codex、gemini CLI）不得猜。回 typed `UNSUPPORTED_PREFIX_DIGEST`，與計畫 12 T8 已有的「opaque CLI 把 INVOCATION_START 冒充 REASSERT」負控同一路數，也符合「能力不足只回 typed `UNSUPPORTED_*`，不得靜默降級」。

八、claim 落點建議 `規格/執行/保證/前綴逐字穩定.claim.json`（claim id `execution.prefix.byte-stable`），與 plan 10 既有的 `knowledge.cache.acceleration-only` 分工：後者管「cache 不准改內容」，前者管「前綴本身可證同一」。兩者都綠，plan 10 T9 那句「hit/miss 送出的 canonical bytes 必須逐 byte 相同」才有東西可比——目前它比對的對象根本沒有被任何檔案定義。

**坑**：
- Anthropic 以 Common mistake 標題寫死的那個坑：breakpoint 放在含時間戳與使用者訊息的最後一個 block，結果每次都是 cache write、永遠沒有 read——付兩次錢還以為在省錢。lookback 不會救你，因為「writes happen only at breakpoints」，前面那些位置從來沒被寫過。
- tools 陣列重排、或 tool input_schema 的 JSON 被非決定性序列化（key 順序不定）→ Anthropic 的 tools_changed，而 tools 是階層最上層，一動就把 tools/system/messages 整串 cache 全部作廢。這是「程式碼看起來沒改」但 cache 全滅的典型。
- 把對話歷史當可編輯資料而非 append-only：截斷早期訊息、重寫、或把 assistant content 與 tool_result 在重送時用不同方式再序列化 → messages_changed。官方對策逐字是「echo assistant content and tool results back verbatim」。
- 一整類「prompt 文字一字未改但 cache 掉了」的參數漂移：tool_choice、thinking、context_management、output_config、output_format、active anthropic-beta header 集合。Anthropic 對這一類連定位都給不出來，只回 unavailable——也就是說踩到這個坑時，你連官方診斷工具都不會告訴你原因。
- model router、A/B test 或 fallback 在對話中途換模型 → model_changed，因為 cache 是 per-model。這在有自動降級／備援的系統裡是最容易無感踩到的一個。
- 拿 OpenAI 的 cached_tokens 當「前綴相同」的證據：它會向下取整到 128 的倍數，而且 hidden system tokens 不計入。用它反推前綴是否逐字相同一定會得到錯誤結論。
- prompt_cache_key 粒度抓錯的兩個方向：太細（把 session id／thread id 塞進 key，本來該共用前綴的請求被拆散）、太粗（單一 prefix + key 組合超過每分鐘 15 次請求，官方明說會 cache overflow）。
- TTL 從請求「開始」計時而非回應結束：官方舉例，一個串流 4 分鐘的回應，後續請求必須在回應結束後約 1 分鐘內發出才還在 5 分鐘窗內。長輸出的 agent loop 很容易在自以為 30 秒內就發下一輪時已經過期。
- 靜態內容超過 lookback 範圍：Anthropic 與 Bedrock 都寫 20 個 content block，Bedrock 另外警告「If your static content extends beyond this range」就得拆多個 checkpoint 或重排 prompt。內容多反而命不中，直覺相反。
- 混用 1 小時與 5 分鐘 TTL 時順序放反：官方硬性要求長 TTL 的 entry 必須排在短 TTL 之前。
- Bedrock cross-region inference 與 prompt caching 併用：官方註明高需求時的跨區最佳化「may lead to increased cache writes」——命中率在你程式碼沒動的情況下由基礎設施決定。
- vLLM 這類自架引擎選了非加密 hash（xxhash）做 block hash：官方文件明說會「cause undefined behavior or even leak private information in multi-tenant environments」，v0.11 之前的預設演算法本身就不保證無碰撞；多租戶還必須另外注入 cache_salt 才有隔離。

### 重複使用同一組隱藏測試會讓它失效——adaptive data analysis 的資訊預算：官方／權威做法如何把「還能再問幾次」變成可計算的量，以及 nova 的 128 次 sealed clause 回饋觀測該怎麼記帳

**nova_fit**：【一句話】nova 現在的四條界線（時間、錢）界的是「花費」，而 adaptive data analysis 這條線界的是「知識」——差別在於前者用完可以加預算，後者用完之後 sealed clause 就永久失去仲裁資格，而且沒有任何方式把它變回來（只能換一組新的 clause）。所以要加的不是第五個 quota，是一本 append-only 的資訊帳，且它必須跟 deadline／budget 一樣放在候選執行者碰不到的地方（CLAUDE.md：候選執行者不能改 budget）。

【一、先把 nova 的數字算出來，因為算出來的結論很尖銳】
每次回饋回四個封閉 enum：clause_id、outcome_class、location_bucket、retryability。因為都是封閉 enum，單次的資訊上界是靜態常數：
  leaked_bits_per_observation = log2(|clause_id| × |outcome_class| × |location_bucket| × |retryability|)
保守起見假設 outcome_class 6 種、location_bucket 8 種、retryability 3 種、單次只針對一個 clause（clause_id 由查詢決定不算新資訊）→ log2(6×8×3)=log2(144)≈7.2 bits。
8 Pursuit × 16 attempt = 128 次觀測 → 累積上界 ≈ 128 × 7.2 ≈ 920 bits（這是 worst case，等價於 2^920 種可能 transcript）。
把 Bertran–Roth–Wu Corollary 2 的形式（gap ≤ √[(ln N + ln(2/δ)) / (2n)]，N=可能 transcript 數）反解成「要多少獨立案例才撐得住」：
  n ≥ (bits·ln2 + ln(2/δ)) / (2τ²)
代 920 bits、τ=0.1、δ=0.05 → n ≥ (638 + 3.69) / 0.02 ≈ 32,000 個獨立 sealed 案例。nova 的 sealed clause 集不可能有三萬個獨立案例。
反過來解「以現有 n 能負擔幾 bits」：
  bits ≤ (2·n·τ² − ln(2/δ)) / ln2
n=200、τ=0.15、δ=0.05 → bits ≤ (9.0 − 3.69)/0.693 ≈ 7.7 bits ＝ **一次全欄位回饋就把整個 Work 的資訊預算用光**；n=200、τ=0.05 時右邊是負數，代表 200 個案例根本不足以支撐 5% 的泛化落差，連第一次回饋都不該給滿。
這就是「128 次的累積上界沒人算過」的答案：以 worst-case 記帳，現行設計超支兩到三個數量級。

【二、對應的槓桿：把回饋壓成 Ladder 式，帳立刻從 920 bits 掉到 ~36 bits】
照 Blum–Hardt ／ Bertran–Roth–Wu 的 input compression：不回四個 enum，只回「是否比本 Work 目前最佳 outcome 有改善」，並限制改善次數 K_max。可能 transcript 數 N = C(T−1, K−1)；T=128、K_max=8 → C(127,7) ≈ 8.94×10^10 → log2 ≈ 36.4 bits。
同樣代回 n ≥ (36.4·0.693 + 3.69)/(2τ²)：τ=0.1 → n ≈ 1,450；τ=0.15 → n ≈ 642。仍然不小，但從「不可能」變成「有機會設計得出來」。而 arXiv:2606.11045 的實驗結果正好給了這條路的可行性證據：1-bit 回饋在 8 個資料集上表現追平或超過回傳實際分數。

【三、資料結構（欄位名依 CLAUDE.md 用 ASCII）】
1) 新 value object `FeedbackObservation`（append-only，寫在權威層，預設拒絕 unknown fields）：
   - `work_id`, `pursuit_ordinal`, `attempt_ordinal`
   - `clause_id`, `outcome_class`, `location_bucket`, `retryability`（現有四欄照舊）
   - `feedback_mode`: enum { `FULL_ENUM`, `LADDER_ONE_BIT`, `THRESHOLDOUT_NOISY` }
   - `transcript_hash`：本次「對外實際可見內容」的雜湊，用於去重——同一 attempt 重複回同一組值不產生新資訊，不重複扣帳
   - `leaked_bits`：本次扣帳量。`FULL_ENUM` 取 enum 基數乘積的 log2（schema 靜態算出）；`LADDER_ONE_BIT` 只在「宣告改善」時扣 log2(C(T_max−1, j−1)) − log2(C(T_max−1, j−2)) 的增量，未改善扣 0
   - `budget_charged`: bool（Thresholdout 語意：只有落差超過雜訊化閾值才付費）
   - `cumulative_leaked_bits`, `remaining_bits`（由權威層計算後寫入，執行者唯讀）
2) 新 value object `InformationBudget`，掛在 Work（與 sealed clause 集綁定，不是與 Work 綁定的話換 clause 就該重開）：
   - `sealed_case_count_n`：這組 sealed clause 實際有幾個**獨立**案例（不是幾條 assert；相關的案例不能各算一份）
   - `target_generalization_gap_tau`, `confidence_delta`
   - `total_bits_budget` = (2·`sealed_case_count_n`·τ² − ln(2/δ)) / ln2，由前兩者導出，不得手填
   - `feedback_mode`, `T_max`(=128), `K_max`（Ladder 模式的改善次數上限，對應論文的 K_max=7）
   - `noise_scale_sigma`, `threshold_T`（Thresholdout 模式才有）
3) 新 typed failure：`INFORMATION_BUDGET_EXHAUSTED`。預算耗盡時回這個，**不得靜默降級**成「照常回饋」——這正是 CLAUDE.md 那條 UNSUPPORTED_* 規則的同構延伸。Thresholdout 原文的作法就是回 ⊥ 而不是勉強回答。
4) 權限：`remaining_bits`、`total_bits_budget`、`K_max`、`sealed_case_count_n` 全部進「候選執行者不能改」清單，與 deadline／budget／criterion 同級。

【四、要寫成會 fail 的測試（不然依 CLAUDE.md 等於不存在）】
- 負控 A：把 128 次 `FULL_ENUM` 觀測餵進去，斷言在第 ⌈total_bits_budget / 7.2⌉ 次就回 `INFORMATION_BUDGET_EXHAUSTED`；若機制沒接上，這格會綠得很難看——先跑到它紅。
- 負控 B：`sealed_case_count_n` 小到讓 `total_bits_budget` ≤ 0 時，第一次回饋就必須被拒。
- 負控 C：同一 attempt 重送相同 `transcript_hash`，`cumulative_leaked_bits` 不得增加（去重生效）。
- 負控 D：`LADDER_ONE_BIT` 模式下連續 K_max+1 次宣告改善必須被拒；未改善的觀測扣帳為 0。
- 防恆真格：預算充足時正常回饋不被擋，且 `remaining_bits` 確實遞減（避免做出一個「永遠拒絕」或「永遠不扣帳」的假機制）。
- 權限格：執行者路徑嘗試寫 `remaining_bits` 必須被拒。

【五、代價要寫在 docstring 裡，不要只寫在計畫】
- Thresholdout 模式意味著回傳的 `outcome_class` 要加雜訊。enum 上的「加 Laplace 雜訊」實作起來就是 randomized response：有機率回報錯誤的 outcome_class。這對 nova 是很重的代價（執行者會依據假訊號行動），所以預設應該選 `LADDER_ONE_BIT` 而不是 `THRESHOLDOUT_NOISY`。
- Ladder 模式意味著執行者拿不到 location_bucket，除錯訊號變差、attempt 收斂變慢。這是明著用「錢與時間」換「資訊」——而 nova 已經有時間與錢的界線可以吸收這個代價，這正好是四條舊界線與新界線的匯率。
- worst-case 記帳一定會過度保守（Roelofs 實測與 arXiv:2606.11045 的 description-length 解釋都指向真實策略空間遠比 2^bits 小）。務實的折衷是：帳照 worst-case 記，但把 τ 訂在誠實可接受的水準（例如 0.15），並把「壓縮落差」當作偵測器——若把成功策略壓成短描述後在乾淨環境重跑不出來，就判定發生了 sealed-clause 過擬合，這是 arXiv:2606.11045 量到 100% sensitivity／91% specificity 的作法，nova 可以直接對應成「用 Pursuit 的最終 diff 摘要在新 worker 上重跑一次」。

**坑**：
- 回報精度本身就是攻擊面：Blum–Hardt Theorem 5.1 證明，對精度 α ≤ n^(−1/2) 的機制，隨機亂猜的對手用 k 次提交即可把 loss 壓到 1/2 − Ω(√(k/n))；Kaggle 把分數回報到 10^(−5) 正好落在可攻擊區間。教訓是「多回幾位小數」看似無害，實際上是把資訊預算免費送出去。nova 若把 location_bucket 切得太細，等同於這件事。
- 只界次數不界資訊：Kaggle 的每日提交上限＋最終只選 2 份，界的是 k 而不是每次洩漏的 bit 數，因此誤差仍隨 √k 成長（Blum–Hardt 的對照組）。nova 現有的『8 Pursuit × 16 attempt』就是同一種界法——它界了 k，沒界 bits。
- 『沒出事』被當成『安全』：Roelofs et al. 在一百多場 Kaggle 競賽上量到幾乎沒有實質 overfitting，這個結果很容易被引用來論證不需要記帳；但同一篇明確指出離群競賽的病因是 non-i.i.d. 切分或測試集實際上太小——而 nova 的 sealed clause 集正是小樣本，屬於它點名的高風險那一類。
- 有效樣本數被高估：Roelofs 用的措辭是「（實際上）小的測試集」——名目案例數與有效獨立案例數不是同一件事。nova 若把一條 clause 底下高度相關的多個 assert 各算一份 n，算出來的 total_bits_budget 會是假的，帳看起來平衡而實際超支。
- 明確要求『把指標衝高』＋細粒度存取，會可靠地引發過擬合：arXiv:2606.11045 量到在這種設定下 102 個檢查點中有 38 個出現 >10% 的 validation–holdout 落差，而同樣的優勢在 prompt 壓縮後全部消失。nova 的 attempt loop 本質上就是「請把 sealed clause 弄綠」＋逐 bucket 回饋，正是這個高風險組態。
- 以為可以靠更聰明的演算法繞過上限：Steinke–Ullman 證到 O(n²) 次適應性查詢在標準困難性假設下就已經計算上困難，而作者自己的推論是任何高效的通用機制「不妨就是 differentially private 的」。也就是說『不加雜訊、不壓縮、又想無限次回饋』這個組合不是還沒被實作出來，是被證明做不到。
- 廠商官方文件在這題上是空的：Anthropic 官方 evals 指引通篇未談 held-out 切分或 eval overfitting，反而鼓勵持續迭代 evals；搜尋也未找到 OpenAI 對應的成文規範。若照『優先序：官方文件 > 論文』直接抄官方，會抄到一份沒有這條防護的指引——這題目前的權威只存在於同儕審查論文那一級。

### 工程度量的官方事件 vocabulary 與投影純度：OTel gen_ai/CI-CD semconv、OTel event 命名規則、DORA 官方指標定義、CDEvents，以及 event sourcing 對 projection 必須是純函式的論述

**nova_fit**：## 一、事件信封：照 CDEvents + fourkeys 的交集釘死欄位

不可變事件表 `度量事件`（append-only，只有 INSERT，沒有 UPDATE／DELETE），欄位名全 ASCII（CLAUDE.md 的 schema 欄位名例外條款）：

- `event_id` — ULID，全域唯一，PRIMARY KEY。
- `event_name` — 例 `nova.gate.run.finished`、`nova.task.claim.admitted`、`nova.external.snapshot.captured`。**照 OTel 條文執法**：全小寫、點分隔 namespace、以字母開頭、以英數結尾、無連續分隔符、**不得含動態值**（不准出現 `nova.task.任務編號_42.finished` 這種）。
- `event_version` — `M.m.p`。CDEvents 把版本嵌在 type 字串裡，nova 拆成獨立欄位比較好查，但 `(event_name, event_version)` 必須共同決定 payload schema（OTel：「uniquely identifies the event structure」）。
- `source` — URI-reference，例 `nova://gate/local`、`github://sbu/nova`、`prometheus://…`。
- `subject_type` / `subject_id` — 例 `("task", "計畫03-task8")`、`("pipeline_run", "1234")`。
- `occurred_at` — RFC 3339，**來源系統的事實發生時間**。重送不得更新（CDEvents 條文）。
- `recorded_at` — 進 store 的時間。**與 `occurred_at` 分兩欄，永不混用。**
- `dedup_key` — 對應 fourkeys 的 `signature`。`UNIQUE (source, dedup_key)`，webhook／輪詢重送直接被 DB 擋掉。
- `payload` — JSON，schema 由 `(event_name, event_version)` 決定，**寫入端拒絕 unknown fields**（符合 CLAUDE.md「每個 object 預設拒絕 unknown fields」）。
- `ingest_provenance` — 只有外部來源的事件有：`upstream_url`、`upstream_fetched_at`、`upstream_etag`、`upstream_raw_sha256`。

## 二、外部資料只有一個入口：擷取器（ingestor），且它不是 projector

分層落點（依 `架構/目錄規則.toml` 的十三層，方向只能向下）：

- `nova.基礎設施.度量.擷取器` — **唯一**允許 import `httpx`／`subprocess`／碰 GitHub API／Prometheus API／deployment DB 的模組。它做兩件事：把 upstream 回應原文寫成 `nova.external.snapshot.captured` 事件（`payload.raw` 存原文、`ingest_provenance.upstream_raw_sha256` 存雜湊），再由**純解析函式**把 snapshot 事件轉成領域事件（`nova.deploy.finished`、`nova.change.committed`、`nova.incident.identified`、`nova.incident.resolved`）。這正是 Fowler 的 Gateway「記住每次外部查詢的回應」，只是把「記住」實作成事件本身。
- `nova.領域.度量.投影器` — 只吃 `度量事件`，一個 `fold(狀態, 事件) -> 狀態`。

## 三、投影純度要有會 fail 的測試背書（CLAUDE.md 最高原則第 1 條）

三個機制 + 一格防恆真，全部要先跑到紅：

1. **AST 全集掃描**（放 `架構/檢查投影純度.py`，比照 `架構/檢查工程規範.py` 的形狀）。照 CLAUDE.md「全集宣稱一律直接列舉目標型別」：走 `ast.Import` / `ast.ImportFrom` 列 import 全集，走 `ast.Attribute` 列屬性呼叫全集，**不從別的型別推導**。禁用清單至少含 `httpx`、`requests`、`urllib`、`subprocess`、`socket`、`sqlite3`、`open`、`os.environ`、`datetime.now`／`datetime.utcnow`、`time.time`、`random`、`uuid.uuid4`。負控三格：靜態違規 import 一格、`importlib.import_module` 動態違規一格、非 literal target 一格。
2. **重播決定性**：同一段事件序列 fold 兩次，第二次前把所有外部 stub 的答案全部改掉（GitHub 回不同 SHA、Prometheus 回不同 alert）。兩次輸出 bytes 必須相同。負控：故意寫一個偷查 stub 的 projector，這格必須紅。
3. **時鐘不變性**：把整批事件的 `recorded_at` 全體 +1 天、`event_id` 重新配發，`occurred_at` 不動 —— 投影結果必須逐 byte 相同。這一格同時抓到「projector 用了牆鐘」與「projector 用了 `recorded_at`」兩種壞。
4. **防恆真格**：一個合法的 projector（只讀 `occurred_at` 與 `payload`）不被上面任何一格誤殺。

## 四、度量規格化：DORA 的技術定義寫進 spec，不散在查詢裡

新增 `規格/工程/度量/*.metric.json`（ClaimSpec 之下的一種），每份至少：

- `metric_id` — `dora.deployment_frequency`、`dora.change_lead_time`、`dora.change_fail_rate`、`dora.failed_deployment_recovery_time`。**用 DORA 現行官方名**，不要再寫 MTTR；若要保留舊名，在 spec 裡註明「舊名 MTTR，2024 官方改稱 failed deployment recovery time」。
- `required_event_names` — 宣告這個 fold 的**輸入全集**（例 `dora.change_lead_time` = `["nova.change.committed", "nova.deploy.finished"]`）。閘要檢查：projector 實際觸碰的 `event_name` 集合必須是這份宣告的子集，多碰一種就紅。這一格把「不得查外部」升級成「連事件都不准超出宣告範圍」，對應 Neos 那條「不准讀其他 projection」。
- `deployment 的技術定義` — ICSSP '24 的教訓：官方定義留白，這裡必須自己釘死。建議照論文：「push 到 default branch 自動觸發、run 成功、且終點是 production 的 pipeline run」，手動觸發／非 default branch／失敗一律不算。這行字必須在 spec 裡，不能只活在 SQL 或 Python 註解裡。
- `window` — 觀察窗與移動平均（論文用 7 天 sliding window）。
- 每個 metric 至少一個事前命名的 mutation + 指定 predicate（CLAUDE.md：raw kill rate 不進驗收判準）。

- 【ICSSP '24】DORA 官方定義留白到「什麼算一次 deployment」都要自己訂。論文最後訂成「push 到 default branch 自動觸發、成功、部署到 production 的 pipeline run」，手動執行與失敗 run 全部排除 —— 同一批原始資料換一個技術定義就是完全不同的數字。這個定義若不進 spec，兩個人算出來的 DF 不會一樣，而且沒人看得出誰錯。
- 【ICSSP '24】他們算 lead time 的第一個 commit 是靠 merge-commit 的兩個 parent 往回推。論文自己承認「The use of commit meta-data prohibits the use of certain Git practices」——squash / rebase / force push 會讓這個推導失效。這正是「當下查 API 而不是當時記事件」的代價：歷史被改寫，昨天算對的數字今天就變了。nova 若記了 nova.change.committed 事件就免疫，若靠 projector 現查 git 就會中。
- 【Fowler】重播會把副作用重打一次。他明講外部系統「don't know the difference between real processing and replays」。nova 若把「開 PR」「發通知」寫進 event handler 而沒有 replay-mode 判斷，重建投影就會重發一輪。
- 【Fowler】外部查詢的坑比外部更新更隱蔽：不是會爆炸，而是**答案悄悄變了**。他的匯率例子——12/5 處理的事件，重播時需要的是 12/5 的匯率。對應到 nova：projector 現查 GitHub 拿到的是「今天的 PR 狀態」而不是「當時的 PR 狀態」，測試會綠、數字會錯、而且沒有任何東西會報錯。
- 【Microsoft】不可變事件遇上 schema 演進是實打實的痛點。官方列出的四種策略裡三種（tolerant deserialization、event versioning、upcasting）都保留不可變性，第四種 in-place migration「breaks immutability and should be a last resort」。**注意這跟 nova「每個 object 預設拒絕 unknown fields」正面衝突**：Microsoft 建議消費端忽略未知欄位。解法是分開兩件事——寫入端（新事件）嚴格拒絕 unknown fields，讀取端（歷史事件）走 upcaster 鏈把舊版轉成當前版。若一律嚴格，某天加一個欄位就會讓所有歷史投影重播失敗。
- 【Microsoft】at-least-once 投遞下若 handler 不 idempotent，官方明講後果是「projections drift from the event stream and side effects such as payments or notifications trigger more than once」。drift 是靜默的 —— 帳會慢慢歪而不會報錯。
- 【Microsoft】append-only 與被遺忘權／個資刪除直接衝突，官方說要「design for this tension from the start」。nova 的事件裡有 user.email（Claude Code OTel 標準屬性就含 user.email）—— 個資放進不可變事件表就再也刪不掉。建議照官方：個資存事件外、事件只放識別碼。
- 【OTel gen_ai】2026-06 的 semantic-conventions v1.42.0 把整個 gen_ai.* 從主 repo 廢棄並搬到 semantic-conventions-genai，新 repo 到 7 月都還沒有 tagged release、沒有可 pin 的 schema URL。已經有人把 gen_ai.* 當穩定欄位名寫進 DB schema，然後遇到整批改名（官方的緩衝機制是 OTEL_SEMCONV_STABILITY_OPT_IN 雙發期，代表改名是預期會發生的事）。把外部尚未 stable 的 vocabulary 當自家真相就是這樣賠。
- 【OTel CI/CD】官方特地寫「Using the CI/CD pipeline run resource for metrics must be opt-in」，理由是 pipeline run id 掛在 metric 上必然 high cardinality，會把 metric 後端的成本打上去。這是有人先付過帳才會被寫進規格的那種警告。
- 【CDEvents】CDF 官方 primer 自己承認目前事件只夠算四個 DORA 指標中的兩個（lead time、deployment frequency）。incident 那半邊（change fail rate、recovery time）沒有標準事件來源 —— CDF blog 列的 incident.identified / incident.resolved 在 primer 裡並未被算進「夠用」的範圍。ICSSP 論文也說「defining and identifying incidents is hard」，最後只好靠自訂的 PromQL alert。別以為接了 CDEvents 四個指標就自動有了。
- 【ICSSP '24】團隊層級的聚合數字跟個別系統的相關性從 0.88 到 0.0 到負相關都有，標準差是均值的 0.98–3.96 倍；27% 的系統貢獻了 62.8% 的部署、單一專案佔了 71.9% 的故障。只 fold 出一個團隊層級數字會把問題整個遮掉 —— fold 的 group key 要能切到最小的可歸因單位。
- 【ICSSP '24】系統資料只看得到自己邊界內的事件；論文引 Forsgren 指出人能察覺邊界外的現象，主張自動與人工混合。純事件 fold 的盲區是「沒有任何系統發出事件的那類故障」——不要把「事件裡沒有」當成「沒發生」。

### prompt 作為版本化、內容定址的 immutable artifact：業界官方立場、identity 綁定方式，以及 nova 的 prompt_family_ref 落地

**nova_fit**：核心問題的業界答案很一致：**identity 綁 digest，名字＋版本號只是人類可讀的指標**（in-toto 逐字「matched purely by digest」；OCI tag 是 pointer、digest 是 content identifier）。兩者同時要的官方組合法有三種現成樣板，nova 該抄 Go sumdb 那種：引用面寫 name@version，但 name@version → digest 的映射釘在一個誰都改不動的地方。以下是落到 nova 的具體結構。

**一、把 `prompt_family_ref` 從 str 換成三元組（抄 nova 自己已有的 ClaimRef）**

`計畫 01 Task 5` 已經有 `core.identity-and-digest.canonical`、`Sha256Ref`、以及 `ClaimRef(claim_id, revision, digest)`（`docs/計畫/01-可執行保證語言.md:416`）。prompt 這邊不必發明新東西，照抄同一個形狀：

```python
@dataclass(frozen=True, slots=True)
class PromptFamilyRef:
    family_id: SemanticId      # ASCII，人類可讀的名字（對應 OCI 的 tag、in-toto 的 name）
    revision: int              # 單調版本號，供人溝通與排序
    digest: Sha256Ref          # 唯一的身分判準（對應 in-toto 的 subject.digest）
```

`PursuitIdentity.prompt_family_ref` 欄位型別改成 `PromptFamilyRef`，schema 層 `additionalProperties: false` 且三欄皆 required。`family_id` 與 `revision` **不參與身分比對**，只進 evidence 與人看的報告。

**二、prompt 本文進 04 的 CAS，digest 必須是同一顆**

`計畫 04` 已定 `ContentRef(algorithm, digest, size, media_type)`，「put 同 bytes 冪等、get 必驗 digest」（`docs/計畫/04-內容證據與分層儲存.md:23`）。prompt family 的 canonical bytes 用 `media_type = "application/vnd.nova.prompt-family+json"` 寫進 CAS，並強制不變式：

```
PromptFamilyRef.digest == ContentRef.digest   （schema 之外要有一條會紅的測試）
```

這樣 `prompt_family_ref` 才第一次有指涉物可解——這是 `交接.md:805`「待辦一」的直接解法。同時要進 04 的 audit pin ledger 釘住那顆 blob，否則 retention prune 之後 ref 又變 dangling（Go sumdb 的教訓：ref 要能事後解得開，稽核才有意義）。

**三、digest 蓋什麼：蓋 PromptPlan IR 的 canonical bytes，且順序必須進 digest**

Nix 的 input-addressed vs content-addressed 是這裡的分水嶺。nova 該選 **input-addressed 的變體**：不蓋 runtime 代入變數後的最終文字（那會被每次的動態輸入汙染，等於每次都是新 identity），而蓋「產生 prompt 的固定配方」——這正好對應 Anthropic Console 那套「只追蹤 prompt 的固定核心、與 dynamic inputs 分離」的切法。

`交接.md:817` 已經點名缺口：「工具清單→system prompt→固定文件那串前綴的內容與**順序**沒有任何一份計畫定義過」。所以 canonical 序列化的輸入至少是：

```python
@dataclass(frozen=True, slots=True)
class PromptFamily:
    family_id: SemanticId
    revision: int
    tool_manifest: tuple[SemanticId, ...]        # tuple 不是 set：順序是 digest 輸入
    system_segments: tuple[ContentRef, ...]      # 逐段 CAS ref，順序是 digest 輸入
    fixed_document_prefix: tuple[ContentRef, ...] # 同上
    serialization_policy_id: SemanticId
    canonical_bytes: bytes
    digest: Sha256Ref
```

`system_segments` 與 `fixed_document_prefix` 用逐段 `ContentRef` 而非一坨大字串，這是抄 OMS 的 (file path, digest) 配對：每段各自有 digest，family 的 digest 蓋住整份清單。好處是「改了哪一段」在 diff 層可定位，而 family digest 仍是單一身分。

`計畫 01 Task 5` 的固定負控已經要求「同一 object 改 key insertion order 必須同 digest」——注意這條講的是 **mapping 的 key 順序**要正規化掉；prompt family 這邊要的是相反方向：**sequence 的元素順序必須影響 digest**。兩者不衝突但容易寫混，要各自有測試。

**四、`classify_identity_change("prompt_family")` 改成比 digest**

現在這條固定負控恆真（`docs/計畫/08-目標追求生命週期.md:340`、`:354`），因為它比的是兩個字串。改成：

- `digest` 相同、`family_id` 或 `revision` 不同 → `ALIAS_RENAME`，**不開新 Pursuit**（in-toto：purely by digest）
- `digest` 不同 → 一律 identity-breaking，**不管 `family_id` 是否相同**（堵住「同一個 ref 底下內容漂移判同一個 Pursuit」）

**五、解引用必驗，失敗是 typed，不靜默降級**

抄 OCI 的「SHOULD verify before consuming」與 SRI 的硬失敗語意：

```python
def resolve(ref: PromptFamilyRef) -> PromptFamily | PromptFamilyResolutionError
# typed failure：PROMPT_FAMILY_NOT_FOUND / PROMPT_FAMILY_DIGEST_MISMATCH
```

digest 不符時直接 terminal，不得回退到「按名字找一份最像的」。這對齊 CLAUDE.md「能力不足只回 typed `UNSUPPORTED_*`，不得靜默降級」。

**六、schema 層拒收 alias／latest 進 immutable 欄位**

MLflow、Weave、Langfuse 三家都建議「生產用 alias」，但那個建議救不了 nova——nova 要的是 Pursuit identity 的可重現性，不是部署便利。所以：可以有一張可變的 `PromptFamilyLabel(label, family_id) -> revision` 表供人操作與 rollout，但 `PursuitIdentity.prompt_family_ref` 這個 immutable 欄位**只准收已解析完成的三元組**，schema 拒收任何含 `@latest`、label 形式或缺 `digest` 的輸入。這是把三家只能靠自律的一條寫成會紅的測試。

**七、IndependenceManifest 比 digest 不比名字**

`docs/決策/sol-新局-第二輪.md:181` 把 `prompt_family` 列為獨立性維度之一，`:189` 說共用同一 prompt family 的兩個 Pursuit 不得算成 2 個 effective independent pursuits。這個比對也要改成比 `digest`——否則換個名字包同一份 bytes 就能虛報獨立性。

**八、落點與四格測試（三紅一防恆真）**

新增 `規格/提示/`：`PromptFamily.schema.json`、`PromptFamilyRef.schema.json`、`規格/提示/保證/提示族內容定址.claim.json`。實作落 `nova/核心/`（value object 與 digest，無 I/O）＋ `nova/權威/提示/`（admission）。

1. 兩個不同 `family_id`、同一份 bytes（同 digest）→ 必須判「不開新 Pursuit」
2. 同一個 `family_id` 與 `revision`、bytes 改一個位元組 → 必須判 identity-breaking
3. 只調換 `tool_manifest` 的元素順序、集合不變 → digest 必須改變（防 canonical 序列化把 sequence 順序丟掉）
4. 防恆真格：同 ref、同 bytes、正常解引用 → 不判 breaking、不報錯

第 1、2 格就是 `交接.md` 那條「兩種錯都不會有測試轉紅」的直接解。

這是**新增判準**，不在任何 active plan 的 `Create:` 裡，且 08 一旦綠了再補就得動已准入的 ClaimSpec 與固定負控——那是實作者無權的動作，只能走 RequirementChange。與 `交接.md` 對「待辦二」的判斷同型：現在補是加欄位，之後補是改題目。

**坑**：
- **最大的坑：把 prompt identity 綁在外部服務的 id/version 上，服務會整個消失。** OpenAI 的 prompt object（pmpt_xxx ＋ version）正在被廢：2026-06-03 起 de-emphasize，2026-11-30 關閉 v1/prompts。官方遷移建議逐字是把版本管理搬回 repo「using git commits, PR review, and tests or evals」。所有 pmpt_ id 加版本號的引用都會變成死指標。（來源：OpenAI 官方遷移文件）
- **可變指標的內容漂移在 OCI 是架構上被允許的，不是意外。** distribution-spec 的 push endpoint 收 <tag-or-digest>，規範沒有禁止把既有 tag 重推到不同 manifest。Go 的 sumdb 設計文件更明講連模組作者本人都可能「move their tags around or otherwise change the bits associated with a specific version from one day to the next」。所以業界的防線不是「禁止漂移」，是「生產環境不准用名字指涉，只准用 digest」＋「把映射釘進 append-only log 讓漂移可偵測」。
- **alias／label 的 client-side 快取讓同一次執行內不同程序拿到不同版本。** Langfuse SDK 預設快取 TTL 60 秒，且 refetch 失敗會自動回退到快取版本（官方 FAQ「I'm not seeing the latest version of my prompt」就是在解釋這件事）；MLflow 同樣是 alias-based prompt 60 秒 TTL，而 immutable version 才可無限期快取。對 nova 的意義：只要 identity 欄位允許存 alias，一個長跑的 Pursuit 內部就可能跨過一次 label 切換而毫無紀錄。
- **「名字＋digest 同時寫」的 ref 格式在 OCI 生態長年不互通。** `name:tag@digest` 在 distribution/reference 文法上寫得出來（例：nginx:1.25.4@sha256:...），但 buildah、containers/image、podman 等工具長期不支援兩者並存（containers/image#783、#1736、buildah#1407 都是同一個抱怨）。教訓：自訂「同時帶名字與 digest」的複合字串格式時，解析器不一致會變成沉默的落地問題——所以應該用**結構化三欄位**而不是一個要靠正規表示式拆的字串。
- **MCP 官方規範把這個坑原樣寫進標準。** Prompt 的資料型別只有 name／title／description／arguments，沒有 version、沒有 digest；而 notifications/prompts/list_changed 明示 server 的 prompt 集合會變。結果是 client 端在協定層沒有任何手段能證明兩次 prompts/get 拿到同一份 bytes。nova 若要接 MCP prompt 作為來源，必須自己在邊界上算 digest 存檔，不能指望對方給。
- **Anthropic Agent Skills 規範也是 name-only。** version 不是一級欄位，官方範例把它塞在 metadata 這個「arbitrary key-value mapping (string→string)」裡，spec-compliant runtime 會忽略不認得的 key；全份規範沒有任何 integrity／digest／signature 欄位；而 name 「Must match the parent directory name」——skill 的身分完全是路徑名。同一個 skill 目錄換了內容不換名字，規範層沒有機制會發現。
- **digest 蓋錯層會得到兩種相反的病，Nix 官方手冊把這兩邊講得最清楚。** input-addressed 的 hash 蓋 derivation 內容（build 圖），所以改個無關的 URL 就會讓整條下游 hash 全變——對環境雜訊過敏；content-addressed 只蓋輸出 bytes，「the rest of the derivation is ignored」——但這樣就對「配方變了而輸出碰巧一樣」無感。prompt 這邊的對應病症是：蓋最終渲染文字 → 每次動態輸入都變成新 identity；只蓋 system prompt 文字 → 工具清單順序或固定文件前綴漂了完全不紅。
- **prompt 的漂移是累積型的，單次 diff 看不出來，這正是測試抓不到的原因。** arXiv 2601.22025《When "Better" Prompts Hurt》描述的症狀是：每次 prompt 微調看似無害，但累積漂移會顯著改變系統行為，表現為「使用者回報 regression 而測試沒抓到」與生產指標的漸進劣化，作者的建議是所有 prompt 進版控並記錄每次修改的理由。（**注意分級：這是 arXiv preprint，我只讀到搜尋摘要，未逐字查證，也未確認同儕審查。**）

### agent harness 十一部件中業界最常指出的缺口，以及 loop engineering 的官方終止條件清單

**nova_fit**：## 一、直接結論（先講，因為它決定後面所有欄位）

**十一部件裡被指為最常見缺口的是「驗證迴圈」，緊接著是「協調迴圈」裡的終止條件。**

證據鏈三條，彼此獨立：
1. MAST 量化：Task Verification 佔全部失敗 25.5%，且 FC1 裡最大的單一設計缺陷之一是 FM-1.5「Unaware of termination conditions」。作者結論是改善來自 refining system design 而非換模型——缺口在 harness。
2. Anthropic 自己把 loop 定義成「gather context → take action → verify work」，驗證佔三分之一；而 AI-Native SDLC playbook 直說瓶頸「moves to the steps to the left and right of the build phase」，右側就是驗證與批准。
3. 反證式證據最有力：**終止條件本身在官方文件裡就是個洞**。Anthropic 只給 max_turns + max_budget_usd；OpenAI 只給 tool call／structured output／error／max turns；Microsoft AutoGen 最完整（訊息數、token 用量、逾時、handoff、外部中止，可 And/Or 組合）但同樣沒有無進展偵測。題目問的五項終止條件裡，**硬迭代上限、成本預算、目標檢查有官方背書；逾時只有 AutoGen 有；無進展偵測三家官方全部缺席**。

跨部件四項的低估排序（依證據強度）：終止條件 > 驗證迴圈 > 成本歸屬 > 人在迴圈的交接。成本歸屬與可觀測性其實**已經有現成規格可抄**（OTel GenAI semconv ＋ Claude Code 的 metric 維度），被低估的不是「不知道要做」而是「以為隨手加個 total 就叫歸屬」。

## 二、落到 nova 的資料結構

### 1. 終止條件建模成 typed object，不是散落的純量參數
新增 `終止條件`（TerminationSpec），預設拒絕 unknown fields：
- `max_iterations: int`（對齊 max_turns，只數有工具呼叫的 turn）
- `max_budget_usd: Decimal`（對齊 max_budget_usd；**含子代理**）
- `wall_clock_deadline_utc: datetime`（AutoGen TimeoutTermination 的對應；Anthropic 官方沒有，這是 nova 自己補）
- `goal_check: ClaimRef`（指向 ClaimSpec 閘，即 `/goal` 的 evaluator 位置）
- `no_progress: 無進展規則 | None`（None 時必須顯式寫 None，不得省略欄位）

`無進展規則` 的欄位：`fingerprint_fields: list[str]`（預設 `["tool_name","args_canonical_json","error_code"]`）、`window: int`（預設 5）、`repeat_threshold: int`（預設 3）。

### 2. 終止結果做成 failure code enum，對齊官方命名但不假裝有官方沒有的能力
`SUCCESS`、`ERROR_MAX_ITERATIONS`、`ERROR_MAX_BUDGET_USD`、`ERROR_DEADLINE_EXCEEDED`、`ERROR_NO_PROGRESS`、`ERROR_PREMATURE_TERMINATION`、`ERROR_DURING_EXECUTION`。

依 CLAUDE.md 的「不得靜默降級」：後端若不支援無進展偵測，回 typed `UNSUPPORTED_NO_PROGRESS_DETECTION`，**不得**把 `no_progress` 靜默忽略後照跑。

`ERROR_PREMATURE_TERMINATION` 是 nova 相對官方多出來的一格，對應 MAST FM-3.1：執行者宣告完成但 `goal_check` 未綠時，把 `SUCCESS` 改寫成這格。這就是 CLAUDE.md 那句「它自認完成不算完成」的機器化。

### 3. 無進展偵測的具體演算法（並且要有負控說明它抓不到什麼）
```
指紋(step) = sha256(tool_name || canonical_json(args) || (error_code or ""))
若 指紋 在最近 window=5 步內出現 repeat_threshold=3 次 → ERROR_NO_PROGRESS
```
負控測試必須包含一格：造一個「每步指紋都不同、但實質上零進展」的 case（例如每次改一個無意義參數），證明這個演算法**抓不到**它。抓不到就把上限寫進 docstring，不要在文件裡宣稱「有無進展偵測」就當問題解決了——這正是 CLAUDE.md 警告的「宣稱有自動把關卻沒有，比沒有規範更糟」。

### 4. 成本歸屬進 effect receipt
receipt 加 `cost` 區塊，欄位名直接抄官方維度以便日後對帳：
`query_source`（enum：`main` / `subagent` / `auxiliary`）、`agent_name`、`skill_name`、`model`、`input_tokens`、`output_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens`、`cost_usd_estimate`。

三條硬規則，全部有官方依據：
- `cost_usd_estimate` 欄位名必須帶 `_estimate`。官方逐字說 total_cost_usd 是 client-side estimate、「Do not bill end users or trigger financial decisions from these fields」。nova 若拿它當**硬預算閘**就是踩坑——閘要卡在 token 計數上，USD 只作顯示。
- 子代理成本必須向上滾算。官方 `usage` 不含子代理、`model_usage` 才含；nova 的 receipt 若只累加主迴圈就會系統性低估。
- 預算歸零事件要顯式記錄。官方 `/clear` 會把 running total 與 budget 比較基準一起重置——nova 若有等價的「重開脈絡」動作，必須發 `budget_reset` 事件並保留重置前的小計，否則預算閘會被無聲繞過。

### 5. 可觀測性欄位直接對映 OTLP
每個 step 事件帶：`run_id`、`prompt_id`（UUID v4，串起單次請求的所有事件，抄 Claude Code 的 prompt.id）、`parent_tool_use_id`（辨識子代理）、`step_index`、`fingerprint`、`termination_reason`。
匯出時映射：`gen_ai.operation.name` = `invoke_agent` / `execute_tool`、`gen_ai.agent.id`、`gen_ai.agent.name`、`gen_ai.conversation.id`、`gen_ai.usage.input_tokens` / `output_tokens`、`gen_ai.tool.name`、`gen_ai.tool.call.id`、`error.type`（Conditionally Required：失敗必填）、`gen_ai.response.finish_reasons`。
基數守則抄官方警語：自訂 resource attribute 不得放無界值（run_id 只能進 span 不能進 metric label）。

### 6. 人在迴圈的交接做成 object，且交接內容必須是原始動作
`交接請求`：`trigger`（enum：`FAILURE_THRESHOLD` / `HIGH_RISK_ACTION` / `NO_PROGRESS` / `BUDGET_EXHAUSTED` / `DEADLINE_EXCEEDED`）、`raw_action`（**原始動作全文，不是執行者寫的摘要**——OWASP ASI09 Human-Agent Trust Exploitation 的直接對策）、`risk_rating`（`low`/`medium`/`high`，判準抄 OpenAI：read-only vs write、可逆性、所需權限、財務影響）、`resume_token`。
前兩個 trigger 是 OpenAI 官方明列的兩個；後三個是 nova 把終止條件與交接接起來——AutoGen 的 HandoffTermination 正好證明「交接是一種終止條件」這個建模是業界做法，不是自創。
權限面沿用既有原則：候選執行者不得自行產生 `ACCEPTED`，不得改 `risk_rating`，不得延長 `wall_clock_deadline_utc`。

### 7. 驗證迴圈：把 ClaimSpec 閘接成 loop 的 goal_check
nova 已經有 `工具/驗全部.py` 與 ClaimSpec 閘，缺的是把它接到迴圈的**停止點**上。對應官方機制是 Stop hook（「When the agent finishes → Validate the result」）。做法：`goal_check` 在執行者宣告完成時強制執行，未綠則回 `ERROR_PREMATURE_TERMINATION` 並把控制權送回迴圈或交接給人。驗證回饋的優先序照官方排：規則式（lint／型別／測試）第一，視覺回饋第二，LLM 評審最後——nova 的既有判準本來就是規則式，這一點是順風。

### 8. claim 落點建議
`規格/工程/保證/迴圈必須有可證的終止條件.claim.json`，固定負控至少五格：①超過 max_iterations 必停且回正確 code ②超過 token 預算必停 ③deadline 到必停 ④同指紋重複達閾值必停 ⑤**防恆真格**：正常會收斂的迴圈不被任何一條誤殺。再加一格 `must_fail_exactly`：goal_check 未綠時 `SUCCESS` 必被改寫成 `ERROR_PREMATURE_TERMINATION`。

**坑**：
- **recursion limit 是事後屍檢不是防護**：LangGraph 預設 recursion_limit=25，實際發作情況是 agent 用同一組 (tool, args) 反覆呼叫直到觸頂——錢已經燒完 25 步才報 GraphRecursionError。業界對此的評語是它「is not loop protection—it is a backstop that fires after the loop has already wasted twenty-five steps」。有真實 issue 紀錄（langchain-ai/langgraph #6731、bytedance/deer-flow #1055）。教訓：硬迭代上限與無進展偵測是兩件事，前者不能替代後者。
- **設了 max_turns 但沒被傳下去**：anthropics/claude-code-action issue #1177 的標題就是「max_turns is never passed to SDK in run.ts, defaults to 10」。參數存在、文件寫了、使用者填了，但接線斷掉——這正是「只靠讀 code 才成立的防護等於沒有防護」的實例。任何終止參數都必須有一格會 fail 的測試證明它真的生效，不是驗參數存在，是驗超限時真的停。
- **用 usage 算成本會系統性低估**：Anthropic 官方明列 usage 不含子代理、total_cost_usd 與 model_usage 才含。一旦架構走上子代理協調，最直覺的那個欄位就開始說謊。
- **per-step output_tokens 是 placeholder**：官方逐字說每則 assistant message 的 output_tokens 只是 message_start 當下的計數，同一次 API 回應產生的多則訊息全帶同一個假值。逐步累加輸出 token 會得到錯誤數字，真值只在 result。
- **平行工具呼叫共用同一個 message id**：官方要求依 id 去重，否則同一次 turn 被重複計數、成本虛胖。
- **session crash 後成本欄位可能全零**：官方說 error_during_execution 的 usage、total_cost_usd、model_usage 都可能是 0，得回頭從崩潰前的 result 或 assistant message 重算。把「最後一筆 result」當帳本唯一真相會憑空丟掉整段花費。
- **預算超限那一刻的帳本自相矛盾**：error_max_budget_usd 時 usage 少算了跨越預算的那次回應，但 total_cost_usd 與 model_usage 有算。同一個 result 裡兩個欄位對不起來。
- **/clear 會把預算歸零**：官方說 maxBudgetUsd 比對的是同一個 running total，而 /clear、/reset、/new 會讓它重來。等於「重開脈絡」就把預算閘無聲重置——這是可被利用的繞過路徑，不是理論風險。
- **拿 client-side 估算當財務閘**：官方 Warning 直接禁止（「Do not bill end users or trigger financial decisions from these fields」），理由是價目表在 build time 打包、模型不認得時會漂。實務上很容易把它當硬預算，然後在改價或升版當天整批失準。
- **compaction 會吃掉初始指令**：官方逐字警告摘要會取代舊訊息，「specific instructions from early in the conversation may not be preserved」。把規矩寫在第一則 prompt 裡的做法，在長迴圈裡必然失效——這對應 MAST 的 FM-1.4 Loss of conversation history。nova 把規矩放 CLAUDE.md（每次請求重新注入）是對的路。
- **回饋路徑沒有上界是普遍現象不是個案**：IAL-Scan 掃 6,549 個 agent repo，人工確認 68 個真實的無限迴圈失敗散在 47 個專案，後果被描述為 cost exhaustion、model denial of service、context growth、以及**重複的對外副作用**。最後這項最痛：不是只有燒錢，是同一個外部動作被做很多次。
- **高基數遙測標籤反噬**：Claude Code 官方對 OTEL_RESOURCE_ATTRIBUTES 有明文基數警語——自訂 key 會變成每條 metric series 的 label。可觀測性做過頭會把儲存成本變成新的成本問題。
- **給人看摘要而不是原始動作**：OWASP 對高風險確認的要求是「showing the raw action」，理由是摘要本身可被操縱（ASI09 Human-Agent Trust Exploitation）。交接介面若只呈現執行者的自述，人在迴圈就成了橡皮圖章——這與 CLAUDE.md「不要對執行者的自報照單全收」是同一條。
- **GitHub 官方頁面查不到不等於規範不存在**：genai.owasp.org 的 Top 10 頁面本輪實測回 HTTP 403，platform.claude.com 的 agent-sdk 路徑 307 轉址到 code.claude.com。若把「fetch 失敗」當成「沒有這份規範」會做出錯誤結論；反過來把二手部落格的轉述當一手引用也是錯的。本輪 OWASP 條目已標明是二手交叉確認。

### LLM-as-judge 分數的合法用途與禁區：Anthropic／OpenAI／Google 官方立場、偏誤量測論文、以及 IV&V 獨立性標準對「誰有資格裁定」的定義

**nova_fit**：先講最要緊的一句：**nova 現在不是「躲掉了」，而是「還沒被寫進去而已」——schema 今天就擋不住。**

我讀了 `/Users/sbu/nova/規格/語言/ClaimSpec.schema.json`。`additionalProperties: false` 只擋 unknown **fields**，擋不住 unknown **values**：
- `judge.all_of[].operator` 是 `{"type": "string"}`，**沒有 enum**。今天寫 `"operator": "LLM_SCORE_GTE"` 完全合法。
- `stimulus[].primitive` 是 `{"type": "string"}`，沒有 enum。寫 `"primitive": "llm.judge"` 完全合法。
- `observations[].source` / `.type` 同樣是自由字串。
- `primitive_catalog` 只有 `catalog_id` + `digest`，**沒有任何欄位描述某個 primitive 是確定性還是隨機的**。

對照 `規格/判準/保證/框架不得改寫裁定.claim.json` 的寫法（judge 是一棵 `all_of` 的 `EQUALS`／`NOT_EQUALS` 述詞樹、對著 `observation` 與 `const` 比），確定性是**目前實際 claim 的寫作習慣**，不是 schema 強制的。CLAUDE.md 說「只以文件或 skill 形式存在的規範等於不存在」——這條同樣適用於「只存在於既有 claim 寫法裡的慣例」。

## 落到資料結構

### 1. 把確定性從慣例升成型別（PrimitiveCatalog + operator enum）
- `ClaimSpec.schema.json` 的 `judge.all_of[].operator` 收成 enum：`["EQUALS","NOT_EQUALS","LESS_THAN","GREATER_THAN","CONTAINS","MATCHES"]`（依 01 計畫 Task 7 `type_check(spec.parameters, spec.observations, spec.judge)` 實際支援的集合為準）。
- PrimitiveCatalog 每個 primitive 加 `primitive_kind`，enum：`DETERMINISTIC` / `STOCHASTIC_JUDGE` / `EXTERNAL_EFFECT`。
- `compile_claim(spec, catalog, binding, offer)` 在 01 計畫 Task 7 已經是 `-> TestPlan | CompileFailure`。加一條規則：**judge 述詞樹或 stimulus 只要觸及任何 `STOCHASTIC_JUDGE` primitive，而 ClaimSpec 沒有帶 `judge_calibration`，就回 typed CompileFailure `UNSUPPORTED_STOCHASTIC_JUDGE`。** 這正好是 CLAUDE.md「能力不足只回 typed `UNSUPPORTED_*`，不得靜默降級」的同一條路。

### 2. 新增 top-level `judge_calibration`（缺一不可，`additionalProperties: false`）
若 nova 哪天真的要開 LLM-judge 車道，這個 object 是入場費，欄位對應到上面每一條官方要求與每一篇偏誤論文：

- `anchor_set_ref`（string，CAS digest）+ `anchor_n`（integer）——對應 Anthropic「closely calibrated with human experts」、Google 的 `human_rating`／`human_pairwise_choice` ground truth、Li 2026 的 human-labeled anchor set。anchor set 的標註**必須是人寫的**，不是另一顆模型產的（Krumdick 2025：self-generated reference 讓 kappa 從 0.78 掉到 0.14）。
- `agreement_metric`（enum：`COHENS_KAPPA` / `KRIPPENDORFF_ALPHA`）+ `agreement_floor`（number）+ `measured_agreement`（number）——編譯期硬檢 `measured_agreement >= agreement_floor`，不符就 `CLAIM_REJECTED`。
- `judge_fingerprint`（object：`model_id`、`model_version`、`prompt_digest`、`decoding_params_digest`）——`measured_agreement` 是**綁在這個 fingerprint 上量的**。跑判準時 fingerprint 不符 → 新 typed verdict `JUDGE_DRIFTED`。這一條直接封 Li 2026 的「分不出是產品退步還是尺變了」。
- `position_swap`（boolean，schema 層 `const: true`）+ `swap_disagreement_ceiling`（number）——Google 的 `flip_enabled` 預設就是 true，nova 沒有理由比 Google 鬆。兩個順序都跑，翻盤率超過 ceiling → `JUDGE_SWAP_INCONSISTENT`。
- `sampling_count`（integer，1–32，抄 Google 的區間）+ `unanimity_required`（boolean）。
- `verbosity_control`（enum：`LENGTH_CONTROLLED_REGRESSION` / `LENGTH_MATCHED_PAIRS` / `NONE`）——`NONE` 在 gating 車道直接編譯失敗（Dubois 2024：長度控制把相關性從 0.94 拉到 0.98，代表沒控制時分數有一塊在測長度）。
- `judge_backend_fingerprint_excludes`（array of string）——**judge 的 backend fingerprint 不得等於候選任何一個 backend fingerprint**。Panickssery 2024 給了因果證據，Anthropic 文件每個範例都寫這句。08 計畫已經有 backend fingerprint 的概念，直接接上去。

### 3. Verdict 集合：judge 出問題是「沒驗到」，不是「候選失敗」
`規格/判準/保證/框架不得改寫裁定.claim.json` 已經把 verdict 釘成 `["PASS","FAIL","ERROR"]` 且 `xfail_is_absent: true`。新增的 `JUDGE_UNCALIBRATED`、`JUDGE_DRIFTED`、`JUDGE_SWAP_INCONSISTENT`、`JUDGE_BELOW_AGREEMENT_FLOOR` **全部映到 `ERROR`（HARNESS_ERROR 那條路），一律不得映到 `FAIL`**。理由和那份 claim 的 statement 一模一樣：把「根本沒驗到」顯示成「候選錯了」，就是把沒驗到說成驗過了。

### 4. 負控要怎麼寫才不是恆真
LLM judge 是隨機的，`controls.negative[].must_fail_exactly` 這個「恰好殺掉指定 predicate」的合約會被隨機性破壞。`run_limits` 加 `judge_repeat`（integer）與 `must_fail_exactly_stability`（enum：`ALL_REPEATS` / `MAJORITY`），**gating 車道只准 `ALL_REPEATS`**：重跑 N 次，每一次都恰好殺掉同一組 predicate_id 才算負控成立。這是 CLAUDE.md「raw mutation kill rate 永遠不進驗收判準；只有事前命名的 mutation 被指定 predicate 殺掉才有驗收權」在隨機判準下的直譯。

### 5. 隔離與錄播：LLM judge 與 06 計畫的網路封鎖正面衝突
06 計畫的固定負控是「ClaimSpec 要求 `NETWORK_DENY_ENFORCED`，宿主只宣告 `NETWORK_POLICY_DECLARED` → 不得開始 evaluator，結果恰為 `UNSUPPORTED_ISOLATION`」。LLM judge 要打網路，所以：
- `isolation` 的 enum 目前只有 `COOPERATIVE_PROCESS`，**不要為了 judge 放寬它**。改成 judge 呼叫一律走錄播帶：`evidence.record_kind: "JUDGE_TRANSCRIPT"`，`evidence.retain` 至少含 `judge_prompt_digest`、`judge_response_digest`、`judge_fingerprint`、`swap_order`、`sample_index`。對應 CLAUDE.md「燒錢測試三擇一：錄／播／明講跳過」——**judge 判準沒有裸真跑這個選項**。
- 沿用 06 計畫 Task 3 已有的互斥 projection：judge 的 prompt、rubric、anchor set 全部放進 `ProjectionManifest.evaluator_paths`，**不得出現在 `candidate_paths`**。這就是 NASA §4.4.1.2 (b) 的「managerial independence」在 nova 的物理實現——候選看不到尺，也就改不了尺。
- NASA §4.4.1.2 (c)「financial independence」也有對應物：**judge 的 token／預算不得從候選的 budget 扣**。否則候選只要把自己的預算燒光，judge 就少跑幾輪甚至跑不成，等於候選能對判準施加財務壓力。這與 CLAUDE.md「候選執行者不能……改 budget」是同一條線的延伸，但需要一個獨立的 `judge_budget` 欄位在 07 計畫的 resource reservation 裡另立 bucket。

### 6. 閘：加一道 `judge-lane`，接到既有的三處共讀
`架構/目錄規則.toml` 的 `[[gate]]` 目前有 format／lint／types／placement／plans／tests 六道。加第七道 `judge-lane`，執行器掃 `規格/**/*.claim.json`：
- 全集宣稱要照 CLAUDE.md 那條——**直接列舉目標型別**，用 `pathlib.Path.rglob("*.claim.json")` 逐檔 `json.load`，不從 catalog 或索引檔推導有哪些 claim。
- 判定：任一 claim 的 `stimulus[].primitive` 或 judge 述詞觸及 `primitive_kind == "STOCHASTIC_JUDGE"`，而缺 `judge_calibration`、或 `measured_agreement < agreement_floor`、或 `position_swap != true`、或 `verbosity_control == "NONE"` → 非零。
- 負控（放 `架構/test_判準車道.py`）至少四格：①含 LLM judge 但無 `judge_calibration` 的 claim 必須被擋 ②`measured_agreement` 低於 floor 必須被擋 ③`judge_fingerprint` 與量測時不符必須產生 `JUDGE_DRIFTED` 而不是 `FAIL` ④**防恆真格：一份 calibration 齊全的合法 LLM-judge claim 不被誤殺，以及一份純確定性 claim（例如 `框架不得改寫裁定`）完全不受這道閘影響**。
- 三處共讀不各自維護：`工具/驗全部.py`、pre-commit hook、`.github/workflows/gates.yml` 自動吃到。
- claim 落點建議 `規格/判準/保證/隨機判準不得裸奔.claim.json`。

**坑**：
- **grader hacking 是廠商自己承認的既成事實，不是理論風險。** OpenAI Graders 文件逐字寫「Models being trained sometimes learn to exploit weaknesses in model graders」，而且指出被 hack 的模型的特徵是「model grader eval 高分、expert human eval 低分」——也就是說**只看 judge 分數的人看不到這個失效**，必須有第二套人評分數才看得出來。凡是判準本身就是優化目標的系統，這個坑一定會踩。
- **AlpacaEval 這個公開排行榜自己被長度偏誤刷過，官方後來得靠統計迴歸事後補救。** Dubois 等人做 Length-Controlled AlpacaEval 的動機就是原版可以靠「輸出更長」提高勝率；長度控制後與 Chatbot Arena 的 Spearman 從 0.94 升到 0.98。這是一個已經上線、被廣泛引用的自動評測榜，被發現有一塊分數在測長度。
- **位置偏誤嚴重到 Google 直接把「交換位置」設成產品預設。** Vertex AI 的 `flip_enabled` 預設 true，官方描述是「flipped for half of the samples to reduce bias」。一個廠商把某個緩解措施設成不需要使用者開啟的預設值，通常代表不開的後果他們踩過。呼應 Shi 等人的實測：兩個答案品質越接近，judge 越是在憑位置決定勝負——**也就是最需要 judge 幫忙分辨的邊界案例，正是 judge 最不可靠的地方**。
- **judge 在自己答不出來的題目上，一致率會崩到接近隨機。** Krumdick 等人量到 GPT-4o 的 Cohen's kappa 從 0.78（自己答對時）掉到 0.14（自己答不出、用自產參考答案時）。意涵極其現實：**judge 一旦弱於受測者，分數就是雜訊**——而「受測者會變強」正是任何驗收系統的預設前提。
- **judge 會被靜默升版，導致監控告警無法歸因。** arXiv 2606.15474 的問題陳述逐字：「every drift alarm is ambiguous between a worse product and a changed judge.」把驗收判準託管給一個你不控制版本的第三方 API，等於你的「規格」隨時可能在你不知情時被改掉。
- **OpenAI 正在 deprecate graders。** Graders 文件掛著「OpenAI is deprecating graders as part of the evals and fine-tuning workflows they support.」把驗收綁在廠商的 judge API 上，除了偏誤問題，還多一個純粹的生命週期風險：判準會被廠商下架。
- **Google 官方範例 notebook 自己講明 autorater 不可能在所有場域達到人類水準**，特別點名「human raters are expected to have specialized knowledge」的場景。廠商自己在範例程式裡寫下的限制，比第三方批評更值得當成硬邊界。
- **Anthropic 兩份官方文件都要求「與人類專家校準」，但兩份都沒有給可接受的偏差上限。** 「closely calibrated」「little divergence」沒有數字。這代表照官方文件做，你會有一個看起來很負責的流程，但**沒有任何可以寫成會 fail 的測試的門檻**——這正是 CLAUDE.md 說的「只靠人記得」的形狀。要落地就得自己選數字（kappa floor）並把它寫進 schema。

### 視覺回歸驗證的業界標準做法：基準儲存、比對判定、抖動消除、三態 triage 狀態機，以及「用 VLM 判畫面」的可重現性

**nova_fit**：nova 的視覺這塊目前只有一條「驗 node/edge ids 與 bundle digest 而非像素、缺 pinned font 必須 typed build failure」活在文件裡。照 CLAUDE.md「只以文件或 skill 形式存在的規範等於不存在」，它現在等於零。下面是把上述業界做法落成 nova 資料結構的具體樣子。

一、渲染輸入必須先被釘死，而且是 object 而非散落的旗標
`渲染參數`（預設拒絕 unknown fields，符合不可違反第一條）：
`viewport_width: int`、`viewport_height: int`、`device_pixel_ratio: float`、`color_scheme: "LIGHT"|"DARK"`、`locale: str`、`timezone: str`、`prefers_reduced_motion: bool`、`font_bundle_digest: str`（sha256，指向自架字體包，不得是 CDN URL）、`renderer_build_id: str`（瀏覽器/引擎建置識別）、`platform: str`（對應 Playwright 的 `chromium-darwin` 教訓）。
這個 object 的 canonical JSON 的 sha256 叫 `render_env_digest`，它是基準查找 key 的一半。缺 `font_bundle_digest` → build 直接紅，failure code `MISSING_PINNED_FONT`；引擎不支援釘住某欄位 → 回 typed `UNSUPPORTED_RENDER_PINNING`，不得靜默降級（對齊 v1 isolation 那條）。

二、基準用內容定址存，git 只當索引（抄 Skia Gold 而不是抄 Chromatic）
`視覺基準` record：`digest: str`（PNG bytes 的 sha256，內容定址，就是主鍵）、`grouping_key: str`（測試識別 + `render_env_digest` 的 canonical hash）、`triage_state: "UNTRIAGED"|"POSITIVE"|"NEGATIVE"`、`approver_id`、`triaged_at`、`commit_sha`、`claim_id`、`force_recapture: bool`。
影像本體放內容定址的 blob store，不進 git（Google Android 官方也承認 git 不適合大二進位）。基準庫與 triage 表放在**執行者碰不到**的位置——這正好落在 CLAUDE.md「候選執行者不能自報完成、不能寫 state DB」那條上：`triage_state` 的寫入權不在執行者手上。
查找 key 是 `(grouping_key)`，而 `grouping_key` 已經把 `render_env_digest` 吃進去了，所以跨平台天然不共用基準，不需要另設規則。
允許一個 `grouping_key` 有多筆 `POSITIVE`（Gold 的多基準機制），這是放寬門檻的正解替代品。

三、比對判定：預設 EXACT，放寬必須是 ClaimSpec 的一部分
`比對規格`：`matching_algorithm: {kind: "EXACT"} | {kind: "FUZZY", max_different_pixels: int, pixel_delta_threshold: int} | {kind: "SOBEL_FUZZY", edge_threshold: int, max_different_pixels: int, pixel_delta_threshold: int}`。
預設 `EXACT`（digest 相等即通過，連比都不用比）。
關鍵機制設計：`matching_algorithm` 這個欄位屬於**已准入的 ClaimSpec 內容**，落在 CLAUDE.md「實作者只改該 task 列出的 subject，不能改已准入的 ClaimSpec」的保護面裡。於是「調高 threshold 蓋過抖動」在 nova 不是一個誘惑而是一個結構性不可能：放寬門檻 ＝ 改規格 ＝ 必須走 RequirementChange，舊 claim 與證據不覆寫。這是把業界四家都只能用文件勸阻的事情，變成 nova 可以用閘擋住的事情。
對應的負控測試至少三格：①把 `max_different_pixels` 從 0 調到能蓋過一個真缺陷，閘必須紅；②合法的 RequirementChange 路徑調整同一欄位不被誤殺（防恆真）；③`matching_algorithm` 缺欄位時預設是 EXACT 而不是最寬。

四、三態狀態機（合併 Gold 與 Chromatic 兩家的官方語義）
狀態：`UNTRIAGED`（初始）／`POSITIVE`／`NEGATIVE`。
允許的邊：
- `UNTRIAGED → POSITIVE`：需人類 approver，寫 `approver_id` 與 `claim_id`；效果是該 digest 成為該 grouping 的合法基準之一。
- `UNTRIAGED → NEGATIVE`：立刻讓 build 紅（`build_status = FAILED`），並設 `force_recapture = true`，讓下一次跑即使增量選片會跳過也強制重拍（Chromatic deny 的官方語義）。
- `NEGATIVE` 與 `UNTRIAGED` 對基準的效果**相同**：都沿用既有 `POSITIVE` 集合比對。這句是 Chromatic 官方原文，也是這個狀態機唯一容易寫錯的地方——`NEGATIVE` 不是第三種基準。
- `POSITIVE → 任何狀態`：只能走 RequirementChange，不提供一般 API。
- **不提供 approve-all / batch accept**：這是 nova 相對業界該加嚴的一點，因為 nova 的執行者是不可靠執行者，批次核可等於把 triage 退化成橡皮圖章。
另外抄 Gold 的一個做法：`UNTRIAGED` 的數量本身是可查詢、可計量的指標，接進閘裡（Flutter 就是為此加了 untriaged 影像數的 benchmark）。閘條件：`count(triage_state == UNTRIAGED) == 0` 才准合。

五、nova 已簽的「驗 node/edge ids 與 bundle digest 而非像素」怎麼落地才不出事
`圖快照`：`{node_ids: sorted[str], edge_ids: sorted[str], bundle_digest: str}`，比對就是三個欄位全等。這條在業界的對應物是 Chromatic TurboSnap——但要抄的是它的**保守 fallback**，不是它的省事。
必須有一份 `全拍觸發條件` 清單，任一成立就 `FULL_RECAPTURE` 而不是信任圖：依賴圖產生器版本變動、lockfile 缺失或不一致、`render_env_digest` 任一欄位變動、`font_bundle_digest` 變動、渲染引擎 `renderer_build_id` 變動、比對規格變動。
這裡還踩到 CLAUDE.md「全集宣稱一律直接列舉目標型別」那條：`node_ids` / `edge_ids` 必須直接列舉圖上的節點與邊（走該型別的列舉 API），不得從別的集合推導或用計數代替。

六、VLM 只能寫 advisory 欄位，永遠不寫 triage_state
若真要讓 VLM 參與，資料結構上要把它關進 `vlm_opinion: {model_id, prompt_digest, verdict: "LIKELY_OK"|"LIKELY_REGRESSION", run_index: int, sampled_at}`，是 `視覺基準` 的附註欄位，**schema 層就不接到 `triage_state`**。理由是可查到的數字：最樂觀的公開 agreement 是 85.3% / κ=0.70，換一批受測對象就掉到 73.9%，而且崩的方向是 hallucination 造成的 false positive（多報成功）——正好是 nova 最不能容忍的方向（執行者自認完成不算完成）。
如果保留 VLM，最少要記 `run_index` 至少三次並算 `agreement_rate`，因為唯一有報跑間變異的來源（WebJudge）標準差 1.1%、最大 1.8%，沒有這個欄位就沒辦法知道自己的評審有多抖。

七、機制落點（把文件變成會 fail 的測試）
`架構/檢查視覺基準.py` ＋ `架構/test_視覺基準.py`，負控四格：①拿掉 `font_bundle_digest` 必須得到 typed `MISSING_PINNED_FONT` 而不是通過；②`matching_algorithm` 被實作者放寬必須被閘擋；③存在 `UNTRIAGED` 時閘必須紅；④防恆真格：全部釘死且無 untriaged 的合法情境不被誤殺。
閘註冊進 `架構/目錄規則.toml` 的 `[[gate]]`（現有六道之外加一道，例如 `visual`），三處共讀（`工具/驗全部.py`、pre-commit hook、`.github/workflows/gates.yml`）——不要另開第二份閘清單。
claim 落點建議 `規格/工程/保證/視覺基準必須釘死渲染輸入.claim.json`。

**坑**：
- 門檻爬升直到缺陷逃逸：Applitools 官方部落格逐字承認調高容忍度會在覆蓋上開洞，「if a page we're testing is corrupt within this new tolerance (e.g., typo, missing icon, etc.), then our test could miss it」。
- Chromatic 官方給了門檻過高的具體後果：threshold 設到 0.8 會讓位移類變化（positioning changes）偵測不到。
- Google Android 官方對「換成 smart differ 就沒事」下了同一句警語：容忍度與語義比較器兩條路都可能製造假紅，也都可能漏掉「被錯誤地認為夠像」的錯誤——換 AI 比較器不是免死金牌。
- Chromium Gold 官方警告 fuzzy diffing「possibly causing a test to erroneously pass」，並建議優先用「同一 test 多張 positive 基準」而不是放寬比對。
- 字體多趟渲染：Chromatic 官方指出瀏覽器為了 time-to-first-meaningful-paint 會分多趟渲染自訂字體，導致同一個 story 在重複跑之間用不同字體渲染而不穩定；解法是 await document.fonts.ready 並把 @font-face 指向本地檔案而非 CDN。
- JS 動畫不會被自動凍：Percy 官方明說預設不執行 JS，所以 jQuery、SVG animateTransform、Highcharts、Velocity、Greensock 全都要逐個 library 手動關；Chromatic 同樣只自動暫停 CSS 動畫/影片/GIF，JS 驅動的動畫會被拍到中間格。
- 跨平台基準：Playwright 官方把 browser+platform 寫進快照檔名，因為「Screenshots differ between browsers and platforms due to different rendering, fonts and more」；Android 官方進一步警告即使全隊同平台，函式庫、OS 或硬體架構的變動仍會造成小差異——在 Mac 產的基準到 Linux CI 就紅是官方預期而非意外。
- 增量選片的錯誤失敗方向：Chromatic TurboSnap 在 preview.js 匯入變動、Storybook 設定變動、static 資料夾變動、package.json 依賴變動但無有效 lockfile、基礎設施升級、新增瀏覽器時，一律退回全拍——因為依賴圖此時不足以保證覆蓋。抄增量選片而不抄這份 fallback 清單就會漏拍。
- 未 triage 的 digest 會沉積：Skia Gold 的搜尋頁預設就是列「at head 仍 untriaged」的 trace，Flutter 甚至為此加了一個統計未 triage 影像數的 benchmark——說明 untriaged 堆積是實際發作過的問題，不是理論風險。
- VLM 評審的 agreement 不是常數：WebVoyager 自報 85.3%／κ=0.70，同一套方法被第三方拿去評六個 agent 只剩 73.9%，主因是 agent 最終回覆的 hallucination 造成高 false positive，等於系統性高估成功率。
- VLM 評審的輸入長度上限會沉默地讓判斷退化：對超過 80 個 action step 的軌跡，截圖過多造成 token 溢出，agreement 顯著下滑，而這不會以錯誤形式表現出來。
- VLM 能排序不能打分：conformal prediction 量出來的分數區間在美學/自然影像上覆蓋約 40% 分數範圍、在圖表/數理上擴到約 70%，作者明指判官「correctly ordering responses but failing to assign reliable absolute scores」——而視覺回歸要的正是絕對判定。
- W3C WebDriver 的 Take Screenshot 規範把實際取像那步寫成「Complete implementation specific steps」，全篇不提 device pixel ratio、縮放或色彩管理，也沒有任何位元組決定性的敘述——任何「用 WebDriver 截圖所以是決定性的」的假設都沒有標準背書。
- 廠商準確率數字不可當量測：Applitools 的 99.9999% 出現在部落格與新聞稿，沒有公開方法學、沒有可重現 benchmark、查不到獨立第三方驗證。

### 在機制上擋住「實作者把驗收條件改弱」：GitHub 分支治理、SLSA、in-toto、OPA、Gerrit/Gitea 與突變測試門檻的官方立場

**nova_fit**：## 先回答三個核心問題

**一、業界公認「本地防線不算防線」嗎？** 是，但業界不用這句話，而是用兩個標準化表述。SLSA Build L1 逐字說 provenance「trivial to bypass or forge」，要跨到 L2 必須「not on an individual's workstation」；SLSA Source L2/L3 的句型一律是「**the SCS** issues」「**the SCS** is configured to enforce」——發證與執法的主詞永遠是 source control system，不是貢獻者。Git 官方文件自己承認 hooks 住在 `$GIT_DIR/hooks`、clone 不帶、`--no-verify` 可繞、沒有 executable bit 就靜默忽略。所以 nova 的 pre-commit hook 在業界分類裡是「開發者便利設施」，不是防線；nova CLAUDE.md 已經把這件事寫對了，不需要改。

**二、權威執法點必須在哪裡？** 在「候選執行者的 write 權限碰不到的控制面」。業界有三種成熟落點，強度遞增：(a) 平台的 server-side ruleset（GitHub org-level ruleset、Gitea protected file patterns）；(b) 規則本身住在受**不同 ACL** 保護的版控命名空間（Gerrit 的 `refs/meta/config`，改它要另開一個 change 由 project owner submit）；(c) 執法器的**程式碼**住在另一個 repository（GitHub ruleset workflows 指定 source repository）。nova 現在三種都沒有：閘的定義（`目錄規則.toml`）、閘的程式（`工具/驗全部.py`）、閘的判準（`must_fail_exactly`）、以及觸發閘的 workflow（`.github/workflows/gates.yml`）全部在同一個 repo、同一個 branch、同一批 PR 可及範圍內。protected branch 只保證「有人看過」，不保證「看的人跟改的人不是同一個」。

**三、「已核准的驗收資產清單」在業界叫什麼？** 業界不用一個名字，而是刻意切成三個不同物件，nova 現在把三個揉成一團：

| 物件 | 業界名 | 內容 | 誰簽 |
|---|---|---|---|
| 規則 | **layout**（in-toto）／**policy**（SLSA VSA 的 `policy` 欄位）／**bundle**（OPA） | 「什麼算通過」 | project owner / 規格作者 |
| 檔案清單＋hash | **manifest**（OPA `.signatures.json` 的 JWT `files`；TUF targets metadata） | 「哪些檔、各自的 sha256」 | 同上，門檻簽章 |
| 判定證據 | **attestation**（in-toto attestation／SLSA Provenance／**VSA**／GitHub artifact attestation） | 「這次跑的結果」 | 執法器本身（CI 的 OIDC 身分） |

**不要叫 baseline。** 業界的 baseline（detect-secrets `.secrets.baseline`、Sonar new-code baseline）語意是「已接受的現狀快照」，它的設計就允許重新產生 —— 那正好是 nova 要防的動作。

**清單自己怎麼防被改？** 官方答案只有三招，nova 應該三招全上：
1. **驗證用的信任根不能跟被驗的資料同源** —— OPA 把 `keys` 放在 OPA 設定檔而不是 bundle 裡；TUF 用 root role 的 threshold 簽章。
2. **驗「集合相同」而不只是「內容相同」** —— OPA 驗證第二步逐字是「the JWT payload and target directory specify the same set of files」。只 hash 已知檔案的話，**刪掉一整份 claim 會靜默通過**，這是 nova 最可能踩的一腳。
3. **放在不同 ACL 的命名空間** —— Gerrit `refs/meta/config` 的模式。

## 落到 nova：具體資料結構與欄位

### A. 把 must_fail_exactly 從四支實作檔裡搬出來，變成 manifest 覆蓋的資料

新增 `規格/驗收/清單.manifest.json`（欄位名照 OPA/SLSA 的既有語彙，ASCII，符合 CLAUDE.md 的跨程序 schema 例外）：

```json
{
  "manifest_version": 1,
  "scope": "規格/驗收/",
  "continuity_since_commit": "bc26f24",
  "enforcement_config_digest": {
    "sha256": "<GitHub ruleset API 回應正規化後的 hash>"
  },
  "files": [
    {
      "name": "規格/工程/保證/閘必須自動執行.claim.json",
      "algorithm": "SHA-256",
      "hash": "…",
      "claim_id": "閘必須自動執行",
      "must_fail_exactly": ["…"],
      "負控": [
        {"mutation_id": "入口第一紅就停", "predicate": "…", "expected": "FAIL"},
        {"mutation_id": "入口永遠回零",   "predicate": "…", "expected": "FAIL"},
        {"mutation_id": "CI漏跑一道",     "predicate": "…", "expected": "FAIL"},
        {"mutation_id": "hook吞掉非零",   "predicate": "…", "expected": "FAIL"},
        {"mutation_id": "全綠時不擋正常commit", "predicate": "…", "expected": "PASS"}
      ]
    }
  ]
}
```

三個非顯而易見的設計點：

- **`files` 必須是全集，且閘要驗「目錄 iterdir 的結果 == files 的 name 集合」**，兩邊互相 diff。這正是 CLAUDE.md 那條「全集宣稱一律直接列舉目標型別」在這裡的具體化：用 `Path("規格/驗收").iterdir()` 過濾 `is_file()` 取得實際集合，跟 manifest 對拍。缺一個要紅，多一個也要紅。這一條要有負控：測試裡刪掉一份 claim，閘必須紅。
- **`負控` 是 in-toto ARTIFACT_RULES 的 REQUIRE 語意，不是一個分數。** `expected: "FAIL"` 對應 REQUIRE（這個 mutation 必須被殺掉），`expected: "PASS"` 對應防恆真格。這跟 nova 既有的「只有事前命名的 mutation 被指定 predicate 殺掉才有驗收權」是同一件事，只是把它從散落的實作檔提升成受 hash 保護的資料。
- **`continuity_since_commit` 與 `enforcement_config_digest` 是抄 SLSA Source Track 的連續性要求**（「continuity MUST be established and tracked from a specific start revision」）。閘每次跑時呼叫 GitHub ruleset REST API 讀當前設定，正規化後 hash，跟 manifest 裡的比對：不一致就把 claim 降級成 `UNVERIFIED_ENFORCEMENT_CHANGED`，而不是直接拒絕。這就把「repo 設定被改掉」從一個沉默的漏洞變成一個**會紅的測試**。

### B. 閘的產出改成 VSA 形狀，寫進 `規格/驗收/證據/<commit_sha>.vsa.json`

```json
{
  "verifier": {"id": "https://github.com/<org>/nova-閘/.github/workflows/gates.yml@refs/heads/main"},
  "timeVerified": "2026-08-27T12:00:00Z",
  "resourceUri": "git+https://github.com/<org>/nova@<commit_sha>",
  "policy": {
    "uri": "規格/驗收/清單.manifest.json",
    "digest": {"sha256": "…"}
  },
  "inputAttestations": [],
  "verificationResult": "PASSED",
  "verifiedLevels": ["NOVA_CLAIM_L2"]
}
```

`verifier.id` 必須是**閘所在的 workflow 路徑**，不是實作者。這對應 `gh attestation verify --signer-workflow`：驗證者可以拒收由別支 workflow 簽出來的結果，也就擋掉「實作者新增一支自己的 workflow 冒充閘」。SLSA Source 的「MUST be created contemporaneously」意味這份 VSA 只能在 CI run 裡生成，不能由本地補簽 —— 所以它**不該進 git**，應該當 CI artifact / attestation 存，否則就變成一份實作者可寫的檔。

### C. GitHub 設定：照官方能力逐項對應 nova 的兩個出口

出口二（repo 設定可被改）——**可以關掉**：建 organization、repo 移進去，把 `main-gates` 從 repo-level 升為 **organization-level ruleset**。官方逐字保證「only owners of the organization can edit the ruleset」且 repo 層疊加「never less restrictive」。實作者即使拿到 repo admin 也改不動。

同時要加的規則（全部是官方原生，不需自己寫工具）：
- **Require approval of the most recent reviewable push** —— 這是擋 nova 最怕的那條路徑（先送乾淨 PR 拿核可，核可後再 push 一個拿掉 `must_fail_exactly` 的 commit）的**唯一**原生機制。只開 required approvals 擋不住。
- **Dismiss stale pull request approvals**。
- **Require review from Code Owners**。
- **Restrict file paths**（push ruleset），鎖 `規格/**`、`架構/*.toml`、`.github/**`，allowed exceptions 留空，bypass list 只放規格作者。
- **Ruleset workflow** 指向另一個 repo（例如 `nova-閘`）裡的 `gates.yml`。這樣實作者改本 repo 的 `.github/workflows/` 完全不影響閘 —— 目前 nova 的 `gates.yml` 是實作者可改的，等於閘的觸發條件握在被閘管的人手上。

`.github/CODEOWNERS` 必須自我持有，並且注意多 owner 是 OR：
```
/.github/CODEOWNERS   @規格作者
/.github/             @規格作者
/規格/                @規格作者
/架構/目錄規則.toml    @規格作者
```

出口一（`gh pr merge --admin`）——**關不掉**，官方逐字就是「Use administrator privileges to merge a pull request that does not meet requirements」。唯一的處理是（a）org-level ruleset 的 bypass list 清空 +（b）用上面的 `enforcement_config_digest` 讓「有人動過設定」變成一個會紅的測試。CLAUDE.md 現在寫「兩者都是人為決定，不是機制漏洞」，這個判斷跟業界一致，可以保留 —— 但可以補一句：業界的做法不是消滅它，是**記錄連續性**（SLSA Source Track），讓繞過留下痕跡並使 claim 自動降級。

### D. conftest / Rego 當中間層（可選但便宜）

`.claim.json` 是結構化資料，conftest 直接吃 JSON。把「每份 claim 必須有非空的 `must_fail_exactly`」「`負控` 至少要有一格 `expected: PASS` 的防恆真格」寫成 Rego `deny` 規則，policy 檔放進 `nova-閘` 那個 repo。好處是規則與資料的授權天然分離，而且 conftest 非零退出可以直接接進 `工具/驗全部.py` 的閘清單，不破壞 CLAUDE.md「閘清單只有一份」的規定 —— 新增一個 `[[gate]]` 條目即可。

**坑**：
- GitHub branch protection 預設**不**套用到 admin（官方逐字「the restrictions of a branch protection rule do not apply to people with admin permissions」）。裝了就以為擋得住自己，是最普遍的誤解。要另外開「Do not allow bypassing the above settings」。
- required status check 的通過定義官方逐字含 `skipped`：「must have a `successful`, `skipped`, or `neutral` status」。一道被 `if:` 條件跳過的 job 會被計為通過。nova 的 `gates` job 若哪天加了條件式，閘會靜默變成永遠綠 —— 這正是 CLAUDE.md 已經警告過的「入口永遠回零」的 CI 版本。
- OpenSSF Scorecard 官方明列：沒有 admin token 就查不到 EnforceAdmins、RequireLastPushApproval、RequiresStatusChecks、DismissStaleReviews。用一般 token 跑會得到一個「看起來有分數」的結果，而它根本沒檢查 admin 是否被豁免。監看器的二手資料問題的實例。
- CODEOWNERS 超過 3 MB 官方逐字「will not be loaded」—— 整份靜默失效，UI 上看不出異常。這跟 nova 已經踩過的「`驗收.yml` 顯示 active 但 push/pull_request 一次都不觸發」是同一類：平台級的靜默失效，沒有錯誤訊息。
- CODEOWNERS 多個 owner 是 OR 不是 AND，官方逐字「an approval from any of the code owners will be sufficient」。寫兩個名字不等於要兩個人簽 —— 要真的兩人審必須另外設 required approvals 數量，或改用 Gerrit L4 那種模型。
- CODEOWNERS 不把自己列為受保護路徑，實作者可以在同一個 PR 裡刪掉或搬走它，之後所有 owner 規則失效。GitHub 官方文件沒有提醒這件事（我查了，未查到），只有第三方指南在講。
- squash merge 時 file path 規則只驗最終那個 merge commit 的 metadata，不驗 PR 內的個別 commit（來源：WebSearch 摘要指向 docs.github.com available-rules-for-rulesets，我未在直接 fetch 中複現該段落，nova 若要依賴 Restrict file paths 應該自己實測一次）。
- Git hooks 沒有 executable bit 就被官方逐字「ignored」—— 靜默。nova 的 `工具/裝_git_鉤子.py` 若某次 chmod 失敗或在某些檔案系統上失效，hook 從此不跑而沒有任何人會發現。這值得一格負控。
- in-toto 規格自己明說 `expected_command` 「should not be trusted for security checks」，不符只能發 warning。教訓：**寫在 policy 裡的東西不等於受 policy 保護的東西**。nova 的 `.claim.json` 若某些欄位只是描述而沒有被 hash 覆蓋或沒有對應的 predicate，它們就是 nova 版的 expected_command。
- Stryker 的 `break` 預設是 `null`，官方逐字「Set `break` to `null` (default) to never let your build fail」。整個生態最常見的狀況是團隊裝了突變測試、產出漂亮報表、CI 從來不會因此紅過。「有工具」不等於「有閘」。
- PIT 的門檻預設是整數百分比，官方承認這讓覆蓋率/突變分數可以靜默退化（文件舉例：一萬行專案設門檻 61，可以掉近百行覆蓋而不觸發失敗），為此才加了 `thresholdPrecision`。任何以四捨五入後的數字當閘的設計都有這個盲區。
- Google 的實測結論：mutation score 不只是算不動，更是「unable to find a good way to surface it to the engineers in an actionable way」。加上等價 mutant 的判定不可決定 —— 分數型突變門檻天生會把不可殺的 mutant 算進分母。這是「分數當閘」這條路在最大規模上被走過並放棄的紀錄。
- detect-secrets 的 `.secrets.baseline` 這類 baseline 檔的結構性缺陷：要接受新的誤判就得重新產生並重新 audit baseline，而重新產生的動作同時會把真陽性一起吞進去。凡是「可重新產生」的已核准清單都有這個缺陷 —— 這就是 nova 不該用 baseline 這個詞、也不該用這個語意的原因。
- Gerrit 的 code-owners plugin 有一個 implicit approval 選項：開了之後，code owner 自己上傳、且只動到自己擁有的檔案的 change，會自動視為已獲 code owner 核可。連 Gerrit 這種以分離度著稱的系統，預設選項裡都藏著一條自我核可的路。

### 一個數字的來源證明：業界 attestation／provenance 的官方欄位形狀，以及「人量／機器量／模型判」有沒有官方封閉列舉

**nova_fit**：## 先講結論：業界收斂出的形狀不是「一個 provenance enum 欄位」

查完 SLSA／in-toto／PROV-O／OSCAL／CycloneDX／C2PA／FHIR，所有官方 schema 收斂到同一個三元組，沒有一份是靠單一字串 enum 解決的：

1. **agent**（誰／什麼產生的）— 一定是 URI 身分 + 型別，不是形容詞。SLSA `builder.id`、VSA `verifier.id`、C2PA `softwareAgent`、OSCAL `actor` + `actor-type`、PROV-O `wasAttributedTo` 指向 `Person`／`SoftwareAgent`／`Organization`。
2. **procedure**（用什麼手段）— SLSA `buildType`、SOSA `usedProcedure`、OSCAL `method`、CycloneDX `technique`、FHIR `Observation.method`。
3. **evidence**（憑什麼）— in-toto `ResourceDescriptor`（`uri`／`digest`／`content` 至少一個）、SCAI `evidence`、CycloneDX `confidence`。

而**唯一**有官方背書、直接切「人做的／從現實量到的／非訓練演算法算的／訓練模型生成的」的封閉列舉，是 **IPTC digitalSourceType**（C2PA 採用）。OSCAL `actor-type` 只給到 `tool｜assessment-platform｜party`，沒有「模型」那一格。所以 nova 需要的分類**必須自己定義，但軸線可以直接抄 IPTC，不必自創**。

## 落到 nova：改 09 的 `RankingSchema.schema.json` 與 `選拔.py`

### 1. 新增 `規格/工作/ScoreProvenance.schema.json`

每個 `score[score_id]` 旁邊必須有一個同名的 provenance 物件，`additionalProperties: false`（照 CLAUDE.md「每個 object 預設拒絕 unknown fields」）：

- `provenance_kind`（必填，封閉列舉，ASCII 因為是跨程序 schema 值）。抄 IPTC 的軸，切成五格：
  - `DIRECT_MEASUREMENT` — 程式直接量到的確定值（exit code、byte 數、wall clock）。對應 IPTC `digitalCapture`。
  - `DETERMINISTIC_ANALYSIS` — 確定性演算法算出來的，同輸入必同輸出（覆蓋率、AST 統計、指定 predicate 的 mutation 判定）。對應 IPTC `algorithmicMedia`（「純粹由演算法產生、不基於任何取樣訓練資料」）。
  - `NONDETERMINISTIC_TOOL` — 機器產生但不保證重播（benchmark timing、fuzz、取樣）。IPTC 無對應格，是 nova 自己的必要切分，因為它直接決定重播器能不能驗。
  - `MODEL_INFERENCE` — 訓練過的模型判的（LLM-as-judge、classifier）。對應 IPTC `trainedAlgorithmicMedia`。
  - `HUMAN_JUDGEMENT` — 人判的。對應 IPTC `digitalCreation`／`humanEdits`，也對應 OSCAL `actor-type=party` 與 `method=INTERVIEW`。
- `agent`（必填物件，抄 SLSA `runDetails.builder` + OSCAL `actor`）：
  - `agent_id`：TypeURI，必填。例 `urn:nova:tool:pytest`、`urn:nova:model:claude-opus-5`、`urn:nova:person:<id>`。
  - `agent_type`：封閉列舉 `TOOL｜MODEL｜PERSON｜PLATFORM`（PROV-O 三分 + OSCAL 的 platform 那格）。
  - `agent_version`：`map<string,string>`，直接抄 SLSA `builder.version`（「元件名到版本的 map」）。`MODEL_INFERENCE` 時必填且必須含模型 id 與取樣參數。
- `procedure_id`（必填 TypeURI，抄 SLSA `buildType` / SOSA `usedProcedure`）：這個分數是用哪個具名程序算出來的。`MODEL_INFERENCE` 時它必須指向一份被版控的 rubric／prompt digest，否則分數不可重現。
- `evidence`（必填，`ResourceDescriptor` 陣列，非空）：每項照 in-toto 硬規則 `uri`／`digest`／`content` **至少一個**。這條是 nova 直接抄得最乾淨的一條——它讓「證據可以是 log 指標、可以是雜湊、可以是內嵌小值，但不能三者皆空」變成 schema 就擋得住的事。
- `confidence`（DECIMAL 0..1，抄 CycloneDX）：**只有 `NONDETERMINISTIC_TOOL`／`MODEL_INFERENCE`／`HUMAN_JUDGEMENT` 允許出現且必填；`DIRECT_MEASUREMENT`／`DETERMINISTIC_ANALYSIS` 出現 `confidence` 直接是 schema 錯誤**。理由：對確定性量測談信心度是自欺。
- `observed_at` / `invocation_id`（抄 SLSA `metadata.startedOn` / `invocationId`）。

**明確不抄的**：in-toto 的 `annotations` 與 OSCAL 的 `prop[@name='method']` 這類泛用逃生口。OSCAL 把 EXAMINE／INTERVIEW／TEST 塞進屬性包，結果 schema 驗證抓不到錯值——nova 不要重演。

### 2. 改 `RankingSchema.dimensions[]`

現行每維是 `score_id`、`value_type=INTEGER|DECIMAL`、`direction=ASC|DESC`、`missing=REJECT_CANDIDATE`。新增兩個必填欄位：

- `allowed_provenance`：非空的 `provenance_kind` 集合。這是本題的核心——**維度自己宣告它接受什麼來源，而不是靠事後審查**。例：`品質` 維度若寫 `["DETERMINISTIC_ANALYSIS"]`，LLM 吐的 7.5 就進不來；若刻意允許 `["MODEL_INFERENCE"]`，那是規格作者的明示決定，留在 ClaimSpec 上有跡可循。
- `min_confidence`：DECIMAL 0..1，選填；當 `allowed_provenance` 含非確定性格時必填。低於此值的分數視同 missing。

### 3. 改 `rank_candidates(schema, verdicts, cutoff_seq)`

在現行 `rank_key = tuple(normalize(score[dim.score_id], dim) for dim in schema.dimensions) + (candidate.digest.value,)` 這行**之前**插入來源閘：

- `provenance_kind ∉ dim.allowed_provenance` → typed failure `SCORE_PROVENANCE_NOT_ALLOWED`，該候選走既有的 `missing=REJECT_CANDIDATE` 同一條路徑。
- provenance 物件缺席 → `SCORE_PROVENANCE_MISSING`。**不得預設當成 `DIRECT_MEASUREMENT`**——這正是 CLAUDE.md「能力不足只回 typed `UNSUPPORTED_*`，不得靜默降級」那條的同型狀況。
- `confidence < dim.min_confidence` → `SCORE_CONFIDENCE_BELOW_THRESHOLD`。

`rank_key` **不含** provenance（來源不參與排序，只參與准入），但 **`SelectionRecord` 的 digest 必須含 provenance**，否則「同分不同來源」會產生相同 digest，等於選拔紀錄說謊。

### 4. 對齊 nova 既有的權力邊界

CLAUDE.md 已有「候選執行者不能自報完成、改 criterion、改 effect receipt」。這裡要補上同型的一條：**候選執行者不能自己寫 `provenance_kind` 與 `agent_id`**。SLSA v1.0 明文的「Consumers MUST accept only specific signer-builder pairs」就是這件事的官方版本——來源欄位若由被評的一方填寫，它一秒就能寫 `DIRECT_MEASUREMENT`。provenance 必須由 05 的執行封套／重播器在封套外側蓋章，落點與 `規格/工作/保證/最佳截止前選拔.claim.json` 同層加一份 `規格/工作/保證/分數來源受限.claim.json`。

### 5. 會 fail 的負控（缺一不可）

1. `MODEL_INFERENCE` 的 7.5 在 `allowed_provenance=["DETERMINISTIC_ANALYSIS"]` 的維度上被拒，且 winner 換成第二名。
2. 沒有 provenance 物件的 score 被拒，**不是靜默通過**。
3. 候選自己在 verdict 裡塞 `provenance_kind="DIRECT_MEASUREMENT"`，封套外蓋章的值與之衝突 → 拒，且以封套值為準。
4. `confidence` 出現在 `DIRECT_MEASUREMENT` 上 → schema 層拒。
5. 兩候選分數完全相同、`provenance_kind` 不同 → `SelectionRecord` digest **不同**。
6. **防恆真格**：合法的 `DETERMINISTIC_ANALYSIS` 分數不被誤殺，winner 與加閘前一致；任意 input permutation 仍得同一 digest（維持 Task 4 既有的 property test）。

**坑**：
- **「有 provenance 欄位」被當成「provenance 可信」。** SLSA 之所以要把等級拆成 Completeness／Authenticity／Accuracy 三個正交面向，就是因為這個混淆。L1 明文允許未簽章、明說偽造是 trivial：能改 build script 的人就能改 provenance。nova 若只在 RankingSchema 加一個來源欄位、卻讓候選執行者自己填，做出來的就是一個 L1 —— 對誠實的執行者有用（抓失誤、事後鑑識），對想贏的執行者等於零。
- **封閉列舉的軸切錯，代價是退役整批詞。** IPTC 的 digitalSourceType 退役了 minorHumanEdits、softwareImage、digitalArt 三個詞。看得出第一版是照「產物長什麼樣／算不算藝術」切的，改版後才改成照「有沒有經過訓練過的模型、有沒有人的判斷介入、是不是從現實量到的」切。教訓：軸要切在**信任邊界**上（誰能偽造、能不能重播），不要切在**外觀分類**上（分數看起來像什麼）。nova 若把 `NONDETERMINISTIC_TOOL` 和 `DETERMINISTIC_ANALYSIS` 併成一格「機器量的」，就是在重犯這個錯——因為重播器能不能驗，正好卡在這條線上。
- **選填的來源宣告等於沒有宣告。** C2PA 早期版本的 digitalSourceType 是選填、也不強制每份 manifest 都有起始動作；現行 2.4 規格改成 standard manifest 中 c2pa.created 或 c2pa.opened **必須擇一存在**。一個可以省略的 provenance 欄位，在實務上會被大量省略，然後下游被迫「沒填就當它沒問題」。nova 的 provenance 物件必須是必填，且缺席時回 typed failure，不是預設成最寬鬆那格。
- **把封閉列舉塞進泛用屬性包，schema 就不再是執法者。** OSCAL 的 EXAMINE／INTERVIEW／TEST 是正式定義的封閉三值，卻放在 `prop[has-oscal-namespace('http://csrc.nist.gov/ns/oscal') and @name='method']/@value` 這種通用 property 裡，不是第一級型別欄位。結果是：值錯了 JSON schema 驗證抓不到，只能靠額外的 constraint 或人工檢查。in-toto 的 `annotations`（自由 key-value）是同一種逃生口。這正好是 nova CLAUDE.md「只以文件形式存在的規範等於不存在」的 schema 版本。
- **provenance schema 本身會演化，欄位名不是永恆的。** SLSA v0.2 → v1.0 大改名：parameters→externalParameters、environment→internalParameters、materials→resolvedDependencies、buildInvocationId→invocationId、buildStartedOn→startedOn、buildFinishedOn→finishedOn；configSource、buildConfig、completeness、reproducible 四個欄位直接刪除。而且改名不是純美學——externalParameters／internalParameters 的拆分是為了讓信任邊界顯性化。nova 的 ScoreProvenance 從第一天就要有版本識別（in-toto 的做法是把版本編進 predicateType URI，例如 test-result/v0.1、scai/v0.3），否則 SelectionRecord digest 會在改 schema 那天全體失效而無法辨識。
- **「一個來源、一個標籤」在實務上撐不住。** CycloneDX 的官方範例是同一個 identity 同時掛 filename（confidence 0.1）與 hash-comparison（confidence 0.8）兩個 method；C2PA 是把 digitalSourceType 掛在**每一次動作**上而不是掛在檔案上，才能表達「原本實拍、後來被生成式模型改過」。FHIR 更直接：performer（人）與 device（機器）是兩個並存的欄位，不是同一個欄位的兩個取值。nova 若某個分數其實是「機器量了 base，模型調了權重」，單一 `provenance_kind` 會逼人選一個講——而那個選擇一定是往寬鬆的方向偏。至少要保留升級成 methods 陣列的空間，或明訂「混合來源一律取最不可信的那格」。
- **AI 供應鏈標準目前解的是「模型是誰發布的」，不是「模型的輸出該不該被採信」。** OpenSSF Model Signing (OMS) 做的是模型權重、設定檔、tokenizer、資料集的完整性簽章；AI/ML 工作組正在做的是模型生命週期 provenance。這些**都不涵蓋**「這個模型在某次推論吐出的分數，下游該給它什麼權重」。nova 不要以為引用 OMS 或等 OpenSSF 出規範就能解決 09 的問題——那是不同層的東西，模型簽章驗過了，它吐的 7.5 一樣沒有任何背書。
