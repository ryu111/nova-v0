# 需求：可宣告的約束

> 起點是一個觀察：有些情況**一直發生**，有些事情**不允許發生**。
> 與其每次派工都靠呼叫端記得寫進提示詞，不如讓它變成**宣告的東西**。
>
> 但這裡有一條線必須先劃清楚，否則這個功能會變成這個系統最痛恨的那種東西——
> **看起來有保護，實際上沒有。**

## 一、兩種強度，混用是錯的

| | 告知型 | 強制型 |
|---|---|---|
| 做法 | 把文字注入執行者的上下文 | 在執行者**碰不到的地方**攔截 |
| 效果 | 執行者**可能**遵守 | 執行者**做不到** |
| 是不是保證 | **不是** | **是** |
| 能不能寫成會 fail 的測試 | 只能測「有沒有注入」，**不能測「有沒有遵守」** | 能測「違規動作確實被擋下」 |

**「不允許發生」這四個字，只能由強制型承接。**

用注入的方式寫「禁止呼叫外部 API」，得到的是一句**請求**，不是一條**邊界**。
而這個系統的教條是：只以文字形式存在的規範**等於不存在**。

所以規則是：

> **一條約束宣告成強制型，就必須指出它的執法點與負控；**
> **宣告成告知型，就不得在任何地方被當成保證。**

**負控**：讓一條告知型約束出現在「保證」清單裡，該格必須轉紅。

## 二、強制型的執法點必須在**我們自己的閘**

執行者後端有好幾種，而且會換。某些後端原生提供工具攔截（且該攔截能穿透
「跳過權限檢查」模式），某些完全沒有。

**所以強制型約束的執法點必須在執行封套自己的閘上**——
後端原生的攔截只能當**額外的內層防線**，不能是保證的所在。

理由與整份架構一致：**保證不能掛在單一廠商的能力上**，
否則同一條約束在不同後端有不同強度，而測試只會覆蓋最常用的那個。

**負控**：把某條強制型約束的執法點改成只在某個後端存在，
「所有後端下該違規動作都被擋」這一格必須轉紅。

## 三、約束是有來源、會過期、可撤銷的東西

這是**最重要的一節**，因為它決定這個功能會不會腐爛。

約束會**累積**。每次事故加一條，沒人敢刪，最後上下文裡有一大半是歷史疤痕組織，
而且沒有人知道哪一條還有意義。

所以每條約束必須帶：

| 欄位 | 為什麼必要 |
|---|---|
| **語義 id** | 不能用編號或章節指涉（編號會變） |
| **適用範圍** | 哪些後端／哪些工作型別／哪些判準版本。**「全部」要是一個明確的選擇，不是預設** |
| **強度** | 告知 ／ 強制。強制型必須同時給執法點 |
| **理由與證據參照** | **為什麼有這條**——指向觸發它的事件或失敗。不是散文，是參照 |
| **負控** | 拆掉它會讓哪一格轉紅。**寫不出負控的約束不准進來** |
| **有效期與複審** | 約束會過期（模型換了、原因消失了）。延長要重新證成，不是自動續 |

寫不出負控就進不來這一條，直接把「有些人覺得這樣比較好」擋在門外。

**這剛好與跨工作知識是同一類東西**：有來源、有准入、會過期、可撤銷。
所以：

- **告知型約束** ＝ 知識治理面的一種型別（它就是有溯源的知識，注入上下文）
- **強制型約束** ＝ 閘上的規則，由判準面或執行封套持有

**不需要為它新增一個權威面。**

## 四、注入點的選擇有實質差異，不是風格問題

告知型約束要注入到哪，會決定它**活不活得過上下文壓縮**：

- 注入在**系統提示的追加段**：壓縮之後仍在（因為它不是對話歷史的一部分）
- 注入在**每輪的使用者訊息**：壓縮時可能被摘要掉，但佔用額度較可控

**所以「這條約束必須在第 N 輪之後仍然在場」是一個可測的性質**，
而不是「我們有注入所以應該還在」。

**負控**：觸發一次真實的上下文壓縮，壓縮後執行者仍必須能正確覆述
被宣告為「必須存活」的約束；把注入點從系統追加段改到對話訊息，該格必須轉紅。

## 五、約束從哪裡來——這條閉合了一個迴路

使用者的觸發條件是「**某些情況一直發生**」。

那正是自我維護要偵測的東西：同一類失敗重複出現 N 次 → 產生一個**提案**：
「建議新增一條約束」。而提案要走與其他工作**同一套流程**——
不可信、要被裁定、要有證據。

**系統不得自己直接安裝約束。** 它只能提案。
否則就是被觀測的系統自己決定要被什麼約束——那是把驗收權還給被驗收者。

## 六、出口條件

1. `告知型約束不得出現在保證清單` —— 負控：把一條告知型標成保證
2. `強制型約束在所有後端下都擋得住` —— 負控：只在某個後端執法
3. `寫不出負控的約束不得被接受` —— 負控：拿掉這道檢查
4. `宣告為必須存活的約束，壓縮後仍在場` —— 負控：改注入點
5. `約束過期後不再套用，延長需重新證成` —— 負控：讓它自動續期
6. `系統只能提案約束，不能自行安裝` —— 負控：給它安裝權

## 七、三處更正（對方指出，我接受）

### 更正一：閘是**執法位置**，不是規則的**擁有者**

我原本寫「強制型歸閘」。錯的。那會讓資源面、效果面、知識面**失去自己的政策寫權**。

正確的是：**每一條可執行規則仍由被限制的那個既有權威持有**；
閘只是它被執行的地方。約束是**共用的宣告語言**，不是第五個權威面。

### 更正二：我高估了自己的閘能攔住什麼

我寫「強制型的執法點必須在我們自己的閘上」，並暗示那樣就成立。**不成立。**

在同一個作業系統身分、沒有真正沙箱的前提下，
我們自己的閘**只能攔住必經該閘的操作**。
候選可以直接發系統呼叫、讀 `/proc`、開 socket——那些根本不經過閘。

**所以規則變成**：

> **沒有不可繞過的仲介能力，就不得把一條規則 admit 成「做不到」。**

這代表在第一版的隔離等級下，**能誠實宣告為強制型的規則很少**。
其餘的只能是告知型——而告知型**不是保證**。

這不是把需求打回去，是把它講誠實：
「不允許發生」要真的成立，**得先有能承載它的隔離等級**，
而那個等級要在宣告裡寫出來（宿主做不到時是明確拒絕，不是靜默降級）。

### 更正三：我的壓縮負控測錯了對象

我原本寫的負控是「壓縮後執行者仍必須能正確覆述被宣告為必須存活的約束」。

**那測的是模型表現，不是注入邊界。**

系統能保證的只有：**壓縮之後，實際送出去的輸入仍然逐 byte 帶著那一版文字**。
它保證不了一個不可靠的執行者理解它、記得它、或遵守它。

**改正後的負控**：在請求出口攔截實際 payload，
壓縮邊界之後的每一次請求都必須逐 byte 含有該約束的文字；
把注入點從系統追加段改到對話訊息，該格必須轉紅。

（這是我一直在別處抓別人的同一種錯——**測執行者，而不是測機制**。）
