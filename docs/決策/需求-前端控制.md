# 需求：前端控制面

> 這不是「將來要做一個 UI」的備忘。它是**現在就會改變架構決定**的需求。
> 使用者已界定了範圍：**以讀為主，寫很少且低頻**。

## 一、要看到什麼（讀，主要用途）

| 看什麼 | 為什麼它不是裝飾 |
|---|---|
| **即時的流程做到哪裡** | 這是「工作正在推進」的唯一外部證據。沒有它，人只能等終態，而終態可能幾十分鐘後才到 |
| **系統整體狀況** | 有多少工作在跑、卡在哪、有沒有東西卡住沒人發現 |
| **各執行者後端的剩餘額度** | **這是派工前的閘，不是儀表**——額度耗盡時派工出去，拿回來的是白卷 |

## 一之二、「即時的 nova 流動」——這條是整份需求裡最硬的一條

使用者的原話：**「就像是你畫的流程圖，現在走到那一格」**。

這不是「顯示一個進度百分比」。這是說：**那張流程圖本身就是介面**，
而且上面會**亮著現在在哪一格**。

### 後果一：流程圖必須是**宣告的資料**，不是手畫的文件

手畫的圖會與實作漂移，而漂移之後「現在在哪一格」就**算不出來**——
因為沒有東西把執行時的狀態對應到圖上的節點。

所以：**狀態機必須以資料宣告**，然後
- 執行時只能在宣告過的狀態之間轉移
- 圖是**從宣告生成**的，不是人畫的
- UI 讀同一份宣告來畫，讀當前狀態來高亮

**這順便讓一件已經要做的事變成免費的**：
「每個非終態都有下一邊、每個終態都有路由、無懸空邊、每個狀態可達終態」
這組檢查，在狀態機是宣告資料的前提下是**純函式**。
手畫的圖做不到，宣告的資料兩者都給。

**負控**：讓執行時能轉移到宣告以外的狀態，該格必須轉紅。
**負控**：讓圖與宣告可以各自改動而不互相拘束，該格必須轉紅。

### 後果二：一次「流動」會跨越三個層，所以那是一個**組合視圖**

人看到的一條流程，實際上跨越：
持久工作的狀態 → 目標追求的狀態 → 執行封套的狀態，
而且同一個工作可能同時有多個執行在跑。

所以「現在在哪一格」不是查一張表，是**跨權威的投影**——
這正是讀模型存在的理由，也是它**不能靠向各權威逐一發問**拼出來的理由
（那會變成 N 個長讀交易）。

**負控**：把組合視圖改成向各權威逐一查詢，
「長查詢進行中時寫入仍能在期限內完成」必須轉紅。

### 後果三：高亮需要「狀態改變」而不是「定時重畫」

「即時流動」的體感來自**轉移發生時就看到**。
定時輪詢會讓一個 200ms 的狀態變化看起來像卡住兩秒。

所以變更流送的不是「快照」，是**轉移事件**（從哪一格到哪一格、什麼時候、為什麼）。
UI 用它做動畫，也用它做**回放**——「這個工作當初是怎麼走到這裡的」
與「它現在在哪」是同一份資料的兩種用法。

### 後果四：先前畫的那幾張流程圖，其實是這個 UI 的原型

它們現在是文件。在這個需求下，它們是**規格**：
圖上的每一個節點與每一條邊，都要在狀態機宣告裡找得到對應。
畫得出來但宣告不出來的，表示那張圖在說謊。

## 一之三、更簡單的講法：**這個 UI 就是視覺化的 log**

使用者的原話。這個講法比前面兩節都準，而且它**簡化**了架構，不是增加。

### 後果一：目前在哪一格是**算出來的**，不是另存的

`目前位置 = fold(該實體的事件序列)`。

不需要另外維護一份「當前狀態快照」給 UI 看——那會製造第二份真相，
而且會有「快照與事件不一致」這種只在崩潰時發作的 bug。
**日誌是唯一來源，位置是它的函式。**

### 後果二：**model 不為 view 讓步**

我原本寫「log 變成產品表面，所以事件的門檻提高了」——**因果講反了**。

正確的是：**事件的欄位由領域不變式證成，不由 view 證成。**
view 與 controller 去配合 model，不是反過來。
否則每一次 UI 改動都會對事件 schema 施壓，而那正是「第二份真相」換一種形式出現。

**而幸運的是，view 要的每一個欄位，領域本來就需要**——這不是巧合，
是因為兩者要回答的是**同一個問題：這件事是怎麼發生的**。

| 欄位 | 領域為什麼需要它（與 UI 無關的理由） |
|---|---|
| 從哪一格到哪一格 | 狀態機正確性、回放、無懸空邊的檢查 |
| 什麼時候 | 租約到期、期限判定、因果排序 |
| **為什麼** | 終態必須分得出「東西做錯」與「**裁判壞掉**」，否則兩者都不可核銷也不可恢復 |
| 花了多少 | 資源核銷 |
| 證據參照 | 溯源；而且**參照不是複製**——證據不可覆寫，紀錄只能指過去 |

**所以規則是**：
若哪天 view 想要一個領域不需要的欄位，答案是 **view 自己算，或者不做**，
**不是改 log**。

**可機械執法的形式**：

> **view 必須能由事件流的純函式重建，不需要對領域發出任何額外查詢。**

做不到只有兩種可能：要嘛領域缺了一個它本來就該有的東西（那就補，理由是領域的），
要嘛 view 在要一個它不該要的東西（那就不給）。

**負控**：讓 view 可以對領域發查詢來補齊畫面，
「view 是事件流的純函式」這一格必須轉紅。

### 後果三：回放是免費的

「當初怎麼走到這裡」＝ **渲染日誌的一個前綴**。
與「現在在哪」是同一份資料的兩種用法，不需要第二套機制。

### 後果四：我先前說「儀表板是長讀交易」講得太重 —— 更正

如果 UI 讀的是**領域狀態**（掃描所有工作、聚合統計），那確實是長讀。
但如果 UI 讀的是**append-only 的事件流**，那是**最便宜的讀取模式**：
尾隨（tail-follow）＋ 依游標的區間查詢，兩者都不需要跟寫入者搶同一個交易。

**所以正確的設計約束不是「要有複雜的讀模型」，而是：**

> **事件流必須是可以被獨立尾隨的 append-only 資料，讀者永遠不碰狀態擁有者的交易。**

這比我先前主張的 CQRS 投影**簡單得多**，而且更硬——
因為它把「UI 會不會拖慢系統」從一個要量測的風險，變成一個**拓撲上的不可能**。

**負控**：讓 UI 的讀取路徑經過狀態擁有者的交易，
「長查詢進行中時寫入仍在期限內完成」這一格必須轉紅。

### 後果五：變更流與日誌是**同一個東西**

先前留了一個未決：「變更流與外部效果的 outbox 是否共用實作」。
在「UI ＝ 視覺化 log」的前提下，答案清楚了：

- **事件日誌**：給人看的、可尾隨、可回放 —— UI 讀這個
- **外部效果 outbox**：給外部系統的、有冪等鍵與回執 —— relay 讀這個

兩者**都是耐久的 append-only**，但**消費語意不同**（一個是觀察，一個是動作），
所以**不共用同一張表**，但可以共用同一套「append-only ＋ 游標 ＋ 至少一次」的機制。

## 二、要能改什麼（寫，少量、低頻）

| 改什麼 | 頻率與性質 |
|---|---|
| **各後端的使用比例** | 低頻。會因為供應商的優惠政策改變而調整，但不會一直改 |
| **要求某個後端 CLI 更新** | 低頻。因為會出新模型 |

## 三、這引出三個必須分清楚的領域概念

### 概念一：「我們花了多少」與「對方還剩多少」是兩件事

| | 我們的花費帳 | 供應商的剩餘額度 |
|---|---|---|
| 來源 | 我們自己記的 | **對外部系統的觀測** |
| 權威性 | 權威 | **不權威**——有新鮮度、可能取不到、可能過期 |
| 語意 | 累加，單調 | **會自己重置**（訂閱制的時間窗） |
| 缺席時 | 不可能缺席（缺席＝機制壞了） | **可能缺席**，而且缺席是常態不是異常 |

**把兩者混成一個「額度」欄位，是一個會咬人的錯。**
因為它們的失敗模式相反：花費帳讀不到是**系統故障**；剩餘額度讀不到是**正常情況**，
只是這時派工必須改用保守假設，而不是當作「還有很多」。

**派工前的閘需要兩個輸入**：我們的預算還有沒有 ＋ 對方的額度還有沒有（**含新鮮度**）。

**負控**：把剩餘額度的觀測時間戳拿掉、或讓它缺席時預設為「充足」，
「額度耗盡的後端不得被派工」這一格必須轉紅。

### 概念二：分配政策是有版本的資料，不是設定值

「各後端的使用比例」是一份**會被引用、會被改、且改了之後要能追溯**的東西。

必須決定的兩件事：
1. **進行中的工作要不要重讀政策？** 若要，同一次追求可能前後用不同比例；若不要，
   政策改動只影響新工作。**兩者都可以，但必須明講並可測。**
2. **政策是硬約束還是軟偏好？** 「盡量用 A」與「不准用 B」是不同的東西；
   後者才需要在派工閘上執法。

**負控**：改動政策後，若進行中工作的行為與宣告的語意不符，該格必須轉紅。

### 概念三：更新後端 CLI 會改變能力面，所以它是一件「工作」而不是一個按鈕

按下去會發生的事：外部副作用（跑一個更新程式）、**能力面改變**（出現新模型）、
**指紋改變**（模型清單是配置指紋的一部分）。

所以它必須經過與其他外部副作用**同一套機制**：意圖先落盤、冪等鍵、
明講 at-least-once 或 at-most-once、可查核回執。

而且它要**與進行中的工作互鎖**：一個已釘住某模型的追求，
不能因為 CLI 被更新而**靜默換成別的模型**。
選擇是「更新前必須排空受影響後端的進行中工作」或「進行中工作繼續用舊指紋」，
**但不能是「悄悄變了」**。

**負控**：更新後端後，讓一個進行中的追求繼續跑而指紋已變，該格必須轉紅。

## 四、對架構的後果

### 讀寫必須分離的讀模型

控制面**以讀為主**，而且要看「即時進度」——那是**持續的、可能很長的查詢**。
若唯一的讀取路徑是向擁有該狀態的權威發問，一個儀表板就會跟寫入者搶同一條路。

需要**投影**：由權威的事件流物化出來、供查詢用、**明確標示新鮮度**
（讀到的是哪個版本、落後多久）。

**負控**：拿掉投影、讓控制面直接查權威狀態，
「長查詢進行中時寫入仍能在期限內完成」這一格必須轉紅。

### 單一應用服務邊界

控制面是**第三個**客戶端（與命令列、程式介面同級）。
三個客戶端各有一條進入領域的路 ＝ 三份保證實作，而只有最常用的那份有測試。

**所有客戶端經同一個應用服務邊界**；客戶端只做協定轉換，不持有領域決策。
寫入面很小（兩件事），所以這個邊界的**命令集合是窄的**——這是優勢，不是限制。

**負控**：任何客戶端能繞過該邊界直接改領域狀態，該格必須轉紅。

### 可續訂的變更流

「即時看到流程做到哪裡」需要**可續訂、可從斷點續讀**的變更流。
斷線期間發生的事必須補得回來——**不能是 best-effort 通知**。

它與外部效果的 outbox 是同一類東西（耐久意圖 ＋ 游標 ＋ 至少一次），
但消費者不同。是否共用實作是設計選擇，**兩者都不能靠不耐久的通知**。

### 儲存拓撲：這條需求直接改變裁定

**更正（見一之三）**：先前我寫「儀表板是長讀交易，所以引擎選擇很重要」。
在「UI ＝ 視覺化 log」的前提下，這個論證**變弱了**——
尾隨 append-only 事件流不需要長讀交易。

但**約束仍在，只是形狀變了**：
> 事件流必須是可獨立尾隨的 append-only 資料，**讀者永遠不碰狀態擁有者的交易**。

這反而讓儲存決策更乾淨：狀態擁有者只服務短交易的命令，
UI 完全在另一條路上。**長讀交易的上限仍要有**（維護掃描、匯出、備份都會產生），
但它不再是 UI 造成的。

## 五、明確不在這條需求裡的

- 不要求 sub-second 更新。**秒級足夠。**
- 不要求多使用者、權限分級、遠端存取。**但邊界要留著**：
  應用服務邊界一旦成立，將來加認證是**加一層**，不是改架構。
- 不要求控制面現在就做。**要求的是：現在的決定不會讓它將來做不了。**

## 六、出口條件

這條需求算被滿足，當且僅當下面六格是綠的、且各自的負控會紅：

1. `長查詢進行中，寫入仍在期限內完成`——負控：讓控制面直接查權威狀態
2. `所有客戶端經同一應用服務邊界`——負控：加一條繞過的路徑
3. `變更流斷線後從游標續讀，不漏事件`——負控：改成 best-effort 通知
4. `額度觀測缺席時不得預設為充足`——負控：拿掉新鮮度欄位
5. `政策改動對進行中工作的效果符合宣告的語意`——負控：讓它半途漂移
6. `後端更新後，進行中的追求不得靜默換指紋`——負控：拿掉互鎖
7. `執行時不得轉移到宣告以外的狀態`——負控：允許臨時狀態
8. `圖與狀態機宣告同源`——負控：讓兩者可各自改動
9. `跨三層的組合視圖由事件流的 fold 得到`——負控：改成另存快照
10. `view 由事件流純函式重建，不對領域發查詢`——負控：允許 view 補查詢
11. `事件欄位的理由都能追到領域不變式`——負控：加一個只有 UI 需要的欄位
12. `UI 讀取路徑不經狀態擁有者的交易`——負控：讓它經過
