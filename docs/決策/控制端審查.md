# 控制端審查：我同意什麼、不同意什麼、查證推翻了什麼

> 定案要雙方都同意。到目前為止我大多在轉述另一方的結論，那不算共識。
> 這份是我自己的獨立審查，含**查證**、**數字交叉檢查**、以及**我還不能同意的**。

## 一、我查證後推翻的：「額度觀測能力可能不存在」

對方把這條列為第五高風險，並推導出「零派工 fallback 可能讓付費 backend 全部不可用」。

**一手查證的結果：兩個主要後端都給，而且比它假設的細。**

### Claude Agent SDK

型別裡有 `RateLimitEvent` 與 `RateLimitInfo`，欄位包括：

| 欄位 | 內容 |
|---|---|
| `status` | `allowed` ／ `allowed_warning` ／ `rejected` |
| `utilization` | **已用比例 0.0–1.0** |
| `resets_at` | 窗口重置的 unix 時間 |
| `rate_limit_type` | `five_hour` ／ `seven_day` ／ `seven_day_opus` ／ `seven_day_sonnet` ／ `overage` |
| `overage_status`／`overage_resets_at`／`overage_disabled_reason` | 超額付費是否可用、為什麼不可用 |
| `raw` | 完整原始 dict，含未建模欄位 |

### codex

session 紀錄的 `token_count` 事件帶 `rate_limits`：

```json
"rate_limits": {
  "primary": {"used_percent": 47.0, "window_minutes": 10080, "resets_at": 1788272016},
  "secondary": null,
  "credits": {"has_credits": false, "unlimited": false, "balance": "0"},
  "plan_type": "prolite", "spend_control_reached": null, "rate_limit_reached_type": null
}
```

比 Claude 多給了 **credits 餘額**與 **plan_type**，少給了細分的窗口型別。

### 但這改變了設計，而不只是解除風險

兩家的共同形態是：**額度是執行期間「觀測到」的副產品，不是「查得到」的端點。**

後果一：**觀測有新鮮度**，而新鮮度來自「最後一次收到事件的時間」。

後果二：**冷啟動一定是未知**。從沒跑過的後端，沒有任何觀測。
第一次派工必然在無資訊下進行——這是設計要正面處理的，不是例外。

後果三：**`resets_at` 讓陳舊觀測仍然有用。** 這一點對方的三態模型沒有涵蓋。

所以我主張把 `KNOWN／UNKNOWN／STALE` 三態改成**五態**：

| 態 | 條件 | 派工閘怎麼用 |
|---|---|---|
| `NOT_APPLICABLE` | 這個後端沒有額度概念（本地模型、重播器） | 不參與判斷 |
| `KNOWN` | 有觀測，且在新鮮度窗口內 | 直接用 |
| `INFERRED` | 觀測已陳舊，**但 `now > resets_at`** | **可推定窗口已重置**，視為充足；但要記為推定 |
| `STALE` | 觀測已陳舊，且窗口尚未重置 | 用最後觀測值，並**標記為保守** |
| `UNKNOWN` | 從未觀測過（冷啟動） | 由政策決定：允許一次探測派工，或拒絕 |

`INFERRED` 這一態是實質差異：沒有它，一個跑完 5 小時窗口的後端會永遠停在 `STALE`
而被保守政策擋住，即使它其實已經滿血。

**負控**：把 `INFERRED` 併回 `STALE`，
「窗口重置後陳舊觀測必須升級為可用」這一格必須轉紅。

## 二、數字交叉檢查：三個已定案的數字互相矛盾

對方的 v1 envelope 各自訂了三個數字，但**沒有把它們相乘**：

- 狀態交易負載：持續 **50 tx/s**（壓力上限）
- 保留期：完整 operational events **90 天**
- active state DB 大小：**10 GiB** hard review point

實際乘出來：

| 事件率 | 每筆 150B | 每筆 300B | 每筆 600B |
|---:|---:|---:|---:|
| 0.5 tx/s | 0.54 GiB | 1.09 GiB | 2.17 GiB |
| 1 tx/s | 1.09 GiB | 2.17 GiB | 4.35 GiB |
| **5 tx/s** | 5.43 GiB | **10.86 GiB ← 爆** | **21.73 GiB ← 爆** |
| **50 tx/s** | **54.31 GiB ← 爆** | **108.63 GiB ← 爆** | **217.26 GiB ← 爆** |

**在每筆 300B、持續 5 tx/s 的情況下就已經超過 10 GiB 的複審點**，
而 5 tx/s 只是壓力上限 50 的十分之一。

### 這不是算錯，是缺了一個欄位

envelope 訂了**上限**（50 tx/s），沒有訂**預期穩態值**。
而保留期是對著穩態值算的，不是對著上限算的。缺了那個欄位，
「保留 90 天」與「DB 不超過 10 GiB」之間就沒有可檢查的關係。

### 我的主張：保留期分層**必須同時是儲存分層**

現有的保留期已經分層（raw log 30 天／operational 90 天／verdict 與帳 365 天），
但那是**依資料種類**分的，不是**依住在哪**分的。

正確的形狀是：**熱事件住權威 DB 且保留期短；冷事件歸檔到內容定址儲存**。
權威 DB 只保有「重建尚未完成的工作」所需要的那一段——
那一段的長度由**最長可能的未完成工作**決定，不由稽核保留期決定。

**負控**：讓 90 天的 operational events 留在權威 DB，
「權威 DB 在預期穩態下 90 天內不超過複審點」這一格必須轉紅。

## 三、我同意，但要記下反轉條件

| 決定 | 我為什麼同意 | 什麼情況下我會反對 |

## 四、我還不能同意的兩件事

### 甲：Guard DSL 的可判定性（對方自己排的第一高風險）

宣告式狀態機的 guard，歷史上都會撞到同一面牆：
**第一個真實的 guard 就同時需要期限、預算、子項裁決與故障分類**，
而一旦允許塞任意程式碼，宣告式就破功了。

對方給了測試（重疊 interval 與未覆蓋 enum 值都必須紅），但**沒有給 guard 的表達力邊界**。

**我要先看到：guard 語言能表達什麼、不能表達什麼、以及不能表達時的逃生路徑是什麼**
（是拒絕、還是升級成一個需人裁決的節點）。

在那之前我不能同意「狀態機是純宣告資料」這條——
因為它可能在第一個真 guard 就變成「宣告資料 ＋ 一堆例外」。

### 乙：工具鏈在 CPython 3.14 上的支援，我沒驗成

pytest／hypothesis／mutation runner／xdist 在 3.14 上的可用性，我試了但沒驗成。
**在驗成之前，3.14 是一個未經檢查的選擇**，而它會影響 day-one 的四項能力。

若任一項在 3.14 上不可用，正確處置是**釘 3.13** 而不是放棄那項能力——
因為那四項是所有其他工作的乘數。

## 五、定案的條件（我這一方）

以下全部滿足，我才同意定案：

1. 額度的**五態模型**被接受，或被更好的方案取代
2. envelope 補上**預期穩態事件率**，且保留期與 DB 上限的乘積被重新檢查
3. **保留期分層同時是儲存分層**（或給出不需要如此的理由）
4. Guard 語言的**表達力邊界與逃生路徑**寫出來
5. 工具鏈在選定 Python 版本上的支援**經過實測**

### 工具鏈：我的一手複驗（不是採信它的宣稱）

環境：全新 uv 專案、CPython **3.14.7**、**中文檔名與中文識別字**。

| 項目 | 結果 |
|---|---|
| pytest 9.1.1 ＋ hypothesis ＋ xdist（`-n 2`） | **2 passed** |
| 負控（拿掉守衛） | **轉紅**（`assert False`）——property test 有牙 |
| mutmut 3.7.0 產生 mutant | **成功**，中文識別字沒問題（`x_收窄__mutmut_1/2/3`） |
| mutmut 完整跑完 | **成功**，64.9 mutations/second |

**必要的設定（踩過才知道，寫下來省下一輪）**：

```toml
[tool.pytest.ini_options]
python_files    = ["測_*.py", "test_*.py"]
python_functions = ["測試_*", "test_*"]
python_classes  = ["測_*", "Test*"]
pythonpath      = ["."]

[tool.mutmut]
source_paths = ["受測.py"]   # paths_to_mutate 已棄用
tests_dir    = ["測試"]      # 必須是 list，字串會 TypeError
also_copy    = ["測試"]      # 測試目錄不會自動進 mutants/，不加就 runner returned 5
```

三個坑各花了一次往返：`paths_to_mutate` 已棄用、`tests_dir` **必須是 list**
（原始碼是 `[] + tests_dir`，傳字串直接 `TypeError`）、
以及**測試目錄不會被自動複製進 `mutants/`**，要 `also_copy`。

### 一個副產品發現：mutation 的原始擊殺率不能當分數

我那份三行的受測程式產生 3 個 mutant，殺掉 1 個、**存活 2 個**。
看內容才發現兩個存活的都是**錯誤訊息文字**的突變
（`ValueError(None)` 與 `ValueError("XX子不得超過父XX")`）——
而我的測試只斷言「有丟 `ValueError`」，不管訊息內容。

**對那條不變式而言，它們是等價突變。**

所以：**擊殺率不是可用的指標**，等價突變會混進分母。
可用的是對方堅持的那個形式——**事前指定的突變，必須被指定的測試殺掉**，
而不是掃完之後回填「應殺格」。

我的實測反過來證實了它的設計選擇，而且證實得比論證更硬。
