```
                       │           │                 │
                    是 │           │ 否 ── 帶理由退回 ┘
                       ▼

                 六道閘全綠才 commit
```

**三方都可以提案，也都是審查者**（2026-08-27 控制端修訂）。
第一版寫「fable 提案、claude 與 sol 審查」，控制端改成：
**審查者不只有審查義務，也可以提出修改方案。**

**但提案來源放寬，門檻不能跟著鬆。** 規則對三方對稱：

```
提案者          必須通過的兩個審查者
──────────────────────────────────────
fable    ──▶   claude ＋ sol
claude   ──▶   sol    ＋ fable
sol      ──▶   claude ＋ fable
```

> **一條決議永遠需要「非作者的另外兩方」都 APPROVE。**

**這條規則的理由是這個迴圈自己教的。** 第一輪 sol 退回 R1-06 的理由是 Clark–Wilson ER4：
**認證者不得是能改動受保護對象的主體**（DOI 10.1109/SP.1987.10001）。若對 fable 嚴格套用、
卻讓 claude 或 sol 批准自己的提案，這個閘就有一條專門給提案者走的後門——
那正是 R1-06 被退回的形狀。對自己放寬的規則不是規則。

| 角色 | 能做 | 不能做 |
|---|---|---|
| fable | 提案；審查 claude 與 sol 的提案；用 subagent 或自行搜尋佐證 | **不能批准自己的提案**；不能直接改檔 |
| claude | 提案；審查；查證；寫檔 | **不能批准自己的提案**；不能改別人的提案內容（要改就退回或另提一條） |
| sol | 提案；審查；提供原意與地基出處 | **不能批准自己的提案**；不能宣告接受產品；不能改已准入的 ClaimSpec |

**提案者可以善用 subagent 或自行搜尋答案**——被退回的常見原因是地基引不出來或判準太弱，
那兩件事都是查得到的，不必靠猜。

任一審查者 REJECT 就退回作者，**必須附理由碼**。無理由的 REJECT 不算 REJECT。

**這不推翻既有的接受權。** 唯一的產品接受權仍在 ClaimSpec 閘（見 CLAUDE.md）。
本迴圈決定的是**計畫文字**要怎麼改，不是「哪個 task 算完成」。

## 決議編號與狀態

編號 `R<輪次>-<序號>`，例如 `R1-03`。**編號後標作者**：`R2-01(fable)`、`R2-07(claude)`、
`R2-09(sol)`——作者是誰決定了要哪兩方批准，看不出作者就判不出票數夠不夠。
狀態封閉為五種：

| 狀態 | 意思 |
|---|---|
| `PROPOSED` | fable 提出，尚未有人審 |
| `CLAUDE_OK` / `SOL_OK` / `FABLE_OK` | 單邊通過，等另一邊 |
| `APPROVED` | 兩邊都過，可以寫進計畫 |
| `APPLIED` | 已寫進 `docs/計畫/` 且六道閘綠 |
| `REJECTED` | 至少一方退回，**理由必填** |

## 每條決議必須填的欄位

fable 的提案不符這個形狀就直接退回，不進審查：

1. **改什麼**：哪一份計畫、哪個 task 附近、Create／Modify 哪些檔（完整路徑）
2. **為什麼**：不改的後果——具體到「哪一條保證會在帳面上維持綠色」
3. **地基**：官方出處（URL／標準編號）＋權威出處（DOI／arXiv）。
   **引不出來就寫「無地基，這是 nova 的拆解決定」**，不准含糊
4. **加蓋**：nova 多出來的那一條拒絕是什麼？有沒有改到地基的介面？
   （合法動作只有兩種，見 CLAUDE.md 最高原則第 4 條）
5. **固定負控**：control_id、faulty_subject、`must_fail_exactly` 要哪幾條 predicate，
   外加防恆真格
6. **不變式檢查**：會不會撞到 I1–I11（一個 task ≤2 條 claim、≤10 檔、恰好 1 個 commit 步、
   要有 `**ClaimSpec落點:**` 行、要有 `Expected:` 的先紅步）

## 審查者的否決理由（封閉列舉，避免「感覺不對」）

- `NO_FOUNDATION`：宣稱有地基但引不出出處
- `FOUNDATION_MISREAD`：出處存在但不支撐這句話的強度
- `WEAKENS_GUARANTEE`：讓既有保證變弱，即使表面結果一樣
- `CHANGES_INTERFACE`：加蓋改到了地基的介面（那叫分叉不叫加蓋）
- `DOMAIN_LEAK`：把具體產品領域寫進了規格
- `NOT_TESTABLE`：寫不成會 fail 的測試，卻被當成機制
- `INVARIANT_BREAK`：撞到 I1–I11
- `SCOPE_TOO_BIG`：口徑大到一次做不完（CLAUDE.md 明列的不可機械化判斷）
- `ALREADY_TRUE`：repo 現況已經如此，這條是空的

### 定案的定義（不可協商，否則這件事永遠做不完）

> **一份計畫定案 ＝ 它的每個 task 都滿足兩條：**
> **① 固定負控殺得到它宣稱的那個性質；**
> **② 沒有引用不存在的指涉物。**

這兩條正是前八輪反覆踩到的兩個形狀：

| 形狀 | 發作紀錄 |
|---|---|
| ①**驗到一層就以為驗到底** | R2-01 欄位存在≠可執法／R3-03 引用 claim≠負控殺得到／R7-01 綁 artifact≠綁交付內容／R8-01 單成員 enum 的負控不可達 |
| ②**比較一個不存在的東西** | R1-01 identity 比字串／R7-01 `prompt_family_ref` 指涉物命中 0 |

**四次與兩次。** 定案判準不是憑空立的，是從實際發作歸納的。

### 節奏（2026-08-28 控制端裁定，成本考量）

claude 與 fable 都是 Claude session，兩隻同時跑等於雙倍額度。裁定不是砍掉一個審查者
——**帳本記錄 8 輪裡 6 次同形缺陷有 5 次是單方抓到的**，砍掉就等於讓那類缺陷寫進計畫，
而它們的共同特徵是**帳面全綠**。裁定的是砍成本：

- **claude 的散文砍掉**：帳本一輪數行、PR 內文一段、給 fable 的訊息只寫
  「哪條過、哪條退、理由碼、怎麼改」。判斷照做。
  （成本主要在寫字不在判斷——驗 diff 與跑閘只要幾秒。）
- **一輪審三到四份計畫**，不是一份一輪。15 份降到 4–5 輪。

## 第十三輪（2026-08-28）：覆蓋審第五批 16／17／18／01B／06B——審到我們自己

28 格，**23 過 5 不過**。**計畫 18 七格全過零決議**（第五份滿分）。決議 4 條，**3 過 1 退**。

### 06B 首次被審，抓到的是三方自己

06B 是 R2-06 開的：**fable 提、claude 與 sol 兩票通過、claude 寫進 repo**。
它的 spec 明文宣告四個門檻，**其中兩個零殺手**——`max_interval_width`（精度門檻）
與 `minimum_absolute_quality`（絕對下限）。

claude 查證屬實：現有八格負控殺的是 `token_ratio_upper_bound_exceeds_max`（決策門檻）
與 `quality_lower_bound_below_margin`（相對 margin），**那兩個門檻一格都沒有**。

**而那兩個門檻是 claude 親手寫進計畫本文的**——
「區間要窄到能做決定」「只有相對非劣性不夠，baseline 0.20、treatment 0.20 統計上非劣
但沒有使用價值」——**寫得出理由、配不出牙齒**。

**這是「驗到一層就以為驗到底」的第六次，也是第一次源頭是我們三個而不是某一方。**
它說明覆蓋審不是走過場：**同一批人寫的東西，換一種問法就會現形**。

### claude 的兩個疑問都成立

**① `max_interval_width` 的 fixture 怎麼造才可信？**
sol 給了 fixture 契約：**必須提供原始成對 observations，由釘版分析器實算區間與決策，
不得直接塞入人工 interval**——塞人工區間測的是 fixture 不是分析器。
可以把門檻設得比該資料自然產生的區間更窄，**無須偽造區間**。

**② `seed-dropped` 能不能真的紅？** → **不能，R13-03 因此退回**。
sol：**seed 的保證是「請求欄位被忠實交付」，不是「輸出因此改變」**。
後端本來就決定性時，丟掉 seed 完全可能不紅。
正解是 seed-sensitive transport spy，直接記錄 adapter 實際交付的 canonical request，
**明確禁止用輸出是否相同作 oracle**——否則又把 `SEEDED_REQUEST` 與 repeatability 混成一格
（那正是 R2-03／R3-03 兩次踩過的形狀）。

### 並排法第二次見效

16／17 並排（通用 CLI vs 本地模型）抓到：16 **零 adapter 級 cancel 負控**
（14／15／17 都有）、16 的 sealed 投影**只有 registry 面沒有 bytes 面**；
17 的 Global Constraints 明文「禁止轉用任何雲端 provider」——**宣告有、殺手無**。

sol 的兩個寫入條件都指向同一件事：**負控自己不能是假的**——
「孫程序不存在」要用程序身分或 handle 驗證，**不得只用會被重用的 PID**；
「不得轉雲端」那格要用 connector spy 或網路 deny fixture，
**負控本身去打雲端就是它要禁止的那件事**。

### 執法器的回歸負控接上閘了——六道變七道

R11 sol 要求的「長期牙齒」落地：`docs/計畫複驗自測/撞號/` fixture ＋ `--自測` 模式。
claude 兩個方向都驗：

```
fixture 帶真撞號     → 自測 ✓，exit 0
fixture 改成序號正確 → 自測 ✗「預期字串沒出現」，exit 1
```

**它偵測的是「執法器不再抓那個缺陷」，不是只跑一次就算。**

fable 沒有自行接進閘清單，說那是控制端的權限邊界。**sol 裁定要現在就接**：

> **未接入前，它是可用的診斷工具，不是持續保護機制。**

claude 接上後，**既有負控立刻抓到它自己**：`test_CI_跑的是同一組閘` 紅了

補上 `gates.yml` 後七道全綠。

### R12-02：否定性產品宣稱要改成 fail-closed 宣告

fable 誠實標了「沒 probe 真 binary」。**sol 判這個誠實邊界原樣不夠**：

> 「沒 probe」可以誠實揭露證據不足，**卻不能同時斷言產品不存在該能力**。

所以「Codex CLI 無 pre-tool callback」必須改成
**「本 v1 adapter 沒有已准入、可驗證的 `PRE_TOOL_DECISION` 機制，因此 fail-closed 宣告 unsupported」**。
理由逐字：**官方文件沒有記載某介面，不能證明該介面不存在**；
`--ask-for-approval never` 只證明核准策略設定，不證明沒有 callback。

**重量是 exit 2**，fail-closed 本來就在——拿到的是 `tail` 的退出碼。
**zsh 管道退出碼，這是同一天第四次踩。**

### 兩條「名字沒有機制」的收縮

- **R11-04**：`EXTERNAL_ATTESTED` 是零 verifier 零負控的 enum 名字（claude 查證：
  全計畫 `AttestationVerifier` 命中 0）→ 移出 v1 enum。
  sol 加重入條件的**原子性要求**：enum 成員、verifier port、production/fake contract、
  不可驗 attestation 負控與正控**必須在同一個變更加入**。
- **R11-05**：刪 import-linter 改用既有 `架構/檢查後端依賴.py`（03 T8）。
  fable 的理由 sol 接受：同一保證兩套執法器會分家，且

  ——較弱的第二套工具等於給動態 import 開繞過道。

### R11-00 的寫入條件：改名不算修

sol 釘死：**production `VerifiedRevealApproval` 只能由 verifier 的成功結果取得**，
否則「只是把 `approval_envelope` 改個名字」。新增負控 `forged-verified-wrapper`——
**直接手造 wrapper 不得取得 reveal**。`validity` 必須是 discriminated union
`EXPIRES_AT | ONE_SHOT`，**不得是數個可同時缺席的 optional 欄位**。
one-shot 消費要與 `CaseBurned` 在**同一個 state-owner transaction** 落盤。

### 兩個審查者各自抓到什麼（這一節是這個迴圈存在的理由）

**claude 獨立抓到、sol 也抓到的**（收斂）：R1-08 的 `pyproject.toml`。
nova 的 `dependencies = []`——零個第三方 runtime 依賴。提案要「釘版外部統計套件」卻沒列
dependency 修改，等於把一個架構決定藏在 task 散文裡。sol 補了一句 claude 沒想到的：
`allow_io=false` 本身不衝突（純計算套件可以在無 I/O 的權威函式裡跑），
**真正的問題是依賴與 supply-chain 身分完全沒進 Files 與 fingerprint**。

**sol 抓到、claude 漏掉的四個**（覆蓋盲區）：

1. **R1-02**：claude 只看到引文問題，沒看到 `DECLARED_NEGLIGIBLE + justification_ref`
   是**散文不是機械判定**——正是「只以文件形式存在的規範等於不存在」。
2. **R1-05**：N 次逐 byte 相同的 probe 只證成「觀測到重複性」，不證成一個叫
   `SEEDED_OUTPUT_DETERMINISM` 的能力；第 N+1 次仍可能變。
3. **R1-06**：`certified_by != executed_by` **只能證明兩個字串不同**，同一主體填兩個 id 就綠；
   `identity_source` 可偽造時只標記卻仍放行，違反「不得靜默降級」。
   另指出 `executed_by` 語意不清——Clark–Wilson 要分離的是認證者與**能改動受保護實體**的主體，
   不是禁止獨立 CI 執行檢查。
4. **R1-07**：提案宣稱 append-only 跨 run 的帳，但 Create 清單**沒有任何持久 owner**，
   而 `nova/權威/判準/揭露帳本.py` 受 `allow_io=false` 本身就不能持久化——
   **程序重啟即可洗掉 cap**，而負控只測同一程序內的第 cap+1 次。

**claude 抓到、sol 未提的**：R1-02 引 Goldstein & Spiegelhalter 的 DOI
`10.1111/j.1467-985X.1996.tb00086.x` 與研究員實際驗到的 `10.2307/2983325` 不符。
sol 複驗後確認後者可驗、前者無法驗證為該文的有效 DOI，併入 R1-02 的退回理由。

**方法論結論**：兩個審查者的價值不是互相背書，是**覆蓋各自的盲區**。
八條裡有四條是單方抓到的；若只有一個審查者，那四條會帶著缺陷寫進計畫。
這也是為什麼送審時不先揭露自己的票——證據可以共享，結論不能，否則第二個審查者不獨立。
