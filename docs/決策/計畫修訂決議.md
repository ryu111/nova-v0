# 計畫修訂決議帳本

2026-08-27 控制端裁定的三方迴圈。**這份是帳本，不是討論記錄**——
每一條決議的狀態必須看得出來，討論過程進各自的回覆檔。

## 協定

```
        ┌──────────────────────────────────────────────┐
        │                                              │
        ▼                                              │
   ┌─────────┐    提案     ┌──────────┐              │
   │  fable  │────────────▶│  決議池   │              │
   │ （提案者）│             └────┬─────┘              │
   └─────────┘                  │                    │
                        ┌───────┴────────┐           │
                        ▼                ▼           │
                  ┌──────────┐    ┌──────────┐      │
                  │  claude  │    │   sol    │      │
                  │ （審查者）│    │ （審查者）│      │
                  └────┬─────┘    └────┬─────┘      │
                       │               │             │
                       └───────┬───────┘             │
                               ▼                     │
                    兩邊都 APPROVE？                  │
                       │           │                 │
                    是 │           │ 否 ── 帶理由退回 ┘
                       ▼
                 寫進 docs/計畫/
                 六道閘全綠才 commit
```

**三方都可以提案，也都是審查者**（2026-08-27 控制端修訂）。
第一版寫「fable 提案、claude 與 sol 審查」，控制端改成：
**審查者不只有審查義務，也可以提出修改方案。**

**但提案來源放寬，門檻不能跟著鬆。** 規則對三方對稱：

```
提案者          必須通過的兩個審查者
──────────────────────────────────────
fable    ──▶   claude ＋ sol
claude   ──▶   sol    ＋ fable
sol      ──▶   claude ＋ fable
```

> **一條決議永遠需要「非作者的另外兩方」都 APPROVE。**

**這條規則的理由是這個迴圈自己教的。** 第一輪 sol 退回 R1-06 的理由是 Clark–Wilson ER4：
**認證者不得是能改動受保護對象的主體**（DOI 10.1109/SP.1987.10001）。若對 fable 嚴格套用、
卻讓 claude 或 sol 批准自己的提案，這個閘就有一條專門給提案者走的後門——
那正是 R1-06 被退回的形狀。對自己放寬的規則不是規則。

| 角色 | 能做 | 不能做 |
|---|---|---|
| fable | 提案；審查 claude 與 sol 的提案；用 subagent 或自行搜尋佐證 | **不能批准自己的提案**；不能直接改檔 |
| claude | 提案；審查；查證；寫檔 | **不能批准自己的提案**；不能改別人的提案內容（要改就退回或另提一條） |
| sol | 提案；審查；提供原意與地基出處 | **不能批准自己的提案**；不能宣告接受產品；不能改已准入的 ClaimSpec |

**提案者可以善用 subagent 或自行搜尋答案**——被退回的常見原因是地基引不出來或判準太弱，
那兩件事都是查得到的，不必靠猜。

任一審查者 REJECT 就退回作者，**必須附理由碼**。無理由的 REJECT 不算 REJECT。

**這不推翻既有的接受權。** 唯一的產品接受權仍在 ClaimSpec 閘（見 CLAUDE.md）。
本迴圈決定的是**計畫文字**要怎麼改，不是「哪個 task 算完成」。

## 決議編號與狀態

編號 `R<輪次>-<序號>`，例如 `R1-03`。**編號後標作者**：`R2-01(fable)`、`R2-07(claude)`、
`R2-09(sol)`——作者是誰決定了要哪兩方批准，看不出作者就判不出票數夠不夠。
狀態封閉為五種：

| 狀態 | 意思 |
|---|---|
| `PROPOSED` | fable 提出，尚未有人審 |
| `CLAUDE_OK` / `SOL_OK` / `FABLE_OK` | 單邊通過，等另一邊 |
| `APPROVED` | 兩邊都過，可以寫進計畫 |
| `APPLIED` | 已寫進 `docs/計畫/` 且六道閘綠 |
| `REJECTED` | 至少一方退回，**理由必填** |

## 每條決議必須填的欄位

fable 的提案不符這個形狀就直接退回，不進審查：

1. **改什麼**：哪一份計畫、哪個 task 附近、Create／Modify 哪些檔（完整路徑）
2. **為什麼**：不改的後果——具體到「哪一條保證會在帳面上維持綠色」
3. **地基**：官方出處（URL／標準編號）＋權威出處（DOI／arXiv）。
   **引不出來就寫「無地基，這是 nova 的拆解決定」**，不准含糊
4. **加蓋**：nova 多出來的那一條拒絕是什麼？有沒有改到地基的介面？
   （合法動作只有兩種，見 CLAUDE.md 最高原則第 4 條）
5. **固定負控**：control_id、faulty_subject、`must_fail_exactly` 要哪幾條 predicate，
   外加防恆真格
6. **不變式檢查**：會不會撞到 I1–I11（一個 task ≤2 條 claim、≤10 檔、恰好 1 個 commit 步、
   要有 `**ClaimSpec落點:**` 行、要有 `Expected:` 的先紅步）

## 審查者的否決理由（封閉列舉，避免「感覺不對」）

- `NO_FOUNDATION`：宣稱有地基但引不出出處
- `FOUNDATION_MISREAD`：出處存在但不支撐這句話的強度
- `WEAKENS_GUARANTEE`：讓既有保證變弱，即使表面結果一樣
- `CHANGES_INTERFACE`：加蓋改到了地基的介面（那叫分叉不叫加蓋）
- `DOMAIN_LEAK`：把具體產品領域寫進了規格
- `NOT_TESTABLE`：寫不成會 fail 的測試，卻被當成機制
- `INVARIANT_BREAK`：撞到 I1–I11
- `SCOPE_TOO_BIG`：口徑大到一次做不完（CLAUDE.md 明列的不可機械化判斷）
- `ALREADY_TRUE`：repo 現況已經如此，這條是空的

### 上一輪的空轉，這一輪用機制解掉

R7 的兩條都接在 08 檔尾，一條被退回就整輪套不上。
fable 這次交**三份獨立 diff**（AB／只A／只B），三個 mock 各自驗過。
R8-01 退回時，claude 直接套「只 B」——**不需要重切，沒有空轉**。

### claude 問對了，sol 證實並補了一刀

claude 問：`PromptAssemblyPolicy` v1 是**單成員 enum**，那
`same-family-different-assembly-policy` 這格負控在 v1 拿什麼當第二個政策？
會不會是恆真的？

sol：**「你的疑問成立：這格目前是不可達、近似恆真的保證。」**
並逐一排除所有假出路：用未知 enum 只證明 closed vocabulary；偽造 digest 只證明 mismatch；
改 `semantic_id`／`revision` **不能拿 metadata 差異冒充政策差異**；
改同一 enum 背後的程式碼是 implementation drift，該由 compiler digest 抓。

**它另外抓到一個反向破壞**：若政策的 canonical bytes 含 `semantic_id`／`revision`，
兩份語意相同、只有 id 不同的政策會得到不同 digest，**錯判 `NEW_PURSUIT_REQUIRED`**
——那會反過來破壞 R1-01 立的規則。

出路採**選項 B（誠實降級）**：保留 `prompt_assembly_policy_ref` 進 identity、保留單成員與
未知政策 fail-closed，但**刪掉目前無合法第二主體的兩格負控**，改驗
`assembly_policy_must_resolve`／`assembly_policy_digest_content_bound`／
`assembly_policy_vocabulary_closed`，並明寫「在第二個 policy kind 被准入前，
不宣稱『不同合法政策必切 Pursuit』已經驗過」。

**再加一條未來的硬前置**：新增第二個 `resolution_rule_kind` 的**同一變更**，
必須同時新增那兩格負控的第一組**可達**正負控；缺少就不得擴 enum。

### fable 這輪的三件事

①**三份 diff** 解掉相依性；
②R7-02 已兩票通過，但本版含實質內容變更，它**仍以 PROPOSED 送**而不是當已通過直接套；
③自己加了一格沒人要求的負控 `vector-releaked-to-executor`
——把 sol 那句「vector 不得重新洩漏給 executor」機械化（傷口→負控第四例）。

sol 的寫入條件補強了那格：**必須檢查完整 outbound manifest**，
不只 `RetryRequested` 的直接欄位，否則 clause detail 可以經其他 context segment 繞回執行者。

這算不算把 R1-01 的保證做了一半？

sol 判**算**，並把層級差異寫成公式：

```
family_digest          = PromptFamily 宣告內容與順序的身分
effective_prompt_digest = PromptFamily ＋ 組裝政策 ＋ 實際解析出的有效段落
```

> **目前只完成第一層，卻接到要求第二層的比較器。**

**它否決了「等計畫 12 補」這條路**：`prompt_assembly_policy_ref` **必須現在就進

### sol 給的 namespace 分工（新規則）

- `prompt.family.*`：家族 artifact、解析、內容身分
- `prompt.plan.*`：有效組裝與 semantic prefix
- `execution.prompt.*`：adapter 實際 outbound mapping

### R7-02 通過，但事件模型要分家

sol 的寫入條件：耗盡**不能只變成 retry payload 裡的一個字串**，事件必須分成
`FeedbackAccepted(feedback_ref)` 與 `FeedbackUnavailable(reason=DISCLOSURE_BUDGET_EXHAUSTED)`；
**`FeedbackAccepted` 的 `feedback_ref` 永遠不可 nullable**。

**不加第三支政策**：「降頻續跑」不是第三種終局語意，是帶參數的新排程政策，

對 deadline 與 budget 的影響——**現在塞進 enum 只會得到一個沒有完整狀態機語意的名字**。

## 第五、六輪（2026-08-28）：同一條循環抓了兩次才乾淨

| 決議 | claude | sol | 結果 | 理由碼 |

| R5-01(fable) detached receipt | REJECT | REJECT | REJECTED | `INVARIANT_BREAK` |
| R6-01(fable) 單向引用 | APPROVE | APPROVE | **APPLIED** | — |

### 循環第一次沒被消除，只是換了一層

R4-03 的循環是 **receipt bytes** 寫進被授權的 tree。R5 把 bytes 移出去了，
claude 驗到「循環源頭的檔案歸零、`detached` 22 處命中」就投了通過。

sol 逐字：

> receipt 本體雖已 detached，但 manifest entry 又新增 `receipt_digest`／`receipt_locator`，
> 同時 receipt 綁定 proposed manifest digest 與 exact head SHA；把這兩欄寫入 manifest
> 仍會改變 manifest digest 與 head，**原本的自我參照循環只是從 receipt bytes 換成 receipt metadata**。

### 這一輪最該記住的一句話

> **我重跑了鏡像閘：I1–I11 全綠。機械結構成立，但沒有抓到這個協定循環。**

**閘綠不等於沒有循環。執法器驗的是結構，不是協定語意。**
三個審查者在 R5 都因為閘綠而增加了信心，而那份信心在這條上是錯的。
這句話已由 fable 寫進計畫 01 Task 17 的本文——**三方共同的教訓入了正典**。

### R6 的解法：單向引用

> **授權證據與被授權內容之間只允許單向引用。**
> receipt 引用 tree（綁 head SHA 與 manifest digest），**tree 對 receipt 零引用**，
> 查找靠可推導的 key `(repository_identity, head_sha, proposed_manifest_digest)`，
> 事後記錄住在外部 audit projection。

fable 另外**誠實刪了一格負控**：`reused-nonce` 絆線移除——nonce 不再出現在 tree 裡，
那格失去主體，唯一性完全由外部 ledger 承載。**它明講這是誠實刪格不是漏。**

### claude 提的疑點與 sol 的釘死

claude 問：Task 18 仍把四個角色欄寫進 manifest，`admission_decided_by` 要與 receipt 的
attested actor 相符——**這個「相符」是誰跟誰比？** 若用 manifest 欄位去挑要查哪張 receipt，
那又是 tree → receipt 的引用。

sol 判推論成立（角色是簽發前已知的內容，不構成循環），但要求方向**釘死在 task 文字裡**：
查找**只能**用公開公式，過程**不得讀取**角色 id／locator／nonce／signer identity；
驗簽之後才從 receipt 取 `attested_actor`；比較方向固定為
`declared == verified`。新增負控 `manifest-actor-selects-receipt` →
`receipt_selected_only_by_derived_lookup_key`。

它另補一條 schema 分辨：**receipt signer 是 workflow issuer，`attested_actor` 是經 trust root
的 actor-extraction rule 從平台核准證據解析出的裁定者——兩者是不同角色，不得混為一欄。**

### sol 對 fable 選型理由的糾正（R5）

fable 選 CAS 而非 merge queue，理由是「CAS 可機械測試」。sol 同意結論但不接受理由：
**「可機械測試」只是必要條件之一，不足以單獨證成選型。** 實質理由是 nonce 的 single-use
是領域不變式、不該綁死 GitHub 方案能力。並補一刀：**假 ledger 第二次 CAS 失敗只證明
port consumer 寫對，不證明 production ledger 真有原子性**——所以要 fake ledger 當日常
contract test、real ledger 當 Authority Step 的 live conformance gate。

### 正控分兩級（沿用至今的規則）

**本地正控**（測試 signer ＋ fake ledger）只證明 checker 不是恆假閘；
**權威正控**是 Authority Step 對真 signer、真 ledger、固定 head 跑完整七步。
Task 17 逐字寫入：**本地 fixture 綠只代表實作可進入 Authority Step；
真 signer、真 ledger 與真 required workflow 正控未綠前，Task 17 不得完成，
任何新 admission 維持 fail-closed。**

**寫入後 head SHA 必然改變**——所以那張 receipt 不是綁錯 head，就是形成不可解的自我雜湊循環。

sol 另抓到第二個競態：nonce 若只靠 repo manifest history 檢查，
**兩個並行 PR 可以在彼此尚未合併時用同一個 nonce，各自通過**——那不是 single-use。

出路：receipt 必須是 **detached**，存在候選不可寫的外部 attestation store，
repo 內只留 digest 或 locator；nonce 必須在外部權威處**原子消費**
（protected ledger 的 compare-and-set，或 merge queue 序列化後對最新 base 重驗）。
創世改兩階段：Authority Step A 在外部信任域建根 → repo PR 只提交 mirror →
Authority Step B 對固定 head 簽發 detached receipt。

### R4-01：sol 不要求降名，但條件很硬

fable 在 sol 的二選一裡選了機械證明而非誠實降名。sol 接受，理由是限縮語意成立：
`EXACT_ARTIFACT_FUNCTION` 現在表示的是「對 pinned manifest 與 pinned implementation 的
**完整、非抽樣**函式結果」，不是「對現實世界的絕對真值」。

**但它指出 claude 問錯了重點**：三條 mutation 確實不能證明「實作沒有漏」——
**正面證據是 `coverage_evidence_ref`，mutation 的作用是證明那道 coverage 閘不是擺設。
兩者缺一不可。** 並補一句警告：
**若 `coverage_evidence_ref` 最後只被驗「存在」，實作就不合本次核准內容，必須退回。**

### R4-02：遷移債可以綁進來，但理由不是先例

fable 援引「claude 第一輪給 08 T1/T2/T5 補落點」當先例。sol **不接受先例當理由**，
改給四個實質理由：該 id 原本就由同一 Task 7 宣告；新增落點行後 task 必須完整列出它宣告的
所有 claim；補的是**同一 task 既有保證的缺失 artifact**，不是夾帶另一個子系統；
口徑仍在上限內。

`wrong-claim-ref` 判**有牙**，但寫入時**不得實作成 claim-id 白名單**——
必須由 capability policy 宣告所需 predicate set、resolver 從 `ProtectedClaimClosure` 解析
exact revision/digest、比對**已准入 predicate set 是否涵蓋**。
如此它問的不是「名字對不對」，而是「這份證據是否真的驗了那三個 predicate」。

### fable 自己補了一格沒人要求的負控

`wrong-claim-ref`——把 `PURE_REPLAYER` 的 evidence 指到 `replayer-contract-parity`

**claude 獨立抓到、sol 也抓到的**（收斂）：R1-08 的 `pyproject.toml`。
nova 的 `dependencies = []`——零個第三方 runtime 依賴。提案要「釘版外部統計套件」卻沒列
dependency 修改，等於把一個架構決定藏在 task 散文裡。sol 補了一句 claude 沒想到的：
`allow_io=false` 本身不衝突（純計算套件可以在無 I/O 的權威函式裡跑），
**真正的問題是依賴與 supply-chain 身分完全沒進 Files 與 fingerprint**。

**sol 抓到、claude 漏掉的四個**（覆蓋盲區）：

1. **R1-02**：claude 只看到引文問題，沒看到 `DECLARED_NEGLIGIBLE + justification_ref`

2. **R1-05**：N 次逐 byte 相同的 probe 只證成「觀測到重複性」，不證成一個叫
   `SEEDED_OUTPUT_DETERMINISM` 的能力；第 N+1 次仍可能變。
3. **R1-06**：`certified_by != executed_by` **只能證明兩個字串不同**，同一主體填兩個 id 就綠；
   `identity_source` 可偽造時只標記卻仍放行，違反「不得靜默降級」。
   另指出 `executed_by` 語意不清——Clark–Wilson 要分離的是認證者與**能改動受保護實體**的主體，
   不是禁止獨立 CI 執行檢查。
4. **R1-07**：提案宣稱 append-only 跨 run 的帳，但 Create 清單**沒有任何持久 owner**，
   而 `nova/權威/判準/揭露帳本.py` 受 `allow_io=false` 本身就不能持久化——
   **程序重啟即可洗掉 cap**，而負控只測同一程序內的第 cap+1 次。

`10.1111/j.1467-985X.1996.tb00086.x` 與研究員實際驗到的 `10.2307/2983325` 不符。
sol 複驗後確認後者可驗、前者無法驗證為該文的有效 DOI，併入 R1-02 的退回理由。

**方法論結論**：兩個審查者的價值不是互相背書，是**覆蓋各自的盲區**。
八條裡有四條是單方抓到的；若只有一個審查者，那四條會帶著缺陷寫進計畫。
這也是為什麼送審時不先揭露自己的票——證據可以共享，結論不能，否則第二個審查者不獨立。
