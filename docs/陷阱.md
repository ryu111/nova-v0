# 陷阱佇列（實測踩過的坑）

> **這份是舊 nova（`~/nova.bak-*`）的實測經驗，不是新系統的現況。**
> 裡面提到的路徑（`tests/驗收/`、`nova 收官` 等）在新樹**不存在**——保留它們是
> 因為坑本身還會再發生，不是因為那些路徑還在。每條坑的預設命運是變成新系統裡
> 一條會 fail 的測試；轉化完就把那條從佇列刪掉。

> **這是待轉化的佇列，不是永久檔案，也不進常駐 context。**
> CLAUDE.md 只放永久規則；坑是 feedback，預設命運是變成機制。
>
> **轉化流程**：能寫成會 fail 的測試就去寫 → 把**發作情況與代價**搬進那格的 docstring
> → 本檔那條刪掉。文字與機制並存只會分岔。
>
> **刪除的前提有二、缺一不可**：①機制存在 ②負控證明它抓得到那個壞。
> 且機制要**涵蓋該陷阱的所有發作面**——跨專案的坑只在 nova 有檢查器就不能刪，改註明範圍。
> 只刪文字不補機制＝本 repo 最糟的形式（某份規範宣稱「由 hook 自動把關」，而那些 hook 從未存在過）。
>
> **評估後決定不做的也要留下判斷理由與量測數字**，否則下一個人會再試一次同樣的死路。
> 實例：`pytest.raises` 的 `match=` 假滿足，靜態版量過兩輪（60 處 → 收窄到 47 處）
> 全是誤報，真前提「訊息裡真的含那條路徑」是執行期性質——見
> `tests/驗收/測_陷阱機械化.py` 檔內的評估紀錄與可行的執行期做法。
>
> 每一條都付過真代價，**發作情況與代價的引註不可刪**——那是它存在的唯一憑據。
> 跨專案的坑寫進 `~/.claude/rules/陷阱.md`；nova 專屬的寫這裡。
>
> **本檔只收「可機械化但還沒做」的。** 判定為**完全不可機械化**的不在這裡——
> 那些永遠不會離開，所以直接住進 CLAUDE.md 當永久規則（見該檔「不可機械化的判斷」節）。

### `GIT_DIR` 指向**連結工作樹** ＋ `git init` 會翻掉共用 config 的 bare（2026-08-28）

**條件是一個合取，少一半就寫不出有效的負控。** nova-ea 的對照實驗（各三跑）：

| 條件 | `core.bare` |
|---|---|
| `GIT_DIR` = **連結工作樹**的 git dir ＋ `git init` | **true** |
| `GIT_DIR` = 主 `.git` ＋ `git init` | false |
| cwd 在工作樹、**不設** env ＋ `git init` | false |
| `GIT_DIR` = 連結工作樹 ＋ **只跑 `git config`** | false（但身分照樣被污染） |

**發作**：agy 在 `實作/01-T11` 這個連結工作樹裡 commit → 鉤子把 `GIT_DIR` 設成
`.git/worktrees/T11` → `造臨時倉` 的 `git init -q` 繼承它 → 主 repo 的 `core.bare`
被翻成 true，`git status` 從此回 `fatal: this operation must be run in a work tree`。

**代價：我第一版負控是恆真格。** 我寫 `assert "bare = false"` 時，誘餌是**普通 repo**、
`GIT_DIR` 指向 `.git`——照上表第二列，那個條件下 bare 本來就不會翻，
那句 assert **永遠綠**。它看起來守住了 bare，實際守不住，而且沒有任何格會告訴我。
被 nova-ea 指出來後才發現：拿掉隔離時先紅的是 hook 那句，bare 那句從沒被行使過。

**第二個代價**：改成連結工作樹之後，隔離失效時 `git init` 先翻 bare、
後面的 `git config` 才炸成 exit 128，於是測試紅在 `CalledProcessError`
而不是紅在斷言——**紅在別的地方等於沒驗到**。要 `contextlib.suppress` 掉那個例外，
讓斷言成為唯一的 oracle。

**機制**：`架構/test_工程規範.py::test_臨時倉不得把共用設定翻成_bare`。
已驗它紅在指定位置（`AssertionError: 共用 config 被翻成 bare`）。

**這條可以刪的前提**：上面兩個代價都已轉化成 docstring 裡的條件表與註解，
所以留在佇列的理由只剩「`裝_git_鉤子.py` 安裝後未驗入口存在」那條還沒做。

### 授權宣告寫錯不會紅，只會安靜地沒授權（2026-08-28，agy 派工實測）

**發作**：派 T11 給 agy 前，我照自己的推論在
`~/.gemini/antigravity-cli/settings.json` 寫 `permissions.allow: ["edit(<worktree>/**)"]`。
agy 全程**沒有寫檔權**，於是改用 `cat << 'EOF' >` 寫檔，那也沒授權，整個 run 中止。

**代價**：兩輪派工白跑。真因是 `edit` 根本不是合法的 action 名——
sol 從 binary 裡挖出 grant parser 的正則，證明全集是
`command|read_file|write_file|read_url|mcp|execute_url|unsandboxed`：

```
rg -a -o '\^\(command\|read_file\|write_file\|read_url\|mcp\|execute_url\|unsandboxed\)\\s\*\\\(.*\\\)\$' ~/.local/bin/agy
```

log 只寫 `ignoring invalid allow entry "edit(...)": unknown action "edit"`，
**設定檔照樣載入成功、CLI 照常啟動**。

**這是「宣告有、機制無」在權限層的版本**：宣告一條不存在的授權，
系統不拒絕、只是靜默忽略，於是「我以為授權了」與「實際沒授權」看起來一模一樣。

**轉化方向**：若 agy 的 capability manifest 要進計畫 16 通用 CLI 後端的軌道，
這是現成的 admission 負控素材——**grant action 全集要向 binary 驗證，不信文件**。
在那之前這條留在佇列，因為 nova 現在沒有消費 agy manifest 的元件。

**同場加映（同一次實測）**：`write_file(<絕對路徑>/**)` 的 entry 會被接受
（出現在 log 的 `Allow:[...]` 裡）但**不匹配**，`write_file(*)` 才通過。
接受 ≠ 生效，這是同一個形狀的第二面。

### 任何一次權限拒絕都會終止整個 run（2026-08-28）

**發作**：allowlist 沒有 `command(pwd)`，agy 第一步跑 `pwd` 被拒，
整個 run 在 1.6 秒、一個 turn 後結束。

**代價**：白名單必須涵蓋執行者**順手會用**的每一條指令，
而開放式實作任務不可能事先列全。實測結論是
**命令白名單無法用來限縮實作型執行者**——`command(uv)` 一條就等於允許任意程式
（sol 的原話：「白名單本身無法保證寫入僅限 worktree」）。

**現行做法與其誠實上限**：圍籬是 **worktree ＋ `--add-dir`**，不是白名單；
每次派工後我驗主 repo 的 `git status` 與 HEAD 沒被動。
**這防的是失誤，不防蓄意**——與計畫 20 T2「name/AST scan 防忘記不防蓄意」
的信任邊界一致。

**評估後決定不做的**：繼續往下鑽 `write_file` 的路徑樣式語法。
理由與量測：`command(uv)` 已授權任意程式執行，把 `write_file(*)` 收窄成
`write_file(<worktree>/**)` 買不到任何實際隔離，而每輪嘗試成本是一次派工往返。

  循環停在「預算耗盡」而那個後端從頭到尾沒花過一毛。
  歸零要**明講原因**（「成本 0，本機推論不計費」），不能靜默歸零——讀紀錄的人要
  看得出這個 0 是「不計費」還是「這次剛好沒花錢」。
  → 新系統對應：本地後端的 quota 狀態是 `NOT_APPLICABLE`，成本 0 且要有理由碼。

- **指向本機端點時，憑證必須是空字串而不是「不設」**
  `ANTHROPIC_API_KEY` 與 `ANTHROPIC_AUTH_TOKEN` 若只是不設，client 會沿用環境裡
  既有的官方金鑰去打你指定的 base URL——**真跑起來變成偷用雲端額度，而帳面上
  看起來像本機推論（成本已被歸零）。這種錯不會有任何錯誤訊息。**
  → 新系統對應：本地後端的 fingerprint 必須涵蓋憑證狀態，而不只是 base URL 與模型名。

- **launchd 只在登入時自動載入 `~/Library/LaunchAgents` 底下的 job**
  把 plist 渲染到別處（例如資料根）再 `bootstrap`，服務會跑得好好的、
  `launchctl list` 看得到、manifest 顯示 completed——**但重開機就不會回來，
  而且零紅零警告**。實測發作於 2026-08-25，成因是部署流程渲染完就地 bootstrap。
  → 新系統對應：部署的驗收不能只驗「現在在跑」，要驗「plist 落在自動載入目錄」。

  `importlib.import_module`／`__import__` 解析成普通 edge，非 literal 一律回
