# 外部效果與後端更新 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 【推論】讓資料庫狀態與外部世界之間的不可原子性成為明示契約：每個效果先有持久 intent，再依 endpoint operation 選 at-least-once idempotent 或 at-most-once，所有 crash gap 有 typed 結果；CLI 更新以 drain→pinned install→fingerprint verify 完成，不偷換在途 Pursuit。

**Architecture:** 【推論】Effect Authority 擁有 immutable intent、delivery attempt、receipt與 terminal truth；domain transaction 只把 intent 寫進同一權威 DB，獨立 relay 才碰 endpoint。`EffectDelivery` 是 ClaimSpec 0.2.0 的必填 conditional contract。At-least-once 在 send/receipt gap 可重送但要求目的端 dedup或收斂；at-most-once 先持久標記 attempt再送，gap 可能遺失但不重送。BackendUpdate 是效果面的 phase machine，由普通 Work 編排，resource gate 在 drain 開始即停新派工。

**Tech Stack:** 【推論】CPython 3.14.7、MachineSpec/FlowSpec、SQLite outbox leases、CAS receipts、async endpoint adapters、fake crashable endpoint、ClaimSpec runner。

**Spec:** 【查證】本檔「子系統規格」，以及[第三輪 CLI 更新與 EffectDelivery 定案](../sol-新局-第三輪.md#43-cli-更新的精確互鎖)、[第一輪 outbox 原則](../sol-新局-第一輪.md)。

## Global Constraints

- 【推論】語言不提供 `EXACTLY_ONCE`；endpoint operation 必填 `AT_LEAST_ONCE_IDEMPOTENT` 或 `AT_MOST_ONCE`。
- 【推論】domain event 與 effect intent 在同一 state-owner transaction 落盤；`DELIVERED` 絕不在該 transaction 內預寫。
- 【推論】relay 不能憑空發明 intent；intent bytes/digest/idempotency key/semantics/attempt policy 都 immutable。
- 【推論】每次 Work transition 最多 16 intents；pending backlog 10,000 後普通新 effects fail closed，不讓 relay storm 餓死 state commands。
- 【推論】network timeout 或不完整 receipt 固定 `DELIVERY_UNCERTAIN`，不能擅自分類成功/失敗。
- 【推論】CLI update 只接受 exact `target_version`，最多 5 attempts，backoff `[1s,5s,30s,120s]`，absolute deadline 15 minutes；不接受 `latest`。
- 【推論】v1 不保留 side-by-side binary；更新期間 backend 為不可派工，舊 execution 先 drain，更新後以完整 capability fingerprint 驗證。

## 子系統規格

【推論】`EffectDelivery` 固定欄位：`endpoint_id`、`operation`、`semantics`、`intent_schema/ref+digest`、conditional `idempotency_key` expression、bounded `attempt_policy`、`receipt_schema/ref+digest`、`success_postcondition`、`duplicate_policy`、literal `uncertain_terminal=DELIVERY_UNCERTAIN`。

【推論】EffectIntent states：`PENDING|LEASED|ATTEMPT_MARKED|DELIVERED|ABANDONED|DELIVERY_UNCERTAIN`。at-least-once 可由 expired lease 回 PENDING；at-most-once 一旦 ATTEMPT_MARKED 永不再 send。

【推論】endpoint admission：有 atomic idempotency key或 operation 收斂到 pinned target才可 at-least-once；其餘只能 at-most-once。adapter manifest不能 runtime 自動換 semantics。

`(EffectIntent machine digest, state)`。

**`ABANDONED` 與 `DELIVERY_UNCERTAIN` 的分界立在「結果可信性」**，不是語意：

- `ABANDONED` ＝ 重試耗盡**且每次嘗試都有明確失敗 receipt**——**確定未交付**
- `DELIVERY_UNCERTAIN` ＝ 結果不可知（network timeout、不完整 receipt、
  premark gap 皆屬此類）

**這是提案第一版寫錯後改的**：原文說 `DELIVERY_UNCERTAIN` 專屬 at-most-once，
而 19 行逐字寫「network timeout 或不完整 receipt **固定** `DELIVERY_UNCERTAIN`，
不能擅自分類成功/失敗」——**不分語意**。雙向殺手
`abandonment_requires_definitive_failure`：沒有明確失敗證據就記 `ABANDONED` 必紅，
有明確失敗證據卻記 `DELIVERY_UNCERTAIN` 也必紅。

**sol 立的通則（不宣稱三台機同構）**：

> 每個 failure-like 封閉集合都要問「**權威能否相信結果**」；可信與不可信若共用
> 同一 terminal，必須有額外證據證明沒有抹掉不確定性。

三層（Work 的 `FAILED_FINAL`、Update 的 `UPDATE_FAILED`、Effect 的 `ABANDONED`）
共有的是**這個裁分類型**，不是可共用的 edge／state invariant——三者的 authority、
觸發、終態 class 與恢復邊都不同。
