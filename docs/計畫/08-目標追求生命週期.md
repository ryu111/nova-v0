# 目標追求生命週期 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 【推論】建立 Work 與 Execution 之間獨立的 Pursuit 生命週期：同一搜尋策略可有最多 16 次執行、由外部判準回饋反覆改進、非終態暫停後換合格後端接手，且任何停止路徑都有外部界線。

**Architecture:** 【推論】Pursuit 擁有策略 identity、evidence/workspace scope、attempt lineage、局部 budget slice、checkpoint 與候選集合；不擁有 Work 最終選拔。一次 Execution 結束可 nominate 一個 CandidateBundle，Evaluation verdict 再觸發 submit/retry/stop。pause 不改 identity；只換到 pinned policy 已允許的 backend 是同 Pursuit 的新 Execution，改 model family／evidence scope／prompt family 或 capability fingerprint lineage 則必須新 Pursuit。

**Tech Stack:** 【推論】CPython 3.14.7、MachineSpec、SQLite state owner/leasing、CAS checkpoints/candidates、ClaimSpec evaluator、resource reservation ports、fake clock。

**Spec:** 【查證】本檔「子系統規格」，以及[第二輪 Pursuit 拆層裁決](../sol-新局-第二輪.md#2-q2目標追求是層而且現在就拆)、[第二輪 workload envelope](../sol-新局-第二輪.md#3-q3-workload-envelope是先訂出來再量測修正)、[第三輪生命週期與後端 fingerprint](../sol-新局-第三輪.md#4-q3所有需裁定歸零)。

## Global Constraints

- 【推論】固定基數 `Work 1 -> 0..8 Pursuit 1 -> 0..16 Execution`；v1 rollout 可把每 Work 同時 active Pursuit 設 1，但資料模型不得降成 1:1。
- 【推論】Pursuit nonterminals：`PLANNED`、`ACTIVE`、`PAUSED`、`PAUSED_CAPABILITY_CHANGED`、`WAITING_RESOURCE`、`WAITING_EVALUATION`；terminals：`SUBMITTED`、`EXHAUSTED`、`CANCELLED`、`POLICY_STOP`、`CRITERION_ERROR`。
- 【推論】`SATISFIED` 不屬於 Pursuit；合格候選只是 `SUBMITTED`，Work 才擁有是否選中與最終成功。
- 【推論】attempt 上限 16、Pursuit paid call 上限 128、absolute deadline pause 時不停鐘；任一先耗盡即 terminal。
- 【推論】Pursuit 不可讀其他平行 Pursuit 的 candidate/intermediate reasoning；交換後 lineage 必須標依賴，不能繼續宣稱獨立。
- 【推論】任何 Execution 只能 nominate 一個 CandidateBundle；同一 candidate digest × criterion revision 最多一個有效 final verdict。

## 子系統規格

【推論】`PursuitIdentity` 固定包含 `strategy_family`、`prompt_family_ref`、`model_family_policy`、`backend_policy_ref`、`evidence_scope_ref`、`workspace_scope_ref`、`tool_policy_ref`、`seed_policy`、`knowledge_snapshot_ref`；建立後 immutable。

【推論】**每個 `*_ref` 一律是 `{semantic_id, revision, digest}` 三元組，不是裸字串。**
理由：identity 比較若比字串，兩個不同 ref 指向同一份 bytes 會判「要開新 Pursuit」、
同一個 ref 底下內容漂移會判「同一個 Pursuit」——**兩種錯都不會有測試轉紅**，
Task 5 的 change matrix 就成了恆真格。帶 digest 之後字串相等 ⇔ 內容相等，恆真消失。
比較的依據是 `effective_content_digest`（該 ref 實際交付內容的 digest），
**不是只含間接引用的 manifest source digest**；完整三元組仍留在記錄中供稽核。
缺 digest 的 ref 進到比較一律 typed `UNRESOLVED_IDENTITY_REF`，digest 與 CAS bytes 不符亦然。

【推論】每次 retry 的輸入由 `checkpoint_ref + FeedbackPacket ref + next Execution selection` 組成；raw verdict 或 sealed evidence 不可進 execution input。

【推論】Pursuit 的**耗盡量測**是 lexicographic `(deadline_remaining, attempts_remaining, paid_calls_remaining, budget_remaining)`；只有外部 events 可單調耗減。暫時 quota 不可用不冒充永久耗盡，Pursuit 等到 deadline 或資源 authority 的 permanent denial。
**命中上限是偵測（typed `EXHAUSTED`），不是進展證明。** 這個量測只證成 safety（不會永遠跑下去），
不證成 liveness（有在前進）——Alpern–Schneider 1985 證明任何性質都是 safety ∩ liveness，
所以只寫得出 safety 的規格是**留白**不是完備。「有沒有在前進」在本計畫目前是空的，
不得用本量測冒充。（Holzmann Power of Ten Rule 2 與 JPL D-60411：上限要靜態可證，
超限路徑是 assertion failure＝偵測，不是證明。）
