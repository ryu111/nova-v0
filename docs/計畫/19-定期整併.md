# 定期整併 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 【推論】把「系統只會累積」的反向力量做成普通 Work：整併可替換保證的可執行表示，但不能縮減不可變的行為義務、遺失任何固定負控、增加 Guard 逃生使用量，review 與訊號都只能提案。

**Architecture:** 【推論】Definition Authority 擁有 `GuaranteeObligation`、`ClaimCoverage`、claim revision status 與原子 alias；Work Authority 擁有 SimplificationWork／RequirementChangeWork 的流程；分析器只從事件與規格算 immutable signal evidence，沒有任何狀態寫權。合法合併以 `ClaimMergeSpec` 把 2–4 個 source claims 映成恰一個 successor，舊 claim 轉 `ALIASED` 而不刪除；真正撤銷需求只能走不同 command set 與短效使用者授權。

**Tech Stack:** 【推論】CPython 3.14.7、JSON Schema 2020-12、ClaimSpec 0.2.0、MachineSpec／FlowSpec、SQLite single-owner transaction、CAS EvidenceRecord、Hypothesis stateful tests。

**Spec:** 【查證】本檔「子系統規格」、[定期整併需求](../需求-定期整併.md)、[總覽的合併裁決](./00-總覽.md#2-定期整併的新裁決合併-representation不縮-obligation)與[雙方簽字](../控制端審查.md#六簽字2026-08-26)。

## Global Constraints

- 【推論】no-weaken 比較的是 active `GuaranteeObligationId` 覆蓋，不是 ClaimSpec 檔案數、digest 數、行數、圈複雜度、重複率或 mutation raw kill rate。
- 【推論】`GuaranteeObligation` 一經 admit，`obligation_id`、authority、subject contract major、sources 與固定 control refs 不可原地修改；更正只能新增 revision／successor edge。
- 【推論】一份 `ClaimMergeSpec` 恰有 2–4 個 sources、1 個 successor、同 authority、同 subject contract major；每個 SimplificationWork 最多一份 merge，沒有 waiver。
- 【推論】每個 source obligation 都要出現在 successor coverage；每個舊 `ControlRef` 的 canonical bytes 與 digest 原封不動，並對 successor actual 重新 direct-run。
- 【推論】successor actual／positive 必須綠；所有舊 negative／named mutation 必須以原 `must_fail_exactly` direct red；廣泛 mutmut scan 只產生 diagnostic evidence。
- 【推論】`escape_count_after <= escape_count_before`；比較的是同一 MachineSpec／Guard proof-cell 集合的已准入逃生計數，不能藉重新命名歸零。
- 【推論】source claim 只會 `ACTIVE -> ALIASED`，永不刪除；successor `DRAFT -> ACTIVE` 與 sources alias 必須同一 transaction。
- 【推論】v1 trigger 固定 `MANUAL_STAGE_BOUNDARY`；所有 structural signals 都是 record-only，review 只能建立 proposal，沒有直接寫 Definition Authority 的 port。
- 【推論】產品保證撤銷不是 simplification。它必須走 `RequirementChangeWork`、user-authority `RequirementRevocation`、完整 impact closure、replacement behavior ClaimSpec 與 10 分鐘 one-use ApprovalEnvelope。

## 子系統規格

【推論】`GuaranteeObligation` 是需求層級的穩定身份；`ClaimCoverage` 是某個可執行 ClaimSpec revision 對義務的覆蓋關係。多個 claim 可覆蓋同一 obligation，一個 successor 也可覆蓋多個 obligation；因此合法合併不需偽稱兩句文字相同，只需證明既有義務與 controls 全部仍由可執行 realization 承接。

【推論】`ClaimMergeSpec` 固定欄位為 `merge_id`、`source_claims[2..4]`、`successor_claim`、`preserved_obligations`、`preserved_controls`、`escape_count_before`、`escape_count_after`、`evidence_refs`、`approval_envelope_ref`；所有 ref 都含 semantic id、revision、digest，拒絕浮動 `latest`。

【推論】合法 merge 的驗證順序固定為 structural → authority／contract compatibility → obligation set inclusion → byte-identical control carry → successor actual／positive → each carried negative direct red → escape budget → approval envelope → atomic activation。前一步失敗就不跑後一步，避免用後來的綠掩蓋較早的不合法。

【推論】RequirementChangeWork 的 command surface 與 SimplificationWork 分離：前者唯一可提出 obligation retirement，後者的 typed command union 根本沒有 `retire`。授權 envelope 綁定 `work_id + revocation_digest + replacement_claim_digest + impact_closure_digest`，10 分鐘過期且 consume-once。

```text

REQUIREMENT_CHANGE_EVALUATING
REQUIREMENT_CHANGE_AWAITING_USER_APPROVAL
REQUIREMENT_CHANGE_ADMITTING

REQUIREMENT_CHANGE_REJECTED
```

  轉移（**一律用全名**，理由見下）：
  `REQUIREMENT_CHANGE_PROPOSED → REQUIREMENT_CHANGE_EVALUATING →
  REQUIREMENT_CHANGE_AWAITING_USER_APPROVAL → REQUIREMENT_CHANGE_ADMITTING →
  REQUIREMENT_CHANGE_ADMITTED`；
  `REQUIREMENT_CHANGE_EVALUATING|REQUIREMENT_CHANGE_AWAITING_USER_APPROVAL|
  REQUIREMENT_CHANGE_ADMITTING → REQUIREMENT_CHANGE_REJECTED`；
  任一非終態到達 absolute deadline → `REQUIREMENT_CHANGE_EXPIRED`。
  `REQUIREMENT_CHANGE_EVALUATING` ＝ impact closure 由 reference graph compiler **重算**
  （不採信提案者自列）＋ replacement claim 驗證；
  `REQUIREMENT_CHANGE_ADMITTING` ＝ consume `ApprovalEnvelope`
  ＋ Definition transaction（Task 5 同款原子）。

  **本段一律用全名，不用縮寫。** 第一版宣告完七個前綴之後，緊接的轉移行就用回
  無前綴的 `PROPOSED → EVALUATING → …`——**撞號以散文形式回流**，掃描器會把那些
  裸 token 對到 461 行的 SimplificationWork。立了規則又在相鄰的文字裡違反它，
  等於沒立。提到 SimplificationWork 時一律寫成
  `(SimplificationWork machine digest, state)`，不留可被誤認的裸 token。

  **為什麼加前綴**：本檔 461 行的 SimplificationWork 機器已宣告
  `PROPOSED|EVALUATING|AWAITING_APPROVAL|ADMITTING|SUCCEEDED|REJECTED|EXHAUSTED`。
  兩台機器若共用 nonterminal 名字，**任何裸 grep 狀態字串的測試都會被另一台滿足**
