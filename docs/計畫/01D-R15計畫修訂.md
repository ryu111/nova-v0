# R15 計畫修訂 Implementation Plan

**Goal:** 【裁定】把 R15-01／02／03 寫成可執行的遷移計畫：先補 typed producer result、`STRING_SET` compiler 與 T13 gate，再逐份把十份 catch-all claim 遷移到 revision 2，保留 direct evidence。

**Architecture:** 【推論】本計畫只修改 01 的 T13 阻塞宣告、ClaimSpec／compiler／執行鏈所屬實作與十份 claim；不修改 `docs/計畫複驗.py`。R15 gate 是可執行的 architecture checker，由 `工具/驗全部.py` 依 `架構/目錄規則.toml` 的 `[[gate]]` 執行。T13 在 debt 非空時必須是 `BLOCKED`；只有 debt 清空且 typed result、compiler 都 ready 才能是 `UNBLOCKED`。

**Spec:** 【裁定】R15-01／02／03（`docs/決策/計畫修訂決議.md`）；【推論】`STRING_SET` 的 wire shape 是唯一字串的 JSON array，compiler／runtime 排序去重，未知舊 compiler 回 typed unsupported；未知 producer result 不得變成普通 `code`，不得進 `ACCEPT` 或 `CLAIM_REJECTED`。

## Design issue record

【硬傷紀錄】核准設計同時寫「拆成 12 個 task」與「第 1、2、3 個 task 加後 10 個 migration task」。後者機械計數為 13，不可能同時滿足 12。為保留裁定列出的十份 claim，不默默少遷移一份，本計畫採 **13 個 task**：3 個基礎 task 加 10 個逐份 migration；01 Task 13 的依賴／阻塞條件同步指向 01D Task 1–13。

## Global Constraints

- 【推論】跨計畫引用一律寫完整 `計畫 01 Task N` 或 `計畫 01D Task N`；本檔的裸 `Task N` 只指本計畫。
- 【推論】每份 migration 各自建立 revision 2、`supersedes` 舊 revision，舊 claim／evidence 不覆寫；每份都重跑 actual、positive 與全部 fixed controls。
- 【裁定】migration debt manifest 是 machine-readable、只准縮的集合基線；它凍結十份決議名單，只擋新增 catch-all，不擋名單內既有十份。既有十份必須各由自己的 migration task 清除，清除一份就從 `debt` 移除一份。
- 【推論】R15 gate 的負控必須同時證明：新增不在基線的 catch-all claim 會紅；manifest 把 debt 擴張到基線外會紅；`BLOCKED`／`UNBLOCKED` 與 debt 狀態不一致會紅。
