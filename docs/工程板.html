nova 與 Claude 的關係

nova 本體就是產品：它是宿主引擎，claude 與 codex、gemini、本地模型平級，都只是後端的一種。 Claude 在這套系統裡出現三次，位置完全不同——把它們混成一個「Claude 在跑 nova」，就會把驗收權還給被驗收者。

#Claude 出現的位置能做絕對不能做
①Claude Code外部實作者 · 不在 nova 內寫 code、跑測試、commit；提出規格修訂宣告自己完成；改已准入的 ClaimSpec、固定負控、must_fail_exactly
②Claude 會話命令發起者 · 應用邊界的 client送 13 個 bootstrap command 之一；訂閱事件 tail；按 digest 取 GraphBundle送目錄外的命令；代寫 terminal／verdict／ledger 餘額／ACTIVE 狀態／delivery receipt
③Claude Agent SDKnova/介接/執行者後端/claude_agent_sdk/產生 BackendEvent 觀察、候選產物、逐 bucket RateLimitEvent宣告執行終態；延長任一外部限額；改預算；直接碰 endpoint（只能寫 EffectIntent 交 relay）
計畫 14 對 Claude SDK 特別封住的七處——它們不是「多塞幾個 SDK 欄位」，每一條都對應一個已知會靜默出錯的形狀： ① manifest fingerprint 對 SDK／CLI／model／protocol 版本敏感，不留 UNKNOWN capability； ② 未知 SDK message 是 PROTOCOL_FAULT 而不是被 drop，result.success 只是觀察； ③ 外部封套可取消 SDK，限額仍由父層掌握（SDK 官方文件自己承認沒有 top-level session timeout）； ④ RateLimitEvent 逐 bucket 保存（five_hour／seven_day／model-specific／overage 不得合成單一狀態）； ⑤ 只宣告 INVOCATION_START；沒有 turn-boundary 重掛能力就明說 unsupported，不冒充「壓縮後仍在」； ⑥ 候選可見的 projection 不含 sealed criterion 或任何 registry； ⑦ 工具授權／結構化輸出／代理樹成本逐一映射，setting_sources=[] 封閉 ambient config—— 因為 usage 不含子代理，核銷必須走 total_cost_usd／model_usage 並標明 scope，否則凡是委派的執行都少算。

分層

十三層，橫軸是同層平行的模組，縱軸是依賴方向。依賴只能向下——上層可用下層，下層不得知道上層。2026-08-27 起這條不再靠自律：架構/目錄規則.toml 宣告、架構/檢查工程規範.py 執法，動態 importlib.import_module 寫的違規邊也抓得到。

與總覽 §6.6 的兩處出入　總覽表寫「設施／」且只列九層；21 份計畫一致寫 nova/基礎設施/（159 比 0），且實際用到十三個第一層目錄。2026-08-27 裁定以計畫實際用法為準——多出的 約束／維護／內容庫／證據庫 的 predicate 逐字引用各自擁有計畫（12／19／04）的 Architecture 段。

權威架構

三個縱向生命週期產生宣告，四個橫向權威做裁定。生命週期不裁定自己的成敗——這是整個系統的中心規則，也是為什麼判準、帳與保護清單都放在執行者碰不到的地方。

分層資格

四個條件同時成立才算一層，缺一不可。沒有自己生命週期的東西不是層，是資料。

#條件
1有穩定身分與封閉終態集合
2承載無法下推到下一層的保證
3透過一個窄且可替換的契約組合下一層的多個生命週期
4擁有自己權威狀態的恢復責任

訊息流

從使用者說一句話，到畫面上那一格亮起來，中間經過哪些手、每一手交出什麼。這條路徑決定了未來 UI 能顯示什麼——因為 UI 只被允許讀最後那條事件流。

建造順序

依信任根排序：能力假設與三個信任根先立，領域核心次之，外部世界再次，反向力量與總驗收最後。編號序就是合法拓撲序——照號碼做不會違反任何依賴閘。

複驗改變了什麼　修訂前第一次碰到真 SDK 是第 120 個任務，那時前面 470 個檔案的契約已經定型。新增 01B 之後，靜態 surface probe 落在第 15 個任務、有界 live smoke 在 Phase A 結束前——SDK 假設若是錯的，在還來得及改契約的時候就會發現。

能力落在哪一層

這是複驗最重要的一次修正。能力契約屬於跨後端的契約層，不屬於任何一個 adapter。

複驗發現

控制端提出五條、sol 逐條附證據裁定並補三條。第 4 條 sol 正確地反駁了一半：live LLM 品質不該混進 deterministic release gate，該拆成雙軸。八條都已落地並經獨立驗證，不是採信自報。

01

SDK 工具授權與結構化輸出零落點

確認

21 份計畫約 500KB，allowed_tools／can_use_tool／output_format 等 17 個 SDK 能力字串全部零命中。四份後端計畫形狀一模一樣。

修訂契約層新增三個 PolicyRef 與三個 typed outcome，落在 05 而非 adapter。

02

子代理成本系統性少結算

確認

usage 不含 subagent，total_cost_usd 與 model_usage 含。核銷若走 usage，凡是委派的執行都少算——而 reserve 是防超支的唯一機制。

修訂UsageEvidence.scope 三態＋核銷來源順序＋USAGE_SCOPE_INCOMPLETE；delegation 算不出 worst case 就不得啟用。

03

MCP 靜默消失

確認

計畫 13 的邊界只有 CLI／Python／HTTP，13 個 bootstrap command 沒有 MCP。這不是裁掉，是沒被處理。

修訂MCP 作為第四 transport adapter，與其餘三者同命令同結果 parity。

04

release gate 不含 LLM 維度

確認一半

DEPLOYABLE=true 可以在一次真 LLM 呼叫都沒有的情況下成立。但把 live 品質混進 deterministic gate 是錯的——sol 正確反駁了這一半。

修訂拆成 CORE_DEPLOYABLE × BACKEND_READY[fingerprint] 雙軸；live probe 只測可機械能力。

05

第 101 個任務才碰到真 SDK

確認

claude_agent_sdk 只出現在計畫 14 與 20，而 01→13 幾乎全序列。任何 SDK 假設若是錯的，在 500 個檔案的契約定型後才會發現。

修訂新增 01B 前置計畫：靜態 surface probe 必跑，有界 live smoke 在 Phase A 末端。

06

ambient configuration 沒封閉

sol 補

計畫 14 的 fingerprint 沒有 setting_sources、filesystem settings、hooks、MCP servers。同一 fingerprint 可能載入不同 prompt 與工具——可重播性漏在這裡。

修訂v1 預設 setting_sources=[]；非空來源必須 exact allowlist 且內容定址並納入 fingerprint。

07

SDK 工具會繞過效果權威

sol 補

工具授權只回答「准不准呼叫」，不回答「寄信、推 remote ref 是否經 outbox」。這比一般 syscall 更容易發生，因為它是系統主動提供的正常能力。

修訂工具四分類；EFFECT_INTENT_REQUIRED 工具只能寫 EffectIntent 交 relay，直接打 endpoint 即轉紅。

08

能力證據沒有新鮮度

sol 補

舊版 SDK 測出來的 can_use_tool 結果會在升版後繼續替新版背書。

修訂CapabilityEvidence 綁 exact fingerprint、probe version、expires_at；任一 component 改變立即失效。

已定案

nova 是十三層，不是九層

總覽 §6.6 的表寫「設施／」且只列九層，但 21 份計畫一致寫 nova/基礎設施/（159 比 0），且實際用到十三個第一層目錄。裁定以計畫實際用法為準；多出的 約束／維護／內容庫／證據庫 的 predicate 逐字引用各自擁有計畫（12／19／04）的 Architecture 段，不由實作者發明。

Tasks 1–4 的 ClaimSpec 閘推遲

runner 在 Task 9 才建立，卻被 Task 1–4 呼叫；Task 1 的 claim 檔沒有建立點。裁定不改計畫、推遲補跑。這筆欠帳只有文件承諾撐著，Task 9 之前沒有任何機制會因它轉紅。

中文標點不是 confusable

Ruff 的 RUF001／002／003 把全形標點判為 ambiguous，與「一切繁體中文」直接衝突（103 處）。用 allowed-confusables 白名單放行——那是 Ruff 為非拉丁語系設計的入口，不是 baseline ignore。D400 要求 ASCII 句點結尾同理排除：保證義務是 D1xx 的「必須有 non-empty docstring」，不是標點形狀。

固定負控 fixture 排出 lint 範圍

事前固定的錯誤 subject 就是要壞的。讓 repo 自己的 ruff check 去管它們，Plan Exit Gate 永遠不可能綠。這是掃描範圍的裁決，不是 baseline ignore。

schema 欄位名一律 ASCII，值可中文

TOML bare key 不接受非 ASCII，而 config 的欄位名本來就在語言規則的 ASCII 例外清單裡。架構/目錄規則.toml 因此是 name／order／allow_io，中文只出現在值。同理 dependency-group 名用 dev。

工程規範 day-one 生效

Ruff formatter（100 字元）＋lint＋import 排序、mypy strict＋warn_unreachable、complexity ≤10／branch ≤12／參數 ≤6、module ≤400／class ≤250／function ≤60 邏輯行。全部在寫第一行 production code 之前就要有牙。

不另立 01A，擴充 01 Task 1

排在 01 後面就管不到 01 寫出的第一批 code；排平行又跟 01 搶 pyproject.toml 的建立權。工程檢查本來就是 day-one 工具鏈信任根，不是另一個領域子系統。

一個檔案命中兩層就拆檔

六個頂層與九個 nova/ 層都寫成決策樹。若一個檔案同時合理命中兩層，不准挑一個塞進去——那表示它有兩個改變的理由。checker 要求每條路徑恰好命中一個 owner。

中文識別字的雙軌規則

Python 內部識別字可全中文或全 ASCII，必須 NFC，同一識別字禁止混 Han 與 Latin（Python 解析時做 NFKC 正規化，「bytes 不同解析同名」是真風險）。shell 變數與函式名 ASCII，且動態生成的 shell 變數名直接拒絕——靜態檢查器證明不了它的字元集合。

新檔必須先列入某份計畫的 Create

由 plan catalog ＋ placement checker 執法。這條擋的是「先亂放，以後整理」——而那正是結構開始腐爛的地方。

本地模型可立即當開發執行者

不必等計畫 17。但它不是正式 nova 後端——正式後端要接 CAS、Execution、Resource、Effect、Constraint 與 Application 契約。預設只評測 8bit，4bit 與原版不進主派工；只准 fixture 生成、封閉列舉、跑既有命令、單檔機械修改。

知識檢索 v1 不做向量

exact scope filter → ACTIVE／TTL／profile 驗證 → provenance DAG 決定性閉包 → 全部 eligible 進 snapshot，不做 top-k。加向量要先過 30 天量測門檻，再過「100 次索引重建 digest 完全一致」。

知識溢位不得靜默截斷

預算 min(32_768 tokens, usable context 的 25%)；放不下就回 typed KNOWLEDGE_CONTEXT_OVERFLOW——不截尾、不摘要、不臨時改用相似度。

MCP 可最後實作，語義現在就定

core 加 OperationRef／OperationReceipt／get_operation，receipt 只由事件投影 fold 出來。舊名映射封閉：get_ticket→get_operation、start_loop→DEPRECATED_OPERATION、未知名稱 UNSUPPORTED_OPERATION。

實作者不得改弱 ClaimSpec

這是控制端原本漏掉的洞。三權分立不夠——還要禁止實作者動已准入的判準、固定負控與 must_fail_exactly。規格真的錯就停下來走 RequirementChange。

一個 task 一個 writer

平行單位是完整 task 不是 step；先取檔案 lease；下游只認綠 commit SHA，不讀別人未提交的工作樹。多 agent 不是免費加速——協作 agent 在同總工作量下實測落後單 agent。

完全重做，不重構

舊經驗與坑保留，測試不保留——150／227 個測試檔 import 內部模組、釘住 65 條舊層路徑。留著會把結構拉回去。

三個宣告不可互推

Attempt.terminated（執行結束）／Assessment.accepted（符合凍結定義）／Commitment.verified（外部生效）各自獨立宣告。

保證義務不可縮減，表述可以合併

量錯對象了：兩份等價寫法合成一份時 representation 減少，但行為義務不該減少。不變式改綁 GuaranteeObligationId。

自動整併 v1 不存在

MANUAL_STAGE_BOUNDARY；signals 只記錄不觸發。要加 threshold 必須有 policy revision、回測證據與「無理由常數」負控。

新計畫不重編號

插入 01B 而非順延。重編號要動 20 份檔案的交叉引用，而那正是會生出不一致的地方。

mutation kill rate 不是閘

等價突變讓百分比不可用。唯一有驗收權的是事前命名的 mutation 被指定 predicate 殺掉。

v1 isolation 明示 COOPERATIVE_PROCESS

防忘記／出錯，不防蓄意。can_use_tool 是 SDK 工具路徑的真閘，不是 sandbox 升級。

前端只讀事件流

view 必須能由事件流的純函式重建，不對領域發任何額外查詢。model 不因 view 而改變。

授權收據的自我參照循環

已解

准入授權收據綁 exact PR head SHA，卻被寫進同一個 PR——寫進去，head SHA 就變了。 第一次把收據本體移出 tree，循環只是從 bytes 換成 metadata：manifest 新增 receipt_digest／receipt_locator，而收據綁 manifest digest，寫這兩欄一樣改變它們。
